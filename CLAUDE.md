## Project overview

Steam achievement auto-tracker, running **entirely locally**: SQLite data store + Node CLI + a local HTTP server for the HTML Dashboard. Tracks achievement completion across the user's whole Steam library.

User-facing docs live in `docs/`. **The README addresses one reader: someone running the packaged Windows app.** It exists in two languages — `README.md` (English, the one GitHub renders) and `README.zh.md` (Chinese) — each linking to the other on its first line; **a change to one is not finished until the other carries it.** It follows a copy template the owner supplied (emoji headings, blockquote tagline, `---` rules, numbered feature subsections, bullets leading with a bold label and a colon — fullwidth in the Chinese, halfwidth in the English), features first. **The bar for including anything is 「would a person who only double-clicks the exe act on this」** — file names, the port, the exe's name, the local-server architecture and close-to-tray are all out, cut twice after the owner said the draft carried too much technical context. **Nothing in it names a command, a runtime or a source file**; the two exceptions are single links to `docs/cli.md` and, from 「参与贡献」 / Contributing, to `CONTRIBUTING.md` — that section addresses a contributor rather than the exe's user, and it is the only place in the file that does.

**Three facts must not drift back into either README, and a plausible-sounding rewrite gets all three wrong:** 「立即同步」 does **not** consult the 12-hour staleness gate; the program reports **tokens and never money**; a manual overwrite-update requires quitting from the tray first. **Each README is written in its own language, never translated out of the other** — an em-dash every third clause and mid-sentence bolding read as machine translation in the Chinese, and the English fails the same way in reverse. House spelling in the English docs is `-ise` (`unrecognised`, `localised`).

## Stack constraints

- **The runtime has zero npm dependencies** — `dependencies: {}`, no root `node_modules`, Node built-ins only: `node:sqlite`, global `fetch`, `node:http`, `node:test`. "No install step" is what makes `git clone && node tracker.js` work and what keeps the packaged build's `extraResources` an allow-list of plain files. **No build step either — the pages are one big string each**, which is why the design tokens are duplicated rather than shared.
- **npm is allowed as a build-time tool; the runtime stays dependency-free.** The font under `assets/fonts/` came from npm, then the files were committed and the package thrown away. Prefer that shape. A real runtime dependency is now *allowed* but still needs an argument.
- **"Offline-only" was never true and should not be quoted as a constraint.** The Dashboard loads capsule images from `cdn.akamai.steamstatic.com`. What is local is the *data* (SQLite, no telemetry, server bound to 127.0.0.1). Say that instead.
- Requires **Node 24+** (`node:sqlite`). ES modules (`"type": "module"`).

## Development workflow

```bash
node tracker.js <command>                # everything is a subcommand; `node tracker.js help`
node --test --test-reporter=dot          # test suite
node --check lib/foo.js                  # syntax check (silent on success)
```

**Run the tests with `--test-reporter=dot`.** The default `spec` reporter prints a line per test — hundreds of green ticks burying the one line that matters. On a failure `dot` still prints the whole `Failed tests:` block.

**What `dot` does not print is a summary line.** There is no `tests N / pass N / fail 0` tail, so **the green signal is the exit code plus the absence of an `X`**, not a sentence. Two consequences: do not pipe it through `tail` and then report "all tests pass" because nothing looked wrong (`| tail -4` on a red run shows dots and hides the failure block above them); and when you actually want a count, use the default reporter for that run.

**Everything a developer reads is English** — comments, documentation, test names, **commit messages and pull request titles and bodies**. This is the same audience rule `test/i18n-boundary.test.js` states at the top, and it extends to the history: the reader of a commit message is whoever is bisecting, not the exe's user. The user-facing side is unaffected — that is bilingual, and `README.md` / `README.zh.md` are the two halves of it.

There is no build, no push, no deploy. Editing a file and re-running the command is the whole loop. `serve` does not hot-reload — restart it after changing `lib/` (`Dashboard.html` and `lib/rpc.js` are re-read per request).

Both sides render the one `notion.tokenBad` entry now. Same shape as the `result.startsWith('已勾选')` coupling `guides.js` already warns about — **if you find yourself matching on a sentence, the thing you want is a `code`** |
| ↳ `lib/cli-messages.js` + `lib/tracker-messages.js` | The same shape for what only ever reaches a **terminal**: `serve`'s own log, and the CLI's. Separate from `messages.js` because CLAUDE.md forbids a Dashboard-reachable message from naming a command line, and these two may — which is the most useful thing to say to somebody who typed one. They are split from each other by **size** rather than audience, and `clog` reads both as one table so there is a single lookup and a single language |
| `lib/lang.js` | Which of two stored values to show: `normalizeUiLanguage`, `pick`, `achievementName`, `gameName`, `gameNamePair`. The preference written once, instead of `d.name_cn \|\| d.name_en` spelled out at each call site |
| `lib/steam.js` | `SteamClient`: owned games (+Unvetted diff), player achievements, schema, name lookup, store search, `fetchGameIcon`. Every request carries `AbortSignal.timeout` — without one the ceiling is undici's **five minutes per call**, and a full sync makes hundreds |
| ↳ **two delay knobs, and merging them is the dangerous edit** | `requestDelayMs` (100 ms) paces `api.steampowered.com`; `storeRequestDelayMs` (300 ms) paces `store.steampowered.com`. The Web API side is **measured** — 400 back-to-back `GetPlayerAchievements` at 0 ms, ~11/s for 36.6 s, zero 429, plus a clean descending ladder — so 100 ms carries a 2× margin. **The store side is deliberately not measured**: hammering store HTML to find its ceiling earns an **IP-level** block rather than a key-level throttle. **The dangerous edit is putting `this.delay` back on a store call** — nothing errors, the sync works, and the consequence surfaces only once something is blocked. `steam-delay.test.js` pins each site by the *next* `sleep(` after the call, all five directions mutation-tested |
| ↳ **the icon is the store header, and the free source is the last resort** | `GetOwnedGames` carries a square-icon hash at no extra request, and that asset is **32×32** — several times smaller than the slot Notion draws it in, so nearly every page written carried a soft icon while nothing failed. Order is now `…/steam/apps/<appid>/header.jpg` (460×215, **HEAD-checked** — a guessed-wrong icon renders broken, which is worse than none), then appdetails for the content-hash path, then the square icon. Each store asset carries its own hash, so a larger capsule cannot be derived from a resolved header address — measured: `capsule_616x353.jpg` and `library_600x900_2x.jpg` 404 there while `header.jpg` returns 200, which is why one size is used everywhere. The appdetails step is a **try/catch, not `.catch()`**: a `steam` object without that method throws synchronously, before there is a promise to attach to, and a missing method must cost an icon rather than the whole call |
| ↳ cover art is guessed first, then asked for | `thumbUrl` guesses `header.jpg`, right for the large majority and free. Steam has moved some store assets under a per-asset content-hash path that is derivable from nothing we hold — measured over 314 games, 9 unreachable, all recent appids, **so this number only grows**. A failed image triggers one `appdetails` lookup, cached into `games.cover_url`. **Guess first, ask second**: asking up front would put a rate-limited store call on all 314 to fix 9. **A failure is deliberately not cached** — rate limits and unpublished pages both look like "no cover" and both expire. `setGameField`'s allow-list is an injection gate (the column name is interpolated into SQL), so a new writable column must be registered there |
| `lib/sync.js` | `syncLibrary` → `syncAchievementStats` → `syncAchievementSchema`, `fullSync`, `computeAgcrStats` |
| `lib/server.js` | HTTP server (127.0.0.1 only), `/api/*` dispatch, background sync state + staleness check, guide discovery on start, auto checkbox tick after each sync |
| ↳ **binding to 127.0.0.1 is not a security boundary** | Any page the user visits can `POST` to `http://127.0.0.1:8777/` — `text/plain` is a CORS simple request, so there is no preflight. The attacker cannot *read* the reply, but every side effect lands, and those include deleting games, overwriting `config.json`, starting a run that spends money, and `/restore`, which replaces the whole database. Every request passes `isLocalCaller`. **Two headers, each covering what the other cannot**: `Origin` blocks cross-site forms and fetches (a *missing* Origin is the launcher/CLI/tests and is allowed; the literal string `null` is refused); `Host` blocks **DNS rebinding**, which defeats the Origin check *and* lets them read responses — which is why the `Host` check applies to `GET` too. `server-guard.test.js` asserts the API method **was not executed**, not merely that the status was 403 |
| ↳ the async request handler needs an outer `catch` | `createServer(async …)` means one throw is an unhandled rejection, which Node ≥15 answers by **killing the process** — a single malformed request is not "one 500", it is 「后台服务意外退出」. Known instance: `decodeURIComponent('%')` throws, so `<img src="…:8777/%">` on any page took the server down. `safeDecode` plugs that one; the outer `.catch` is what makes it not happen again |
| ↳ a body limit that only rejects does not limit anything | `readBody` checked the cap **before** appending and called `req.destroy()`. Rejecting the promise ends the *handler*, not the *stream* — the `data` listener stays attached and the string keeps growing. Measured: a 1 MB cap fed an 80 MB body ended with 80 MB in memory. Same shape in `readBinaryBody` (200 MB cap) |
| ↳ **a dedup gate checked before an `await` is not a gate** | `startGuideGen` ran `isPending(appid)` and then `await`ed two live Steam calls before anything recorded the appid — two clicks both saw an empty state, the same guide generated and paid for twice (reproduced with 200 ms of Steam latency). `claim(appid)` **tests and records in one synchronous step**, released in a `finally`. `startBackgroundSync` never had the bug because its check and its `begin()` are adjacent synchronous lines — copy that shape. `guidequeue.test.js` |
| ↳ cancelling — one `AbortController`, not a flag anywhere in the pipeline | `runGuideGen` makes one per job and hands `.signal` to `generateGuide`/`patchGuide`, which thread it into every `session.ask()` and nowhere else — not into the Notion landing at the end, which is a few hundred ms of local work not worth tearing down mid-write. `cancelGuideGen` picks between two shapes by asking `guideGenState.snapshot()`: the **running** job gets `controller.abort()`; a **queued** one is spliced out and given a synthetic `finished` record on the spot, because nothing else would ever un-grey that row (`setGuideBusy` only fires off a `finished` entry, and a job that never reaches `begin()` produces none). The controller lives *inside* `createGuideGenState`, set alongside `begin()` and cleared in a `.finally` alongside `end()` — two closure variables drifting apart is exactly how a stale controller would end up letting a later job's Cancel button abort a request that already finished. **Cancellation needed no new branch in the retry ladder**: a cancelled `AiError` carries no `.code`, so it is neither retryable, splittable, nor `CHUNK_LOCAL` — rung ③ already rethrows anything shaped like that immediately, the same path a dead network or a 401 takes. The one exception is the post-round classification pass (`regroup`), the sole AI call reachable *after* every writing round already succeeded; its own catch degrades any failure into "skip the tidy-up, land anyway", which would silently turn a Cancel click into "finished anyway" — so it checks `err.cancelled` first and rethrows before rolling back. `test/guidequeue.test.js` covers the state half and an end-to-end HTTP cancel against a real (fetch-intercepted) provider; `test/ai.test.js` + the two vendor files cover the network half: an external signal and the idle timeout share one internal `AbortController`, told apart afterwards by asking the external signal itself, never by which one the catch block happened to see first |
| ↳ **both pipelines report progress through one function** | `runGuideGen` hands `onProgress` to `patchGuide` or `generateGuide`, and the two handlers were separate copies. How many steps a run has, which one it is on and how many entries have been written were added to the generation copy — the partial rewrite then shipped a release reporting none of the three, and its tool events put the provider's own vocabulary word (`search`) on screen under a Chinese interface. **Nothing errored and nothing was missing from the screen; it simply said less**, which is why no report and no test caught it. `reportProgress` is the shared half and both handlers return through it, with `stepReporter` and `toolNote` likewise one implementation each. `guidequeue.test.js` asserts there are exactly **two** call sites and that neither handler keeps its own copy |
| ↳ the corner buttons were one pixel under WCAG's minimum | `.gen-close`'s `var(--s1)` padding (4px) plus the 15px icon is 23×23 CSS px — one under Success Criterion 2.5.8's 24×24 minimum pointer target. **The mobile "44pt/48dp" number is the wrong one to reach for here**: that is native-platform guidance and does not apply to web at all. `var(--s2)` clears it at 31×31. **Also had no `:disabled` style whatsoever** — `genCancelBtn.disabled = true` on click relied on the browser default, which on an otherwise unstyled `<button>` is close to invisible, so a press looked ignored for the ~3s until the next poll. Found by running the ui-ux-pro-max community skill's local guideline search against this component rather than eyeballing it |
| ↳ the button's own top offset does not equal the container's | The corner buttons had shared `top: var(--s1)` (4px from `#gen-bar`'s edge) while the text they sit beside starts at the container's own `padding-top`, `var(--s3)` (12px) — two different anchors that happen to be close, not the same one. With the buttons grown to 31px tall (the row above), the gap became visible: **button centre at 19.5px, first text line's centre at 12 + (12px × 1.6 line-height)/2 = 21.6px** — a real, measured 2.1px mismatch, not a rounding error. `top` is now the literal `6px` that equalises the two, with the arithmetic written out in the comment so the next resize (either the button or `--fs-sm`/`--s3`) has something to recompute against instead of eyeballing it again |
| ↳ a circle-plus-glyph badge was the wrong family for a stop icon | The first cancel icon copied `i-check`/`i-clock`'s shape (a 9-radius circle around a small inner glyph) for visual family consistency with the other status icons in this same bar. At the 15px it actually renders at, the inner square all but disappeared and the icon read as **a plain circle** — indistinguishable at a glance from a bullet, and from the two icons it was trying to match. **Consistency with the wrong reference loses to a universal convention**: stop has exactly one — the solid square from every media player and code-runner's "stop" button — and `i-stop` is now that alone, rendered filled (`icon('stop', true)`) rather than as an outline, since a hollow square reads as an empty checkbox, not "stop" |
| `lib/api.js` | The Dashboard/Setup methods. **Names and return shapes must match what `Dashboard.html` calls** — see the contract section below |
| `lib/rpc.js` | Served at `/_rpc.js`. Proxies `rpc.…` chains to `fetch('/api/…')`, plus the sync status bar |
| `lib/guides.js` | Achievement↔checkbox matching (both directions), both guide backends, guide discovery, `auditGuideTicks`, `syncGuideStatuses`, `mapAchievementGuides` |
| `lib/guidelint.js` | Guide validator + mechanical ticking. **Backend-agnostic on purpose** — takes the `{key, text, checked, parent}` shape both backends produce, so one rule set covers Notion and markdown and the tests need no network. `computeCheckedKeys` decides which boxes should be checked from the database, which is what makes "checked state equals real unlock state" impossible to violate rather than merely checkable |
| `lib/ai.js` | AI provider layer, **shared half**: usage accounting, SSE unpacking, sessions, `checkResult`, the provider registry. Adding a provider means a new file implementing the interface at the top of this file; this file and `guidegen.js` should not change |
| ↳ **what a new vendor has to prove before it ships** | Two measurements, both taken on real guide runs rather than on `ai-check`: **does it actually ground** — count the search events across a full run, because a vendor that answers fluently from memory still writes unverifiable guides, and `canSearch` reports only what it *declares* — and **does the same request succeed twice**, because a per-request failure rate compounds: a guide run is many requests, so even one failure in five kills most runs. Neither shows up in a single `ai-check`, and both are cheap |
| ↳ one vocabulary at the boundary | Providers translate their own stop reasons into one set (`end_turn` / `max_tokens` / `refusal` / `recitation` / `other`), keeping the original in `rawStopReason`. **An unrecognised reason maps to `other` and is judged unusable** — defaulting it to success means a vendor's new terminal state makes failed generations look like successes. Progress events and tool errors are normalised the same way |
| ↳ **the accumulator runs before the reporter**, and that ordering is the whole progress story | A `server_tool_use` block's `input` arrives as streaming JSON and is not assembled until `content_block_stop`, so a reporter running first can only ever say the tool's name — which is why the longest phase of a run used to show one unchanging word (issue #78). `emitProgress` now takes the accumulated blocks and emits the query, and tool names are put through `toolLabel` so no `web_search_20260209` reaches a screen. **Both vendors report the same sentence**, pinned in `ai-guidegen-contract.test.js` |
| `lib/ai-anthropic.js` | Anthropic. **Streaming is mandatory, not a performance choice** — `max_tokens` caps thinking *plus* prose, and a long researched answer hits undici's 5-minute timeout before the token ceiling. Server-side `web_search`/`web_fetch`; the "tool loop" resumes a `pause_turn` by appending the assistant turn verbatim — **never add a "continue" message**. Failure modes, tool-error grading and the endpoint capability matrix: [docs/ai-guide-writing.md](docs/ai-guide-writing.md) |
| ↳ four 200-OK failures, all funnelled through `checkResult()` | `refusal`, `max_tokens` (truncated prose — worse than a failed run), a tool error (`end_turn` with an error object inside the result block), and **control tokens leaking into the prose** (`leakedControlToken`, measured on DeepSeek: the output simply ended mid-line and 10 achievements were never written). **The prose is truncated, not merely dirty, so stripping the markers is the wrong fix.** The detector is deliberately narrow because a false positive burns a paid round — guide prose legitimately contains `<br>`, `<details>`, `<table>` |
| ↳ the two web tools' *success* shapes differ | `web_search` succeeds with an **array**, `web_fetch` with an **object**. Using `Array.isArray` for both meant every **successful** fetch was recorded as an error and killed the round — and because the predicate had been written twice, the progress bar simultaneously rendered every successful fetch as 失败. Both now share `toolResultError()`, and success is recognised **positively** per tool: an unrecognised shape is an error, because a rate-limited search read as "found nothing" is the more expensive direction |
| `lib/ai-deepseek.js` | DeepSeek's **OpenAI-compatible** `/chat/completions`; `canSearch` is false there. `reasoning_content` sits beside `content` in the same delta — miss it and the chain of thought lands in the guide. **The Anthropic-compatible endpoint (`api.deepseek.com/anthropic`) *does* have server-side search**, which is why `provider: 'deepseek'` is a preset that builds an **AnthropicProvider** pointed there. Judging one vendor by one of its endpoints was a real mistake made here |
| ↳ **`--models` is the diagnostic that breaks unwatched** | It is the one command that reveals a stale default model, and the one nobody runs until something is already wrong. A stray `streaming = true;` once left it dead for a whole release cycle: ESM is strict mode, so it threw a `ReferenceError` — and the line sat **after** the `!res.ok` check, so a bad key still reported its 403 correctly while a **working** key got `streaming is not defined`. **The better your credentials, the worse the error.** Found by simply running it against a live key. This is the blind spot the "make uncertainties runtime-answerable" policy leaves open: it is sound about *vendor* facts but assumes the code reaches the vendor |
| ↳ no spend caps, deliberately | Four caps, a price table, an `ai_usage` ledger and an `ai-cost` command were all **removed**. The dollar half cannot be honest: rates change, there is no verified table for DeepSeek, and **how server-side search is billed has never been measured**. A cap computed from an untrustworthy number reads as protection while protecting nothing. What bounds a run is `maxSearches` / `maxFetches` / `maxTokens` / `maxRounds` plus the pre-run confirmation. **If you are tempted to add cost estimation back, first go measure how search is billed** — that measurement is the whole precondition |
| ↳ token counts stay, money goes | `formatUsage` prints requests / input / output / search count, and that is the only number reported. Tokens are what the API returns — a fact, not an estimate, and the one figure that reconciles against a provider bill. **Report what was measured, never what was inferred from an unverified rate** |
| ↳ no cross-provider model default | `ai.model` defaults to **empty** and each provider supplies its own. Model names aren't portable, so any concrete default guarantees that switching provider without editing `model` trips the mismatch guard. Learned by shipping one and immediately hitting it |
| `lib/guidegen.js` | AI guide generation, orchestration half: fetch → research + write → mechanical tick → lint → feed specific errors back and rewrite (max 3 rounds) → land. **Guarantees format and data, never content.** Sharding, the concurrency pool, the three-rung failure ladder, classification, clustering, brief entries for unlocked achievements, the prompt rules and every measurement behind them: [docs/ai-guide-writing.md](docs/ai-guide-writing.md) |
| ↳ **every prompt forks by language, not only the rules** | A generated guide is written in the interface language, resolved once in `planGuide` and carried on the plan like `target`. **The system prompt is the cached prefix and was the only half that forked for a year** — the round-by-round messages (write this shard, this shard failed validation, rewrite these entries, and the classification pass that decides the final section headings) were Chinese regardless, so an English guide was written to English rules and then instructed in Chinese every round; the headings are where that showed ([#121](https://github.com/LethalKebab/steam-achievement-tracker/issues/121)). Each builder takes `lang`, defaulting to `'zh'`, so a forgotten call site falls back to what this project has always spoken rather than to English. `lintGuide` cannot catch a heading in the wrong language: it guarantees format and data, never content. Four rules genuinely differ — the output language, preferring the official English name, dropping the two rules about a game having no Chinese name, and citing whatever source was read rather than defaulting to Bilibili. **The research sources do not**: they were Chinese-*first* rather than Chinese-only, and for a Chinese-developed game the best guide really is on NGA or Bilibili. Rule text cannot be shared across a translation, so what is shared is the shape — `PROMPT_SECTIONS` pairs the two languages' `##` sections in order, and a section added to one language and forgotten in the other is a failing test |

The trigger moved to the window's `show` event, calling `api.maybeSync`. **It must not be `startSync`**, which deliberately bypasses `syncStaleHours` because a button click has already answered that question |
| ↳ self-update | `launcher/updater.js` + a generated PowerShell helper. `updater.js` deliberately **does not import Electron**, which is what makes version compare / manifest generation / sha256 / skip-memory unit-testable. **It must be in `build.files`** — missing it breaks only the packaged build, exactly like `icon.ico`. Full rationale in [docs/self-update.md](docs/self-update.md), mechanics in [launcher/README.md](launcher/README.md). `selfupdate.test.js` also parses the generated PowerShell, since that script runs with no console |
| ↳ the three rules that must not be softened | **Deletion goes by a manifest of what the previous build installed, never a keep-list** — user data sits *inside* the app folder, so a wrong manifest leaves a junk file while a wrong keep-list destroys data, and `dbPath`/`guidesDir` are configurable so a keep-list can never be complete. **A missing manifest ⇒ plain overwrite, never a guess** at which files are program files. **The helper must be confirmed alive before `app.quit()`** — it writes an alive-marker, the app polls, and if nothing reports in it shows an error and **keeps running**, which turns "the program closed itself and never came back" into "the update didn't happen". `detached` does not make a child outlive Electron (job object, kill-on-close); only `cmd /c start` and WMI do, measured |
| ↳ **a build must not eat its own data** | `postbuild.js` renames `win-unpacked` over the previous app directory, and that directory is exactly where a packaged build keeps `config.json` and `data/` — so a locally built exe lost everything on the next `npm run build`. **Invisible to anyone holding a `local.config.json`**, whose data is somewhere else entirely, which is how it survived to be reported by a contributor. Two halves, and neither is sufficient alone: the build **generates** a `local.config.json` pointing at the repo root when `launcher/` has none, so a local build's data never enters `dist/` and the built exe reads the same dataset as `node tracker.js serve`; and the delete is **refused, failing the build**, if `userDataEntries` finds data in there anyway. That fixed list is legitimate only because it decides what *not* to delete — as a deletion keep-list it would be the shape the row above forbids. The generated file also sets `autoUpdate: false`: a build from a working tree offering to install the published release ends with somebody testing code that no longer holds their change |

### The frontend ↔ backend contract

`Dashboard.html` makes calls shaped like `rpc.withSuccessHandler(fn).withFailureHandler(fn).method(args)`, served by `lib/rpc.js`. **Count them, don't trust a number written here** — a count in this file has already drifted twice. Count the chain's entry point (`withSuccessHandler(` appears once per chain), not method names.

**Keep the contract:** a method that returns `{error: '...'}` is a *successful* call (the frontend inspects `result.error` itself); only network/thrown failures reach the failure handler. Adding a Dashboard method means adding it to `lib/api.js` — `rpc.js` proxies any name.

`Setup.html` uses the same `/api/<method>` contract via a plain `fetch`, not `rpc.js`. Its methods are the only ones in `lib/api.js` that mutate `config`/`steam` in place rather than only touching `db` — required because `SteamClient` copies `steamApiKey`/`steamId` into instance fields at construction, so writing `config.json` alone leaves the running process unusable until restart. `NotionClient` is built fresh at each call site, so updating `config.notion` is enough there. **Any future path that accepts credentials at runtime hits the same trap.**

Two methods are **button-only and never on the save path**, because they write outside this machine: `repairNotionGuideDb` appends options to the **user's Notion database**, and `restoreGuideArchive` **deletes the live blocks of a real Notion page** before rewriting them (so it takes a fresh backup first and is confirmed by a second click reading 「整页重写」). `createNotionGuideDb` saves the new database's ID itself rather than handing it back — the database already exists by then, and a user who forgets to press save is left with an orphan database and a tool that says Notion isn't configured.

**Blank secret means "keep", never "clear"** — see the `Setup.html` row. Clearing a secret is deliberately a `config.json` edit.

## Data model (`games` table)

`appid` (PK) / `name` / `name_en` / `achieved` / `total` / `has_achievements` / `rate` / `status` / `sync_locked` / `favorite` / `priority` / `family` / `new_ach_date` / `updated_at` / `last_played` / `stats_checked_at` / `perfect_lost_date` / `ach_added_date` / `cover_url`

The other two tables, since three columns arrived late and none of them is obvious from the first:

- `achievements`: `appid` / `api_name` / `game_name` / `name_cn` / `name_en` / `description` / `description_en` / `hidden` / `icon`
- `guides`: `appid` / `name` / `url` / `kind` / `updated` / `lang` / `gen_prose`

- `status`: `''` (normal), `'Unvetted'` (Steam Profile Features Limited), `'Manual'` (hand-maintained).
- **`Manual` is the 🔒 lock in the UI — same column, different vocabulary.** Do not rename the column to match: `status` values reach CSV export and the user's spreadsheet, so the storage name is a compatibility surface. **`addGame` does not force `Manual`** — a family-shared game *is* the case where Steam returns real progress, so locking it on add would freeze the numbers at that moment.
- `has_achievements = 0` replaces the old `'N/A'` string. `NULL` means "not synced yet".
- **`sync_locked` is what the sync actually checks**, not `status`. Separate columns because "skip the daily achievement sync" and "pin this row's label against Steam re-classifying it Unvetted" are different wishes. The Dashboard moves both together; diverge them by hand when you actually want to.
- `family` is purely informational and never affects sync behavior — "not in `GetOwnedGames`" and "should skip achievement sync" are two *different* facts.
- **`last_played` / `stats_checked_at` are the sampling state for phase 2.** `updated_at` cannot substitute — it moves on any row change, including a ♥ toggle, so it can't answer "when did we last ask Steam". Written by `markStatsChecked()`, never on a `retry`.
- **`perfect_lost_date` / `ach_added_date` are the 🔔 notifications, and this project's *only* deliberate transition detection.** Both are stamped inside `updateGameStats`, the one moment `prev` is still readable. Two guards carry them: `wasPerfect` requires a real numeric baseline (so a row's first sync can't fire it), and `achAdded` matches **only an explicit `0`**, never `NULL` — treating `NULL` as the transition would dump the entire library into the bell on the first full sync. **Read the contrast with "Guide page status" below before touching either.** The cost is accepted: an event observed by a run that fails to write is gone. `notifications.test.js`
- New columns need `ALTER TABLE`, not just an edit to `SCHEMA`. `SCHEMA` is `CREATE TABLE IF NOT EXISTS` and does nothing to an existing table — `migrate()` walks `ADDED_COLUMNS` against `PRAGMA table_info`. **Add to both.**

## Sync behavior

`fullSync` runs three phases over the whole library, no cursor, no runtime cap. Ctrl+C mid-run is safe — each game is committed as it completes.

1. **`syncLibrary`** — new owned games inserted (with a name lookup); existing *owned* rows get their `Unvetted` stamp refreshed, except `'Manual'`. Rows whose appid is **not** in the current `GetOwnedGames` snapshot are left completely untouched — that's the preservation rule, and it keys off ownership, not `status`.
2. **`syncAchievementStats`** — refreshes counts for rows with `sync_locked = 0`. A total higher than last time stamps `new_ach_date`. Which rows get checked is `selectStatsTargets()`, below.
3. **`syncAchievementSchema`** — per-achievement detail for games new to the `achievements` table or bumped in the last 7 days; skips games at exactly 100% and games with no achievement system. One exception outranks the 100% skip: a game whose stored detail predates `description_en` (Chinese descriptions, not one English) is re-fetched once — the description shows in the panel whether or not the game is finished.

**`serve` also runs guide discovery on start** (off via `syncGuidesOnServe: false`). Deliberately **outside** the `syncStaleHours` gate and needs no Steam credentials: a guide page created minutes after a sync must show its link immediately. `fullSync` itself does **not** touch guides — a new Notion page will never be discovered by achievement syncing alone, which is why this hook exists. Failures are logged and swallowed; a dead Notion token must not take the Dashboard down.

**The three startup jobs are sequenced, not concurrent.** Each feeds the next: discovery must finish before the sync knows which guide pages are new, and the tick pass must run after the achievement refresh or it matches against last run's unlock state. Still off the `listen` callback's critical path.

### Phase 2 sampling — `achieved` and `total` do not change for the same reasons

Getting this wrong loses data *silently* — a skipped row doesn't error, it leaves a stale number on the Dashboard forever.

- **`achieved` is a fact about the account.** It cannot change unless you played. Gating on `rtime_last_played` is exactly right for it.
- **`total` is a fact about the game.** A developer patch adds achievements with zero playtime, dropping a 100% game below 100%. **Gating that on `rtime` is simply wrong.**

So `selectStatsTargets()` unions three groups:

1. **played** — `rtime_last_played` exceeds the stored `last_played`. Keeps `achieved` exact.
2. **unowned** — appid absent from the `GetOwnedGames` snapshot (family-shared / delisted / hand-added). No timestamp exists, so they are checked every run — **except the ones already at 100%, which go to sweep instead**: the `rtime` gate exists to protect `achieved`, and a finished game's `achieved` cannot move. The predicate is deliberately **stricter** than `maxAge`'s (`rate === 1` *and* `achieved === total` *and* `total > 0`) because the error directions are not symmetric: a stale `rate` alone would freeze a still-moving `achieved` for three days, while a disagreement merely costs a few requests.
3. **sweep** — rows overdue for a re-check, capped at `sweepBudget`. **This is the only thing that catches a retro-added achievement, so do not remove it as an optimisation.**

Load-bearing details:

- **The sweep sorts by *overdue ratio* (`age / itsOwnDeadline`), not absolute age.** Perfect games expire in 3 days and everything else in 7; sorting by raw age lets an 8-day-old ordinary game jump ahead of a 4-day-old perfect one, making the shorter deadline decorative. `selection.test.js`
- **`markStatsChecked` is never called on a `retry`.** Recording a rate-limited game as "just checked" turns throttling into silent data loss.
- **A row with no baseline (`stats_checked_at IS NULL`) is always checked, uncapped.**
- **No `playSnapshot` ⇒ check everything.** `node tracker.js sync` stays a true full sync; `sync --fast` and the Dashboard auto-sync opt in by passing `selection`. Keep that escape hatch.
- **Thresholds are targets, not guarantees**, and the requirement is **Σ(1/each row's own deadline)**, not a fixed share of the library — measured once at 313 unlocked rows (143 of them perfect, so on the 3-day deadline) it came to ~72 rows/day. **Do not remove the cap**: an uncapped sweep stamps every row with the same `stats_checked_at`, so they fall due together and the load herds into a spike instead of staying spread. **Re-measure rather than quoting any of these numbers.**

### The 「立即同步」 button

A page refresh only re-reads SQLite — `getDashboardData()` never touches Steam. The button calls `startBackgroundSync()`, **the same function the startup auto-sync uses**. Keep it that way: one function means one concurrency guard, and that guard is the only thing stopping a click landing during the startup sync from running two `fullSync`es over the same database. Sharing it is also what gives the button its checkbox ticking for free.

Two deliberate asymmetries with `maybeAutoSync`: the button **ignores `syncStaleHours`** (that gate answers "should we sync unprompted", and a click has already answered it), and it still passes `selection`, so it's the sampled sync, not the full one. `node tracker.js sync` remains the way to force a true full pass.

The button owns no progress UI of its own — `lib/rpc.js`'s 3-second poll drives its label and disabled state through `window.onSyncState`. **That hook fires before every branch in the poll handler**, because two branches return early; hanging it off the end strands the button on 「同步中...」 forever.

**`stats.bumped` must stay visible.** It was computed and thrown away on the Dashboard path for a while — backwards, since a retro-added achievement is precisely the change you cannot notice on your own. That notice deliberately does **not** auto-dismiss.

There is deliberately no destructive rebuild/reset command. A "wipe and repopulate from `GetOwnedGames`" helper would silently drop every family-shared and manually-maintained row — data the API cannot give back.

## Steam API quirks

Verified and hard-won — don't re-derive them, and don't "simplify" the handling:

- `GetPlayerAchievements` HTTP **400** = this game genuinely has no stats for this account. A normal signal, **not** an error, do not retry.
- HTTP **429** = real rate limiting, retry next cycle. Everything else non-200 is also treated as transient.
- HTTP **403** `"Profile is not public"` can come back for *one specific game* even when the profile is public — a per-game privacy toggle. Falls in the retry bucket, but retrying never succeeds until the setting changes.
- `appdetails`'s `name` field **ignores the `l=` param** (Steam bug) — Chinese names require scraping the store page HTML, with age-verification cookies and a deliberately loose regex.
- Determining whether an owned appid is currently Unvetted **requires two `GetOwnedGames` calls** (`skip_unvetted_apps=false` minus `=true`). A single plain call silently returns the vetted-only view.
- `GetOwnedGames` omits free games unless `include_played_free_games=true` (already set).
- A game can disappear from `GetOwnedGames` while `GetPlayerAchievements` keeps returning its full permanent stats. **"Not owned" ≠ "no achievement data."**
- Family Sharing achievements are recorded per **playing** account. A shared game played on someone else's account will correctly and permanently show 0. Not a bug to chase.

## Guide checkbox matching — do not loosen this

Matching an unlocked achievement to a guide checkbox is **exact equality against extracted title candidate segments**. Never substring, never prefix. Three rounds of false positives produced this rule:

1. an achievement name appearing inside an unrelated achievement's *description*;
2. a short achievement name being a strict *prefix* of a harder achievement's name — which mis-ticked the harder one once the short one's box was already checked; and
3. **two achievements in the same game with genuinely identical names.** Exact matching cannot fix this one: the unlocked twin's box gets ticked, leaves the candidate pool, and the same name then matches the *other*, still-unearned box. `findAmbiguousNames()` refuses any name shared by several achievements unless *all* are unlocked, and logs the skip rather than staying silent. Not rare — a 310-game library had 12 collisions across 11 games.

`extractTitleCandidates()` splits checkbox text into candidates (by line, then by colon/dash, plus the `中文名(English Name)` pattern, plus a trailing-punctuation-stripped variant of each) and requires the achievement name to *equal* one. Adding a candidate-extraction rule is fine; weakening the equality check or removing the ambiguity gate is not.

Two rules about *how* to add one:

- **Append, never replace.** The trailing-punctuation rule adds `秘密食材` alongside `秘密食材。` rather than rewriting it — achievements like 「白手起家。」 have punctuation in their real names, so replacing turns working matches into misses. Stripped variants go last so exact ones win first.
- **Normalize the candidate side only, never the `defs` name index.** Stripped keys in the index would collide `X` with `X。`, and the ambiguity gate would then skip *both* — trading "fails to tick" for "ticks the wrong one", backwards from this project's whole bias.

**The gate closes per name, not per achievement** — a colliding Chinese name does not disqualify a unique English one, and most collisions are Steam localization bugs in one language. The equality rule is untouched, and the colliding name itself is still never usable. Pass 1 cannot finalise a skip, since pass 2 may rescue the achievement. `matching.test.js` pins all three failure modes.

**The one way out of case 3 is the description.** `matchAchievements` runs two passes: ambiguous names first, resolvable *only* by the checkbox quoting the achievement's full description when that description is unique in the game; then exact name matching for everything else. **Description-first is deliberate** — it is the more precise signal, so it claims its box before name matching could take it. This is why the writing convention is `**name**` / verbatim official description / your own notes, and why paraphrasing has a real cost. See `.claude/skills/achievement-guide-writing/SKILL.md`.

**Both languages' descriptions are accepted, and uniqueness is counted across both.** A guide may quote `description` or `description_en`; either resolves the box. The uniqueness requirement is unchanged and now spans the pair, which can only ever *refuse* more than the one-language version — so it cannot mis-tick, and it removes any dependence on `guides.lang` being right. That matters because `guides.lang` is a display fact with no correctness role: the rows that predate the column carry an assumed value rather than a recorded one. `paraphrased-description` accepts either for the same reason — a rule that fires on every guide the moment one is mislabelled is a rule nobody reads.

**The design deliberately prefers a missed checkbox over a wrong one.**

**`flatCompare` is the one "is this the same text" predicate, and folding typographic quotes into it is normalization rather than loosening.** Measured before changing anything: on the reported game, 45 of 91 achievements were quoted verbatim, 45 have no description on Steam at all, and exactly 1 mismatched — where only the quote glyphs differed. Across the library that is **14 of 791**; the other **777 are genuine paraphrases in hand-written guides and must stay untouched**, which is why `paraphrased-description` is a warn. Folding `“”„‟＂` → `"` and `‘’‚‛＇` → `'` cannot make two *different* descriptions equal, only two spellings of the same one. **Dashes and the ellipsis are deliberately not folded.** The extraction matters as much as the fold: the predicate existed as three private copies, and only two were the same question — `nameGroupAlreadySatisfied`'s is **deliberately looser and must not be merged**. `matching.test.js` pins that the two write-side callers do not re-inline it, and that the fold stops at quotes.

**Always `checkbox-sync --dry-run` before a manual full run.** Ticking a Notion box can't be undone automatically, and failure mode 3 was caught by a dry run before it wrote anything. Sync only ever ticks, never unticks, so it cannot repair its own mistakes.

### Automatic checkbox ticking (the one unattended write path)

`serve` and the 立即同步 button both run a tick pass after the achievement sync (off via `checkboxSyncOnServe: false`). **This is the only place in the project that writes to Notion without a dry-run in front of it**, so every narrowing below is load-bearing — do not widen one without replacing the safety it provided:

- **`appids` whitelist, not the full candidate set.** Only rows whose counts actually moved this run, plus guide pages registered for the first time this run. **`appids: []` means "run nothing", never "no filter"** — writing `appids?.length ? … : everything` turns the common case (nothing changed) into a full scan and silently undoes the whole design. `checkbox-selection.test.js`
- **`gained` is false when there's no baseline.** On a row's first sync `achieved` goes `NULL → n`; counting that as "gained" would make the entire library a candidate on the run where that's most expensive.
- **Cascade off by default here**, unlike the CLI. The cascade is the one deliberately over-ticking path, and this route has no human gate in front of it.
- **A game that hit 100% *this run* is still visited.** The 100%-skip must stay decoupled from `cascade` — folding them into one expression is a real bug: with cascade off, the achievement that *completes* a game could never be ticked automatically, because by the next run the game is skipped forever.
- **Failures are soft and separate.** Errors go to `syncState.tickError`, never `syncState.error` — a dead Notion token must not present as "achievement sync failed" when the achievement data synced fine.

Review is `sync_log` + `node tracker.js log`. The Dashboard raises a notice naming the first few ticks, and like `bumped` it **does not auto-dismiss**: it is reporting a write to the user's own notes.

### Guide page status (`Done` ⇄ `Staged`)

Kept in step with completion, **both directions** — `syncGuideStatuses`, run by `guide-status` and, on the serve path, right after the tick pass.

- 100% and not `Done` → **`Done`**.
- Below 100% and currently `Done` → **`Staged`**. Effectively always a developer patch adding achievements.

Load-bearing:

- **It converges on state; it does not watch for the transition.** Crossing 100% exists only for the instant `updateGameStats` writes it, so any run that observes it but cannot write loses it permanently. The rules are stated over current state, which is idempotent, self-healing and re-runnable. **Do not "optimise" this into transition detection.** (The 🔔 columns *do* detect transitions, and that is not a contradiction — they answer "what changed recently", which current state genuinely cannot answer, and they pay the matching price. This rule applies where current state *is* sufficient, and there it always wins.) Measured proof: the one page that needed demoting has `new_ach_date = NULL`, so a rule gated on "we saw `total` grow" would never have fired.
- Convergence is nearly free — `queryGuideDatabase` already pages through the whole database and only has to stop throwing `Status` away. ~3 API calls per run total, not per game.
- **The two directions are deliberately asymmetric.** Promotion overwrites *everything* except `Done`. Demotion touches *only* `Done` — a sub-100% page at `Paused`/`In progress`/`Not started` is a state you chose, and rewriting it on every Dashboard open would put you and the tool in a loop. `guide-status.test.js`
- The two rules are mutually exclusive by construction, so a page can never oscillate.
- **A `total` of `NULL` is not "dropped below 100%".** The `total > 0` guard is what stops a Steam hiccup from demoting a finished page.
- **The property's *type* is read, never assumed.** `status` and `select` are different types whose write payloads differ. `fetchGuideStatusSchema` reads name, type and options; **both** values are validated up front, so a database missing one fails readably instead of 400-ing halfway through.
- Notion-kind guides only. Failures are soft (`syncState.statusError`); it returns `applied` so callers report direction without parsing log text.

**Ordering matters:** status runs **after** the tick pass, so a game that just completed gets its last boxes ticked before the page is marked done.

### Nested sub-step checkboxes (`collectSubStepTicks`)

Guides nest sub-steps under an achievement. Two things were true and both wrong: the backends disagreed (markdown always read indented boxes, Notion never descended into one — identical content behaving differently by backend), and sub-steps could never be auto-ticked, because they aren't achievements and match nothing. Notion now recurses and both backends set `parent`; containers like `toggle` pass `parent` through unchanged.

So `collectSubStepTicks` ticks them by **inheritance**: if the parent achievement is known unlocked, its nested boxes get ticked. Evidence of "known unlocked" is only ever (a) a match made this run, or (b) an already-ticked box that `resolveTodoToAchievement` maps to a uniquely-identified, genuinely unlocked achievement. Without (b) the feature would be useless.

**This is the one place in the codebase that prefers over-ticking, and it is deliberately inconsistent with the rule above.** "Parent unlocked ⇒ every listed sub-step was done" holds for *all-of* achievements and **fails for *any-of*** — "reach an ending" with nine endings listed underneath would falsely tick eight, and the code cannot distinguish them. Mitigations, all of which should stay: `--no-cascade`, every cascaded tick logged as 已勾选子步骤(父成就已解锁), and `--dry-run` listing them separately. **If you write a guide whose sub-steps are alternatives rather than requirements, don't nest them under the achievement.**

Two consequences elsewhere. `checkboxSync` will consider a 100%-complete game when cascade is on — **but only if that game has rows in `achievements`**, because recognising a parent needs `resolveTodoToAchievement`, which needs names/descriptions, and `syncAchievementSchema` deliberately skips games at 100%. Widening the filter unconditionally cost dozens of wasted page reads plus Steam calls per run and could never tick anything. Second, `auditGuideTicks` ignores ticked sub-step boxes that resolve to no achievement — counting them as "undetermined" would drown the one number that measures real audit coverage.

## Reverse lookup (the `audit` command)

`checkbox-sync` asks "where does this achievement go?"; `audit` asks the opposite — "which achievement is this ticked box about, and is it actually unlocked?" That's `resolveTodoToAchievement()`, which accepts only two unambiguous handles: the achievement's full description when unique in the game, or a name mapping to exactly one achievement. Anything else is reported as undetermined rather than guessed, and **the undetermined count is always printed** — "0 wrong" would otherwise imply coverage the audit doesn't have.

**Never map by description *prefix*.** A first draft matched the first 14 characters, which collapses tiered families ("deal 100/500/1000 damage"): a correctly-ticked easy tier gets attributed to its locked harder sibling. On real data that produced 4 false findings out of 5 — the same bug class as the name-prefix one, in a different disguise. `matching.test.js` pins the tiered-family case.

**Requiring the *complete* description does not by itself escape that family.** The easier tier's whole description is routinely a substring of the harder one's (「建造出内燃机车。」 inside 「在游戏90分钟内建造出内燃机车。」), so one box legitimately contains both and the stage has to choose. **The longest contained description wins**, a proper substring of it being strictly weaker evidence about the same sentence; equal lengths from two achievements is a real tie and resolves to nothing. Taking the first `defs` happened to list is what filed 61 of Factorio's 88 boxes under the wrong achievement — and since `mapAchievementGuides` gives an achievement to the first box that claims it, one wrong answer also swallows every later box that should have had it.

**A description holding no characters is not evidence, and Steam ships those.** Factorio's 咸鱼翻身 stores a single space: truthy, so a `!raw` guard admits it, and empty after `flatCompare`, so every checkbox on earth "contains" it. `isQuotableText` is the predicate for "is there anything here to quote", and both this lookup and `guidelint`'s two quote rules go through it rather than testing the raw string. `syncAchievementSchema` also stores a whitespace-only description as `''`, so rows synced from now on cannot carry one — but rows already in the database can, which is why the predicate rather than the ingest is the load-bearing half.

## Don't cry wolf in the log

When the sync can't act, think about whether that's *actionable* before logging it. Ambiguous-name groups whose boxes are already correctly ticked must not log "needs manual review" — on every run that is a permanent false alarm, which is worse than no alarm because it trains you to ignore the log. `nameGroupAlreadySatisfied()` silences those, and they speak up again if a second same-named achievement gets unlocked without its box ticked.

That helper uses loose substring matching, which is banned in the tick path. The distinction is intentional and commented at the call site: **it decides whether to print a line, never whether to write.** Getting it wrong costs one log line; getting the tick path wrong corrupts the user's notes. Keep new heuristics on the correct side of that line.

## Known pitfalls

- **The 🎮 recently-played badge can never appear on a family-shared / delisted row.** It derives from `last_played`, which comes from `GetOwnedGames`; those rows have no timestamp and Steam offers no other source. Looks like a bug, isn't one.
- **Games with `has_achievements = 0` are retried**, not permanently excluded. `GetOwnedGames`'s `has_community_visible_stats` flag predicts this set exactly and skipping them would save a few dozen calls per full pass — **considered and deliberately rejected, don't re-propose it.** The moment a game adds achievements is the moment that flag flips, and by then we'd have stopped asking.
- **`sync_locked = 1` rows are never touched by any sync phase.** If a row "won't update," check that first.
- **Notion page identity must use the normalized UUID**, never raw URL text — Notion sometimes prefixes URLs with a title slug, so the same page's URL differs between queries. Comparing raw URLs once caused already-linked pages to be treated as new and overwrite curated names.
- **One appid, one guide backend.** Markdown discovery won't overwrite a registered Notion guide unless `--force`.
- **`syncGuidesFromMarkdown`'s `added` includes re-registrations.** It re-upserts every local `.md` each run, with `action: 'appended' | 'updated'` telling them apart; `syncGuides` filters to `'appended'` before feeding the tick pass — without that filter the targeted tick degrades into a full local scan every start.
- **Local guide paths are contained to `guidesDir`.** Keep that check — `guides.url` is data, and `guidepatch.landPatchLocal` **writes** to what it returns, so a hole there is a write primitive, not just a read one.
- **Guide text never goes in the database** — only a pointer. Guides must stay human-editable and tickable where they live; the `guides` table tracks *where*, never *what*.
- **`localDate()` not `toISOString().slice(0,10)`** for user-facing dates — the latter is UTC and will be off by a day in the evening.
- **An author `display:` silently defeats the `hidden` attribute.** `[hidden] { display: none }` comes from the *user-agent* stylesheet, so any author rule outranks it — JS keeps setting `.hidden = true`, the element keeps showing, nothing errors. Both pages carry a global `[hidden] { display: none !important }`. Patching per element is whack-a-mole.
- **Native dialogs are unusable in this app — in *either* process.** They appear and vanish before they can be clicked in the packaged build, and `dialog.showMessageBox` from the main process returns instantly with `response: 420`, outside the button range. **The boundary is native-vs-page, not renderer-vs-main.** Use `askConfirm(...)`, which returns a **Promise** — a forgotten `await` makes `if (!askConfirm(...)) return` never return, silently green-lighting the dangerous action. Pinned in `guidegen.test.js`.
- **Documentation drifting from code is a real failure mode here.** A secret once sat hardcoded in this public repo for months while three separate docs claimed it was read from config. **Verify against code, not docs.**

### Source assertions: five ways they pass while proving nothing

Every one of these was paid for.

- **Strip comments before any source assertion — including `//`, not just `/* */`.** This codebase's comment density is its own hazard: an assertion that greps for a symbol gets satisfied by the *comment explaining that symbol* beside the code, so deleting the code changes nothing and the check passes forever. **Write the assertion, then break the thing it guards and watch it go red.** A source assertion that has never been seen failing is not evidence of anything.
- **Strip line comments *before* block comments, not after.** A `//` line here can legitimately contain `/api/` followed by a star, and the block-comment regex reads that as an opening delimiter, then deletes everything up to the next closing one — **including real code**. Measured: a strip silently ate the line under test, and mutating `appendChild` to `innerHTML +=` left the test green.
- **Slice to the block you mean — never `indexOf(anchor)` plus a byte count.** A fixed window drifts as the code between the markers grows, and the dangerous direction is the quiet one: a window that still contains both markers while the code between them has changed. Slice between two real anchors and assert both exist.
- **An assertion is evidence only about what it counts, and "lossless" is the word that hides this.** `regroupByAssignment` had two fault-injected assertions — the achievement-id multiset and the multiset of non-heading lines — and a real run still tore a `<details>` into an empty shell plus loose siblings. **Not one character was lost; the structure was**, and both passed. Text, order, nesting and identity are four different invariants; after a green fault injection, name what the checker actually counts and ask what else the transformation can destroy.
- **A downstream step that re-derives the same result masks a broken upstream one, and everything stays green.** Replacing `joinBodies(liveBodies())` with a bare concatenation broke nothing in the whole suite, because the classification pass runs afterwards and re-buckets by heading. It is only observable on the **degraded** path. When a change looks untested, check whether something downstream is covering for it before concluding the code is dead.
- **The fault injection needs its own verification, or its green means nothing.** Two ways this went wrong in one session: the confirmation predicate was **not unique**, so a `sed` matched nothing while the guard still passed and two "still green" runs were misread as "the assertion is too weak"; and a test case was **blocked by a different guard** than the one under test, so disabling the code under test changed nothing. **Treat an unexpectedly-green injection as a finding to chase, never as a result to report.**
- **Defence in depth defeats single-mutation testing, and that is not a reason to remove a layer.** `safeGuidePath` and `containedPath` each hold overlapping checks; deleting any *one* leaves the rest blocking every hostile input, so the mutation comes back green. The honest mutation is replacing the whole function with the version that shipped the bug — do that instead of thinning the checks to make them individually observable.

### UI state that only breaks on a slow day

**UI state hanging on a single un-retried async call whose failure is swallowed will eventually be wrong on screen.** Both known cases were invisible in development, where the server is always warm and always up: a flag whose repaint depended on one request beating another, and a page load with no `catch` against a server that wasn't listening yet. **Ask what the screen looks like when that call is slow, and when it throws.** Prefer re-rendering from state already in memory over re-fetching to flip a flag.

**When a value has two renderers and only one repaint path, assume they have drifted and go measure.** The rewrite dialog's 「已选 N 条」 sat stale for three rounds because `paintCount` only ran inside the full repaint, which single-entry ticking deliberately skips; nobody saw it because the sentence above it was correct. It surfaced only from comparing the displayed count against `querySelectorAll('input:checked').length` — checking the UI against the DOM rather than reading the UI. Details in [docs/frontend.md](docs/frontend.md).

## Current state and open items

The core pipeline (library sync, achievement counts, achievement detail, Dashboard, ♥/★ flags) is done and in daily use. Guide sync works against both backends, ticking happens automatically on Dashboard open and on 立即同步, and the same chain keeps each guide page's `Status` in step.

**Re-measure, don't quote.** Corpus figures — how many guides, how many collisions, how many ticked boxes — go stale silently, and every one ever written into this file did. Run `audit`, `guide-lint` or a SELECT when you need a number.

Four readings that have been got wrong and will be again:

- **`checkbox-sync --dry-run` proposing 0 ticks is not evidence that Notion and Steam agree.** A dry run only proposes ticks for achievements it can *match*; a guide whose boxes match nothing produces the same silent 0. `guide-lint` measures that gap; `audit` doesn't catch it either, since it only inspects boxes already ticked. **Read 0 as "nothing actionable found".**
- **A clean recorded baseline is not evidence the sync is running.** A machine with no Notion token errors nothing — `checkbox-sync` simply never runs. Check `sync_log` has recent rows.
- **A description cannot make an achievement stop being ambiguous.** The gate reads names only.
- **The gate closes per *name*, not per achievement.** Don't confuse "stop discarding a unique name" with "loosen matching".

`config.json` is per-machine and gitignored; the guide database ID lives there and stays out of this repo. `saveConfig` requests mode `600`, which Windows does not honour.

Known outstanding items:

- **Guides not yet written** — some pages exist in the guide database with no `appid:` line, so discovery skips them every run (expected). If they are also *empty*, `guide-gen` adopts and fills them.
- **Leftover spreadsheet automation** — a few daily jobs still update an old Google Sheet. To retire them, delete the triggers in that Apps Script project; run `node tracker.js export` first.
- **The Notion landing path has run live, and reading the page afterwards is still the step that finds things.** The fake-client tests pin the refusals and the read-back but cannot say whether Notion renders our blocks the way we think — and twice it did not (a blank line inside 28 of 50 checkboxes; four literal `<details>` paragraphs). Both were reported by the owner from the rendered page; no test and no read-back verdict caught either. **Read the page after a landing.**
- **`--only` has never completed a verified live run.** Its first attempt failed and was fixed; nothing has gone end to end since. Run it on a **local** guide first, with `--dry-run` before anything that spends.

### The AI guide commands

- `ai-check [appid]` exercises the whole provider chain against the real API and prints stop reason, server-tool calls, continuations and usage. `--dry` assembles the request and prints it **without sending and without needing a key**.
- `guide-gen <appid>` runs the pipeline; `--dry-run` prints the assembled prompt and the landing plan without sending anything. Confirms before spending unless `--yes`; takes `--effort low|medium|high`. **Every refusal reason is raised up front in `planGuide()`** — never halfway through, after you have paid.
- **`--overwrite` regenerates over an existing guide.** Without it a registered appid is refused, and the refusal says what to type instead. Three rules are load-bearing: the backup is a *precondition* (it fails ⇒ nothing is written); `landToNotion` deletes exactly the blocks the backup returned rather than re-reading the page; and **overwrite writes back to the guide's own backend** — changing backend is `guide-to-notion`'s job. **What it costs the user:** achievement checkboxes are reconstructed exactly from the database, but **sub-step boxes are not**, so a hand-ticked box comes back unticked. That is the only irreversible loss, which is why it is computed from the *old* guide alone and shown before the spend. **The GUI gate is not allowed to be looser than the CLI's** — `previewGuideRewrite` runs the same preflight but returns **numbers, not a formatted sentence**.
- **`--only` rewrites part of a guide instead of all of it** (`--only <selector> [--note "…"]`). It exists because a full rewrite discards every hand-edited passage and every hand-ticked sub-step box, and re-rolls the dice on the parts that were already right. Selectors are computed, not parsed by a model: `rare[:pct]`, `locked`, `section:<heading>` (local only), or a name/`api_name` list. **That set is exactly what the Dashboard dialog offers**, on the rule that a selector which cannot be drawn as a button is telling you something about the selector.
- `guide-lint [appid]` runs the linter over real guides (read-only). Steam unlock state is **opt-in** via `--checked`: "unlocked but unticked" is `checkbox-sync`'s job, so reporting it by default would bury the content problems.

## Working on this efficiently

1. **Bulk repetitive external calls are disproportionately expensive.** Notion has no batch-update API, so "add one line to forty pages" is forty round trips — each carrying the whole conversation history. Before starting that kind of job, say roughly how many calls it will take and offer to do it in a fresh session.
2. **Rule of thumb for a fresh session:** if the content to read/write clearly exceeds what's already in context, or the task is purely repetitive and needs no history, suggest starting clean. Small one-off edits are fine inline.
3. **Verification beats assumption.** A successful tool call does not mean the content is right. Re-read results after bulk writes or overwrites, and prefer a read-only preview (`--dry-run`, a SELECT) before anything that writes outside this repo.
