# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Steam achievement auto-tracker, running **entirely locally**: SQLite data store + Node CLI + a local HTTP server for the HTML Dashboard. Tracks achievement completion across the user's whole Steam library.

User-facing docs live in `docs/`. **`README.md` addresses one reader: someone running the packaged Windows app.** Install, first run, tray behaviour, updating, what each feature does from the UI, and "What runs when" — the trigger/cadence table, since knowing what the tool does on its own is part of using it day to day. **Nothing in it names a command, a runtime or a source file**, because that reader has no terminal; the one exception is a single link to `docs/cli.md`. Running from source and the full command reference live there, and it is also where `CLAUDE.md` and `launcher/README.md` are linked from. Reference material (every config option, the data model, how matching works) goes in `docs/`. Task-scoped guides for specific jobs are in `.claude/skills/`.

## Stack constraints

- **The runtime still has zero npm dependencies** — `dependencies: {}`, no root `node_modules`, Node built-ins only: `node:sqlite` for storage, global `fetch` for HTTP, `node:http` for the server, `node:test` for tests. **"No install step" is still true and still worth keeping**, because it is what makes `git clone && node tracker.js` work and what keeps the packaged build's `extraResources` an allow-list of plain files.
- **npm is allowed as a build-time tool; the runtime stays dependency-free.** The font under `assets/fonts/` came from `npm install @fontsource-variable/noto-sans-sc`, and then **the files were committed and the package thrown away** — npm was the delivery mechanism, not a dependency. Prefer that shape: fetch with npm, vendor the artefact, keep the runtime clean. A real runtime dependency is now *allowed* but still needs an argument.
- **"Offline-only" was never true and should not be quoted as a constraint.** The Dashboard loads 167 capsule images per page from `cdn.akamai.steamstatic.com`, and has for as long as the gallery has existed. What is genuinely local is the *data* (SQLite, no telemetry, server bound to 127.0.0.1). Say that instead.
- Requires **Node 24+** (`node:sqlite` availability).
- ES modules (`"type": "module"`).

## Development workflow

```bash
node tracker.js <command>                # everything is a subcommand; see tracker.js header or `node tracker.js help`
node --test --test-reporter=dot          # test suite — 1001 tests (the dot count wraps to terminal width; don't pin it)
node --check lib/foo.js                  # syntax check (silent on success)
```

**Run the tests with `--test-reporter=dot`.** The default `spec` reporter prints a line per
test — ~600 lines of green ticks to say what `dot` says in six, and the one line that matters
gets buried in them. On a failure `dot` still prints the whole `Failed tests:` block: test
name, message, stack, and the actual/expected diff. Nothing diagnostic is lost.

**What it does not print is a summary line.** There is no `tests 541 / pass 541 / fail 0`
tail — `dot` emits the dots and stops, so **the green signal is the exit code plus the absence
of an `X`**, not a sentence. Two consequences. Do not pipe it through `tail` and then report
"all tests pass" because nothing looked wrong: `| tail -4` on a red run shows dots and hides
the failure block that was printed above them. And when a count is what you actually want —
"did the suite grow?" — use the default reporter for that run rather than counting dots.

Commit messages are Chinese or English, whichever suits the change. This is settled — don't raise it.

There is no build, no push, no deploy. Editing a file and re-running the command is the whole loop. `serve` does not hot-reload — restart it after changing `lib/` (`Dashboard.html` and `lib/rpc.js` are re-read per request, so a browser refresh picks those up).

| File | Role |
|---|---|

| ↳ `ai.providers` — one block per vendor, because three fields were never really one | `apiKey` / `model` / `baseUrl` each had a single slot while there are three vendors. **The test for what belongs in a per-vendor block is measurable, not a matter of taste: is the field read by more than one provider, and is the correct value different for each?** Only those three pass it. The budgets (`maxTokens`, `effort`, `chunkSize`, `maxSearches`, …) are correct at the same value everywhere; the single-vendor knobs (`geminiTools`, `webFetch`, `searchTool`, `anthropicExtras`, `thinking`, `fallbacks`) are read by exactly one provider, so a leftover value is **ignored, not misapplied** — both stay flat. Resolution is one function, `resolveAiKey` / `switchAiProvider`: env var (looked up **by the vendor being asked for**) → `providers[vendor]` → the legacy flat field, and that last step **only when the asked-for vendor is the one `ai.provider` names**. Refusing to fall back is the whole point: sending one vendor's key to another's endpoint produces a 401 that reads 「检查 ANTHROPIC_API_KEY」 about a variable that is already correct. `model` being per-vendor is the same argument one step over: sharing one slot forced it to be *wiped* on every switch (a `claude-*` name sent to Gemini trips `assertModelMatchesProvider`), which silently discarded a pinned version — storing it per vendor removes both problems at once. The settings page had **already derived half of this rule** on its own (`api.js`'s `effective` refuses to reuse the previous vendor's key) and could only act on it by making you re-paste; the knowledge existed, the storage didn't — same shape as the `fixable` flag nothing read |
| `lib/db.js` | SQLite schema + all table accessors. `openDb()` is idempotent (safe `CREATE TABLE IF NOT EXISTS`) |
| `lib/steam.js` | `SteamClient`: owned games (+Unvetted diff), player achievements, schema, name lookup, store search. Every request carries `AbortSignal.timeout` — without one the ceiling is undici's default of **five minutes per call**, and a full sync makes hundreds, so one hung Steam response shows up as the Dashboard sitting on 「同步中」 and never erroring. Also `fetchGameIcon` — a plain Steam query, so it lives here rather than in the AI module both landings would otherwise have to import |
| ↳ two services behind one client, so **two** delay knobs | `requestDelayMs` (100 ms) paces `api.steampowered.com`; `storeRequestDelayMs` (300 ms) paces `store.steampowered.com`. They were one value, and the merge was hiding a real asymmetry. **The Web API side is measured**: `GetPlayerAchievements` took **400 back-to-back requests at 0 ms delay, ~11/s sustained for 36.6 s, with zero 429** — plus a descending ladder (300/200/150/100/60/30/0 ms, 30 requests each) that was also completely clean. So the old 300 ms was pacing the whole sync at 2/s against a service that tolerates 11/s, and it is now 100 ms with a 2× margin. **The store side is deliberately *not* measured, and that is the point of splitting them**: hammering store HTML to find its ceiling is the behaviour that earns an **IP-level** block rather than a key-level throttle, so the risk/return on that experiment is upside-down. It stays at 300 ms, it is only reached by name lookup / cover art / search, and it is a small share of any sync. **The dangerous edit is not a wrong number, it is putting `this.delay` back on a store call**: nothing errors, the sync still works, and the consequence surfaces only once something is blocked — `steam-delay.test.js` pins each site by finding the *next* `sleep(` after each store call rather than a fixed byte window, and all five directions are mutation-tested. Two readings from that run are worth keeping. The ladder's latency column *fell* as the delay fell (121 ms → 44 ms), which is **warm-up and connection reuse, not a real effect** — 300 ms ran first and 0 ms last, so that column is confounded by order and should not be quoted as "smaller delays are faster per request". And the run's only two non-200s were **403s that reproduce on the same two appids every time** (651490 昨日难留, 242760 The Forest), which is the documented per-game privacy toggle under "Steam API quirks" showing up live — not a soft throttle. **What is still unmeasured:** the 100k/day account cap (a 130-row sync twice a day is ~260, nowhere near it), whether repeated bursts accumulate across hours, and every endpoint other than `GetPlayerAchievements`. Re-measure before leaning on any of this; Steam publishes none of these numbers and can change them |
| ↳ the icon has two sources | The square icon's hash comes **only from `GetOwnedGames`**, which silently omits family-shared and delisted games — the same quirk documented under "Steam API quirks". So that whole class of game got no icon, with nothing erroring: the helper returned `null`, the page was created fine, and only opening Notion revealed it (hit for real on 中国式家长, 736190). It now falls back to `…/steam/apps/<appid>/header.jpg`, which needs **only the appid** and no account state. The fallback is **HEAD-checked before being returned** — the first URL is built from data Steam gave us, the second is one we guessed, and a guessed-wrong icon renders as a broken image, which is worse than none |
| `lib/sync.js` | `syncLibrary` → `syncAchievementStats` → `syncAchievementSchema`, `fullSync`, `computeAgcrStats` |
| `lib/server.js` | HTTP server (127.0.0.1 only), `/api/*` dispatch, background sync state + staleness check, guide discovery on start, auto checkbox tick after each sync |
| ↳ **binding to 127.0.0.1 is not a security boundary** | Any web page the user visits can `POST` to `http://127.0.0.1:8777/` — `Content-Type: text/plain` is a CORS "simple request", so there is no preflight to block it. The attacker cannot *read* the reply, but every side effect lands, and the side effects here are deleting games, overwriting `config.json`, starting a run that spends money, and `/restore`, which replaces the whole database (no `?dry=1` ⇒ it applies immediately; the confirmation is client-side only). So every request passes `isLocalCaller`. **Two headers, each covering what the other cannot.** `Origin` blocks cross-site forms and fetches — browsers always send it cross-origin and the page cannot forge it; a *missing* `Origin` is allowed through because that is the launcher / CLI / tests, while the literal string `null` (sandboxed iframe, `file://`) is refused, since that is "has an origin it cannot state". `Host` blocks **DNS rebinding**, where the attacker points their own domain at 127.0.0.1 so the browser considers it same-origin — that case defeats the `Origin` check *and* lets them read responses, but the `Host` header is then their domain rather than a loopback name. That is why the `Host` check applies to `GET` too |
| ↳ the async request handler needs an outer `catch`, and it is not optional | `createServer(async …)` means one throw is an unhandled rejection, which Node ≥15 answers by **killing the process** — so a single malformed request is not "one 500", it is "the backend is gone", rendered in the packaged app as 「后台服务意外退出(代码 1)」. The known instance: `decodeURIComponent('%')` throws `URIError`, so `<img src="http://127.0.0.1:8777/fonts/%">` on any page took the server down. `safeDecode` plugs that one; the outer `.catch` on `handle()` is what makes it not happen again for the next unforeseen input |
| ↳ a body limit that only rejects does not limit anything | `readBody` checks the cap **before** appending and then calls `req.destroy()`. Rejecting the promise ends the *handler*, not the *stream* — the `data` listener stays attached and the string keeps growing. Measured: a 1 MB cap fed an 80 MB body ended with 80 MB in memory. Same shape in `readBinaryBody`, whose cap is 200 MB |
| ↳ **a dedup gate checked before an `await` is not a gate** | `startGuideGen` used to run `isPending(appid)` and then `await` the preflight (two live Steam calls) and `createProvider` before anything recorded the appid. Two clicks both saw an empty state and both went through — the same guide generated twice, paid for twice. Reproduced with 200 ms of Steam latency: one `started: true`, one `queued: position 1`. The fix is `claim(appid)`, which **tests and records in one synchronous step**, released in a `finally` once the queue or `begin()` has taken over. `startBackgroundSync` never had the bug because its check and its `begin()` are adjacent synchronous lines — that is the shape to copy |
| `lib/api.js` | The Dashboard/Setup methods. **Names and return shapes must match what `Dashboard.html` calls** — see the contract section below for the count and how to re-derive it rather than trusting a number written here. One method (`maybeSync`) is called by neither page but by `launcher/main.js`; see the tray row under `launcher/` |
| `lib/rpc.js` | Served at `/_rpc.js`. Proxies `rpc.…` chains to `fetch('/api/…')`, plus the sync status bar |
| `lib/guides.js` | Achievement↔checkbox matching (both directions), both guide backends, guide discovery, `auditGuideTicks`, `syncGuideStatuses`, `mapAchievementGuides` |
| `lib/guidelint.js` | Guide validator + mechanical ticking. **Backend-agnostic on purpose** — takes the `{key, text, checked, parent}` shape both backends already produce, so one rule set covers Notion and markdown and the tests need no network. Reuses `guides.js`'s predicates rather than reimplementing them, so "the linter says `audit` can resolve this box" is backed by calling what `audit` actually calls. `computeCheckedKeys` is the mechanical-tick half: it decides which boxes should be checked from the database, which is what makes "checked state equals real unlock state" impossible to violate instead of merely checkable |
| `lib/ai.js` | AI provider layer, **shared half**: usage accounting, SSE unpacking, sessions, `checkResult`, the provider registry. Adding a third provider means a new file implementing the interface documented at the top — this file and `guidegen.js` should not change |
| ↳ one vocabulary | Providers translate their own stop reasons into one set at the boundary (`end_turn` / `max_tokens` / `refusal` / `recitation` / `other`), keeping the original in `rawStopReason`. **An unrecognised reason maps to `other` and is judged unusable** — defaulting it to success means that when a vendor adds a new terminal state, failed generations start looking like successes. Progress events are normalised the same way (`text`/`tool`/`tool-result`/`search`), and so are tool errors (`tool: 'search' | 'fetch'`), so display code never learns a vendor's wire format |
| ↳ the progress vocabulary is **half** normalised, and the half that isn't shows on screen | Measured by `ai-guidegen-contract.test.js`, which is the first thing to run both providers through the same code path and compare. **`search` is a Gemini-only event.** Its `groundingMetadata.webSearchQueries` repeats in every chunk, so the query is readable mid-stream and `emitProgress` reports 「搜索「怎么拿到 X」」. On Anthropic the query lives in the `server_tool_use` block's **streaming JSON input**, which has not arrived at `content_block_start` — so that provider can only emit `{type:'tool', name:'web_search'}`, and `guidegen` renders `ev.name` verbatim. **The result is that the raw English wire-format tool name is what the progress bar shows on Claude and DeepSeek**, while the same bar on Gemini shows Chinese plus the actual query — i.e. the run that takes 2–11 minutes is the one that cannot say what it is searching for. Nothing errors, and the **end-of-run** `searchQueries` report is identical on all three, so no summary reveals the difference. The fix is to buffer the block and emit a `search` event at `content_block_stop`; it has not been made, and the test pins **current** behaviour with that stated, so flipping it is a deliberate edit rather than a surprise |
| `lib/ai-anthropic.js` | Anthropic. **Streaming is mandatory, not a performance choice** — `max_tokens` caps thinking *plus* prose, and a long researched answer hits undici's 5-minute HTTP timeout before the token ceiling |
| ↳ the "tool loop" | **Not client-side tool execution** — `web_search`/`web_fetch` run on Anthropic's side. The loop exists because the server's sampling loop has an iteration cap; hitting it returns `stop_reason: 'pause_turn'`, and you resume by appending the assistant turn verbatim. **Never add a "continue" message** — the server resumes off the trailing `server_tool_use` block and an extra user turn interrupts it. Earlier rounds' content must be concatenated back into the result or the research is silently lost |
| ↳ a **fourth** 200-OK failure: the provider writes its own control tokens into the prose | Measured on KINGDOM HEARTS via DeepSeek: achievement 173 came back as `- [ ] **The Warrior: Ventus</｜｜DSML｜｜parameter>` followed by `</｜｜DSML｜｜invoke>` / `</｜｜DSML｜｜tool_calls>`, and the output simply ended there — the remaining 10 achievements were never written, on all three rounds. **Stop reason normal, prose non-empty, no tool error**, so every existing branch waved it through and those three lines landed in the user's draft; only an unrelated `missing-checkbox` count kept it out of Notion. `leakedControlToken()` now gates it and `checkResult` returns `control-token`. **The prose is *truncated*, not merely dirty, so stripping the markers is the wrong fix** — that yields a guide which looks complete and is short a section, and this project's whole bias is that a reported failure beats a silent omission. It joins `empty` in `RETRYABLE` (same nature: the sampler went off the rails this once, so asking again usually works) and in `SPLITTABLE` / `CHUNK_LOCAL`, so it costs one re-ask rather than the run. **The detector is deliberately narrow because a false positive burns a paid round:** guide prose legitimately contains `<br>`, `<details>`, `<summary>`, `<table>` and `<span underline="true">`, so it matches only shapes that cannot collide with those — a fullwidth `｜` (U+FF5C) *inside* angle brackets (DeepSeek's family), `<\|…\|>` (Llama/OpenAI's), and the closing forms `</invoke>` / `</tool_calls>` / `</parameter>`. Opening tags like `<function_calls …>` are deliberately **not** matched: they resemble real HTML too closely, and missing a novel variant merely re-surfaces as missing checkboxes, which is the cheaper direction |
| ↳ three 200-OK failures | `refusal`, `max_tokens` (truncated prose — worse than a failed run), and a tool error (`end_turn`, with an error object inside the result block) all look like success. All three are funnelled through `checkResult()` so no caller has to remember the branches |
| ↳ the two web tools' *success* shapes differ | `web_search` succeeds with an **array**; `web_fetch` succeeds with an **object** (`{type:'web_fetch_result'}`). `Array.isArray` was used as the success test for both — that rule holds only for search — so every **successful** fetch was recorded as an error whose code was the success block's own type, `web_fetch_result`, and `checkResult` killed the round on it. `web_fetch` only defaults on at the official endpoint (`ai.webFetch ?? !ai.baseUrl`) and every live run to date had gone through DeepSeek's compat endpoint where it defaults off, so this shipped and first fired on a user's own Anthropic key: on that path *a successful page fetch was a failed generation*. The two call sites (validation and progress events) had each written the predicate separately, so the same bug had two copies — the progress bar was simultaneously rendering every successful fetch as `失败(unknown)`. Both now share `toolResultError()`, and success is recognised **positively** per tool: an unrecognised shape is reported as an error rather than waved through, because a rate-limited search read as "found nothing" is the more expensive direction |
| ↳ tool errors are graded, not pooled | **Search failure kills the round** — search is the entry point, so without it the model writes from memory, which is the silent quality gap `canSearch` exists to prevent. **Fetch failure is reported and waved through** — `web_fetch` is per-URL, and both `url_not_allowed` (it can only fetch URLs already present in the conversation, so any URL the model constructs itself trips this) and `url_not_accessible` (404 / anti-bot / timeout, routine on Chinese guide sites) appear a few times in any normal research session. Ten pages searched with two fetches failed is enough material; voiding the round there spends the minutes and tokens the user already paid in order to punish the normal case. Not silent though: `checkResult` returns them in `warnings`, `guidegen` emits them as progress events, `ai-check` lists each one and marks it as not affecting the round. An unrecognised `tool` value grades as blocking |
| `lib/ai-gemini.js` | Gemini — added because it has a **free tier**, which is what let the pipeline run at all (Anthropic is pay-as-you-go and this machine has no key). Replaced OpenAI as the second provider; OpenAI has no usable free allowance either, so it solved nothing |
| ↳ **`--models` was dead for a whole release cycle, and the reason it went unnoticed is the row below** | `listModels` carried a stray `streaming = true;` — one line that fell out of `#once` during `694be36` ("Windows 上退出时的 libuv 断言"), wrong indentation and all. ESM is strict mode, so assigning to an undeclared variable is a `ReferenceError`, and the line sits **after** the `!res.ok` check. That placement is the whole story: a bad key still reported its 403 correctly, while a **working** key got `streaming is not defined`. **The better your credentials, the worse the error** — and the real answer, which had already come back over the wire, was thrown away and replaced with nonsense. Found by simply running the command against a live key; fixed, and `listModels` now has the four tests it never had (returns the parsed list, filters to `generateContent`, key stays in the header, and a non-200 raises something actionable rather than a `ReferenceError`). **This is the exact blind spot the next row's policy leaves open.** That policy — "anything a wrong guess would make error loudly is deliberately untested, the first real call is the better check" — is sound about *vendor* facts, but it silently assumes the code reaches the vendor. Here it never did. And the casualty was the one command the row below calls the thing that revealed the default model was stale: a diagnostic breaks exactly when nobody is looking at it |
| ↳ written without docs | Field, model and tool names came from memory — the web tools were down. So every uncertainty was made **runtime-answerable** instead: the model name is config plus `ai-check --models` (asks the API); tool declarations are config (`ai.geminiTools`); the thinking budget is simply not sent unless configured. **Whether search actually happened is read off the response** (`groundingMetadata.webSearchQueries`), not off a pricing page — which is how "does the free tier include grounding" answers itself on the first real run |
| ↳ `RECITATION` | A failure mode Anthropic has no equivalent of: blocked for reproducing copyrighted text. **Guide writing is its high-risk case** — we explicitly demand verbatim official descriptions and wiki reading. It gets its own `stopReason` and its message says outright that quoting descriptions verbatim must *not* be relaxed to dodge it; that rule is the matching system's foundation |
| ↳ thought parts | Gemini puts reasoning and prose in the same `parts` array, separated only by `thought: true`. Miss that flag and the model's reasoning gets written into the user's guide file |
| ↳ `provider: 'deepseek'` is a preset | It builds an **AnthropicProvider** pointed at the compatible endpoint, not `ai-deepseek.js` — because that's the endpoint with search. Before the preset, the good path had to be written as `provider: "anthropic"` plus a DeepSeek URL (which reads like a misconfiguration) while the obvious spelling gave the search-less one. **The good path must not sit behind counter-intuitive config.** The OpenAI-compatible one is still reachable as `deepseek-openai` |
| ↳ no spend caps, deliberately | There were four (`maxTokensPerRun`/`PerDay`, `maxSpendPerRunUsd`/`PerDayUsd`), a built-in price table, an `ai_usage` ledger and an `ai-cost` command. **All removed.** The dollar half cannot be honest: rates change, there is no verified table for DeepSeek or Gemini, and **how server-side search is billed has never been measured**, so every figure rests on an amount nobody can stand behind. A cap computed from an untrustworthy number is worse than no cap; it reads as protection while protecting nothing. The token half worked but asked the user to pick a number they had no basis for choosing. What bounds a run now is `maxSearches` / `maxFetches` / `maxTokens` / `maxRounds` — all of which measure something real — plus the pre-run confirmation. **If you are tempted to add cost estimation back, first go measure how search is billed.** That measurement is the whole precondition |
| ↳ token counts stay, money goes | `formatUsage` still prints requests / input / output / search count after every run, and that is the *only* number reported. Tokens are what the API itself returns — a fact, not an estimate, and the one figure that reconciles against a provider bill. The distinction is the whole rule here: **report what was measured, never what was inferred from an unverified rate.** |
| ↳ no cross-provider model default | `ai.model` defaults to **empty**, and each provider supplies its own. Model names aren't portable, so any concrete default is one vendor's name — which guarantees that anyone switching provider without also editing `model` trips the mismatch guard. Learned by shipping `claude-opus-5` as the default and immediately hitting it |
| `lib/ai-deepseek.js` | DeepSeek's **OpenAI-compatible** `/chat/completions`. `canSearch` is false there — but see the row below, because that is not the whole story about DeepSeek. `reasoning_content` sits beside `content` in the same delta; miss it and the chain of thought lands in the guide |
| ↳ two endpoints, different capabilities | **DeepSeek's Anthropic-compatible endpoint (`api.deepseek.com/anthropic`) *does* have server-side `web_search`** — verified against the live API (`server_tool_use` blocks, `web_search_requests` in usage, and the same model answering "查不到" without tools). So the working setup is `provider: anthropic` + `ai.baseUrl` pointed there, reusing the existing server-tool loop. Judging one vendor by one of its endpoints was a real mistake made here; don't repeat it |
| ↳ compat-endpoint switches | `ai.webFetch` was learned from a 400: compat endpoints reject the `web_fetch` tool — search-only, so the model never reads a full page. It still defaults off when `ai.baseUrl` is set. **`thinking` / `output_config` / `fallbacks` are three separate decisions and must not be bundled behind one flag — see the row below** |
| ↳ **the bundle was the bug: `output_config.effort` is the one lever that works, and it was never sent** | `extras = ai.anthropicExtras ?? !ai.baseUrl` asks *"is this the official endpoint"*, which is not the same question as *"will this field be accepted"*. Those come apart on DeepSeek's `/anthropic`, which is not official and **does** accept it. Since `provider: "deepseek"` always sets `baseUrl`, `ai.effort` — documented in `config.js` as 「深浅旋钮」, defaulting to `high` — **was never transmitted on the only provider in real use.** Measured: same 10-achievement shard, web tools on: nothing sent → **337 s, 145 955 chars of thinking, 8 searches, 255 chars/achievement**; `output_config: {effort:'low'}` → **43 s, 15 523, 2 searches, 211 chars**; `effort:'medium'` → 219 s, 6 searches. The shipped default `high` was verified end-to-end through `createProvider` after the fix (179 s, 6 searches) but **that run was not in the same batch as the 337 s baseline, so it is not a valid comparison** — with 8× run-to-run variance on this path, only back-to-back numbers mean anything, and `high` has no same-batch baseline. What is same-batch, on a different game, is the row below. The baseline spent **332 of its 337 seconds before emitting the first character of the guide**. Three things follow. **(1) `thinking` and `effort` must be separately sendable**, because sending `{type:'adaptive'}` alongside the same `effort:'low'` doubles thinking and halves the gain (43 s → 87 s) — adaptive overrides effort. **(2) `thinking: {type:'disabled'}` is not "a faster high"**: 6 s and *zero* searches, reproduced twice, i.e. the model writes from memory — exactly the silent quality gap `canSearch` exists to prevent. Windows can't replace a running exe, so the flow is: check GitHub Releases → dialog → download zip **and manifest** → verify both against the `sha256:` digest the API returns → write `apply-update.ps1` to temp, spawn it detached → `app.quit()` → the helper waits for the PID, deletes, extracts, restarts. `updater.js` deliberately **does not import Electron**, which is what makes version compare / manifest generation / sha256 / skip-memory unit-testable at all. It must be in `build.files` — missing it breaks only the packaged build, exactly like `icon.ico`. Full rationale in [docs/self-update.md](docs/self-update.md), mechanics in `launcher/README.md` |
| ↳ the manifest, and why not a keep-list | User data sits *inside* the app folder (`resources/tracker/`), so "clean the folder, then extract" deletes `steam.db`. Deletion therefore goes by a **manifest of what the previous build installed**. The two designs fail in opposite directions and that is the entire argument: a wrong manifest leaves a junk file, a wrong keep-list destroys data — and `dbPath`/`guidesDir` are configurable, so a keep-list can never be complete. Three properties do the work: **deletion runs before extraction** (so over-deleting program files is self-repairing, and a stale manifest is untidy rather than dangerous), **only files are removed and only already-empty directories are pruned** (`resources/tracker/data/` holds the database, so it is never empty), and **the manifest cannot contain user data** because it is generated from the unpacked build, which the `extraResources` allow-list already guarantees is program-files-only. Safety is constructed here, not filtered |
| ↳ manifest missing ⇒ overwrite, never guess | The manifest is a **separate release asset**, not a file in the zip — it has to be, since electron-builder seals the zip before `postbuild.js` runs and a manifest describing a zip containing itself is circular. The helper writes it into the app folder after extracting. That yields the ≤1.1.3 fallback for free: a fresh unzip has no manifest, so the first update off it is a plain overwrite. **Do not "improve" this into inferring which files are program files.** One last dirty overwrite for existing users, clean forever after, is the accepted price. `postbuild.js` must also generate the manifest *before* it copies `local.config.json`, or that file joins the manifest and the next update deletes it — the data directory then silently reverts to the default, which reads as total data loss. Guarded by a check that fails the build, because ordering is precisely what a later edit undoes without noticing |
| ↳ the two failure directions | The **check** is silent — offline is the normal case, and an error box every morning trains you to dismiss the feature. A **download or verification failure after the user clicked 立即更新** is not silent: they are standing there waiting. A missing or unparseable `digest` **refuses the update** rather than installing unverified, since skipping the check means executing 133 MB of unverified code with nothing about the result looking wrong. Checks run 10 s after launch and then daily — **not startup-only**, because tray residency made "startup" rare, the same reason `maybeAutoSync` had to move to the window's `show` event |
| ↳ the helper must outlive `app.quit()`, and `detached` does not achieve that | Measured in a real session — four launch strategies each starting a dummy helper, then quitting immediately: `detached: true` **dies**, plain `spawn` **dies**, `cmd /c start` survives, WMI `Win32_Process.Create` survives. That is the signature of a **Job Object**: Electron puts its children in one with kill-on-close, and Windows' `DETACHED_PROCESS` (which is what Node's `detached` maps to) governs the *console*, not job membership — it cannot escape. Only "not our child at all" works. `detached` is not enough, and the failure is silent: the app quits and never comes back while the log reads 「helper 已启动」, because `spawn()` returning says nothing about whether the process started — **launch failure arrives as an async `error` event**, so it needs a listener. `primaryLaunch` is `cmd /c start`, with WMI as `fallbackLaunch`; the redundancy is justified here specifically because *a broken updater is already on the user's machine and the fix has to travel through it*. The primary uses `-File`, not `-EncodedCommand`, because cmd's command line caps at 8191 and the encoded script is ~10 700 |
| ↳ confirm the handoff *before* quitting | The helper's first statement writes an alive-marker; the app polls for it (15 s, then the fallback launcher, then gives up) and **only then** calls `app.quit()`. If nothing reports in, it shows an error and **keeps running**. This is what turns the worst outcome — "the program closed itself and never came back", which happened once for real — into "the update didn't happen, but the program is still here". Blind-quitting is the actual defect that made the `detached` bug catastrophic rather than merely annoying |
| ↳ packaging | `extraResources` is **one rule with an allow-list filter** (`tracker.js`, `package.json`, `*.html`, `lib/**/*`), never a file-by-file list — so new core files need no packaging edit, and `config.json`/`data/` can't leak into a build because they're not on the list. Build output is the repo-root `dist/` (gitignored); `launcher/postbuild.js` renames it, copies `local.config.json`, and writes the root `.lnk`. Packaged filenames are ASCII (`SteamAchievementTracker`) while all UI stays Chinese — Chinese filenames break `WScript.Shell`, `taskkill` output, and shell quoting |

### The frontend ↔ backend contract

`Dashboard.html` makes **26** calls shaped like `rpc.withSuccessHandler(fn).withFailureHandler(fn).method(args)`, served by `lib/rpc.js`. (This said 12 for a while, then 17 — and 17 was *already* wrong before `previewGuidePatch` was added, so it has now drifted twice, exactly like the test-file count below. **Count it, don't trust it**, and count the chain's entry point rather than its tail: `withSuccessHandler(` appears once per chain, while grepping method names sweeps in `getElementById` and misses any chain whose method sits far from the handler.) **Keep the contract:** a method that returns `{error: '...'}` is a *successful* call (the frontend inspects `result.error` itself); only network/thrown failures reach the failure handler. Adding a Dashboard method means adding it to `lib/api.js` — `rpc.js` proxies any name and needs no changes.

`Setup.html` uses the same `/api/<method>` contract via a plain `fetch`, not `rpc.js` (no need for the shim's sync-status polling). Its methods — `completeSetup`, `getSetupStatus`, `getSettings`, `saveNotionConfig`, `listNotionParents`, `createNotionGuideDb`, `repairNotionGuideDb`, plus the four guide-archive ones (`listGuideArchives`, `readGuideArchive`, `restoreGuideArchive`, `deleteGuideArchive`) — are (bar `repairNotionGuideDb` and the archive four) the only ones in `lib/api.js` that mutate `config`/`steam` in place rather than only touching `db`. `repairNotionGuideDb` is the odd one out and worth knowing about: it touches no local state at all, it writes to the **user's Notion database** (appending missing status options), which is why it is only ever reached from a button the user pressed and never from the save path. `restoreGuideArchive` is the second of that kind and the sharper one — restoring a `.json` archive **deletes the live blocks of a real Notion page** before rewriting them, so it is likewise button-only, takes a fresh backup first, and is confirmed by a second click that reads 「整页重写」 rather than 「确定」. (`createNotionGuideDb` saves the new database's ID itself rather than handing it back for the page to submit later: the database already exists by then, and a user who forgets to press save is left with an orphan database in Notion and a tool that says Notion isn't configured.) That is required because `SteamClient` copies `steamApiKey`/`steamId` into instance fields at construction (`lib/steam.js`), so writing `config.json` alone leaves the running process unusable until restart. `NotionClient` is built fresh at each call site, so updating `config.notion` is enough there. Any future path that accepts credentials at runtime hits the same trap.

**Blank secret means "keep", never "clear".** Both `completeSetup` (API key) and `saveNotionConfig` (integration secret) treat an empty field as *unchanged*, because the settings page pre-fills the non-secret values: without that rule, opening settings to change a SteamID and pressing save would wipe the Notion token. `Setup.html` also compares the DB id against its loaded value and skips `saveNotionConfig` entirely when nothing Notion-related changed, so an unrelated edit never blocks on a Notion round-trip or fails because Notion happens to be down. Clearing a secret is deliberately a `config.json` edit.

## Key config

`config.json` (gitignored, mode 600), read via `lib/config.js`. Env vars `STEAM_API_KEY` / `STEAM_ID` / `NOTION_TOKEN` / `PORT` override it.

- `steamApiKey` / `steamId` — required for anything touching Steam
- `language` (default `schinese`) — affects game and achievement names
- `port` (8777), `syncStaleHours` (12, `0` disables sync-on-open), `requestDelayMs` (100), `storeRequestDelayMs` (300) — two knobs, see the row below
- `sweepBudget` (120), `maxStatsAgeDays` (7), `perfectGameMaxAgeDays` (3) — phase 2 sampling, see "Sync behavior". Only the Dashboard auto-sync and `sync --fast` read these; plain `sync` ignores them.
- `checkboxSyncOnServe` (true), `checkboxSyncOnServeCascade` (false) — the automatic tick pass, see "Automatic checkbox ticking". The cascade default deliberately differs from the CLI's.
- `guideStatusOnServe` (true) — keep a guide page's `Status` in step with completion in both directions, see "Guide page status".
- `notion.token`, `notion.overviewDbId` — guide sync only. The DB ID lives in config, never in source.

**Never hardcode credentials, and never commit `config.json`, `data/` or `guides/`.** All three are gitignored. The repo is public, and `guides/` holds guide text written by the owner plus its history (`.drafts/` unvalidated AI output, `.migrated/` local copies left behind by a move to Notion, `.backups/` pre-overwrite originals) — none of it repo content.

## Data model (`games` table)

`appid` (PK) / `name` / `achieved` / `total` / `has_achievements` / `rate` / `status` / `sync_locked` / `favorite` / `priority` / `family` / `new_ach_date` / `updated_at` / `last_played` / `stats_checked_at` / `perfect_lost_date` / `ach_added_date`

- `status`: `''` (normal), `'Unvetted'` (Steam Profile Features Limited), `'Manual'` (hand-maintained).
- **`Manual` is the 🔒 lock in the UI — same column, different vocabulary** (renamed). The word never described what it does; locking a row does. Do not rename the column to match: `status` values still reach CSV export and the user's spreadsheet, so the storage name is a compatibility surface. **`addGame` does not force `Manual`.** Locking every hand-added row is backwards for the commonest reason to add one: a family-shared game *is* the case where Steam returns real progress, so locking it would freeze the numbers at the moment of adding. New rows sync normally; the lock is one click away if Steam has nothing.
- `has_achievements = 0` replaces the old `'N/A'` string in the numeric total column. `NULL` means "not synced yet".
- **`sync_locked` is what the sync actually checks**, not `status`. They are separate columns because "skip the daily achievement sync" and "pin this row's label against Steam re-classifying it Unvetted" are different wishes — conflate them and you cannot have one without the other. The Dashboard moves both together (`setManualStatus` sets both); diverge them by hand when you actually want to.
- `family` is purely informational and never affects sync behavior. It exists because "not in `GetOwnedGames`" and "should skip achievement sync" are two *different* facts.
- **`last_played` / `stats_checked_at` are the sampling state for phase 2** (see below). `last_played` is `rtime_last_played` as of the last *successful* read; `stats_checked_at` is when that read happened. `updated_at` cannot substitute — it moves on any row change, including a ♥ toggle from the Dashboard, so it can't answer "when did we last ask Steam". Written by `markStatsChecked()`, never on a `retry`.
- **`perfect_lost_date` / `ach_added_date` are the 🔔 notifications, and they are this project's *only* deliberate transition detection.** They record "you had this at 100% and the developer added achievements" and "Steam said this game had no achievement system and now says it does". Both are stamped inside `updateGameStats`, the one moment `prev` is still readable — afterwards a sub-100% row is indistinguishable from one that was never perfect, and `has_achievements` has already been overwritten with `1`. Two guards carry them: `wasPerfect` requires a real numeric baseline (so the first sync of a row can't fire it), and `achAdded` matches **only an explicit `0`**, never `NULL` — `NULL` means "never synced", and treating it as the transition would dump the entire library into the bell on the first full sync. Read the contrast with "Guide page status" below before touching either: that rule forbids transition detection because its question ("what should this page's status be *now*") is answerable from current state; this one requires it because its question ("what changed recently") is not. The cost is accepted and unavoidable — an event observed by a run that fails to write is gone, and an existing database starts with an empty bell because nothing recorded these events before the columns existed. Pinned in `test/notifications.test.js`.
- New columns need `ALTER TABLE`, not just an edit to `SCHEMA`. `SCHEMA` is `CREATE TABLE IF NOT EXISTS` and does nothing to an existing table — `migrate()` in `lib/db.js` walks `ADDED_COLUMNS` against `PRAGMA table_info`. Add to **both** when adding a column.

## Sync behavior

`fullSync` runs three phases in order over the whole library, with no cursor and no runtime cap. Ctrl+C mid-run is safe — each game is committed as it completes, so re-running only redoes work that was in flight.

1. **`syncLibrary`** — new owned games get inserted (with a name lookup); existing *owned* rows get their `Unvetted` stamp refreshed, except `'Manual'` ones. Rows whose appid is **not** in the current `GetOwnedGames` snapshot are left completely untouched — that's the preservation rule (it keys off ownership, not `status`).
2. **`syncAchievementStats`** — refreshes counts for rows with `sync_locked = 0`. A total higher than last time stamps `new_ach_date` (the Dashboard's "new achievements" badge). **Which rows get checked is decided by `selectStatsTargets()` — see "Phase 2 sampling" below.**
3. **`syncAchievementSchema`** — per-achievement detail for games that are new to the `achievements` table or bumped in the last 7 days; skips games at exactly 100% and games with no achievement system.

**`serve` also runs guide discovery on start** (`syncGuides()` in `lib/server.js`, off via `syncGuidesOnServe: false`) — the same work as `node tracker.js guides`. It is deliberately **outside** the `syncStaleHours` gate and needs no Steam credentials: a guide page created minutes after a sync must show its Dashboard link immediately, and gating it on staleness would hide new pages for hours. `fullSync` itself does **not** touch guides — a new Notion page will never be discovered by achievement syncing alone, which is why this hook exists at all. Failures are logged and swallowed; a dead Notion token must not take the Dashboard down with it.

**The three startup jobs are sequenced, not concurrent** (`startupJobs()`). They cannot be fire-and-forget, because each step feeds the next: discovery must finish before the sync knows which guide pages are new, and the tick pass must run after the achievement refresh or it matches against last run's unlock state. Still off the `listen` callback's critical path — the page opens immediately either way.

### Phase 2 sampling — `achieved` and `total` do not change for the same reasons

This is the whole design, and getting it wrong loses data *silently* (a skipped row doesn't error, it just leaves a stale number on the Dashboard forever):

- **`achieved` is a fact about the account.** It cannot change unless you played. Gating on `rtime_last_played` is exactly correct for it.
- **`total` is a fact about the game.** A developer patch adds achievements with zero playtime, which drops a 100% game below 100%. **Gating that on `rtime` is simply wrong.**

So `selectStatsTargets()` unions three groups:

1. **played** — `rtime_last_played` exceeds the stored `last_played`. Keeps `achieved` exact.
2. **unowned** — appid absent from the `GetOwnedGames` snapshot (family-shared / delisted / hand-added). No timestamp exists for these, so they are checked every run. Freezing them out would contradict the "a game can vanish from `GetOwnedGames` while `GetPlayerAchievements` keeps working" quirk below. **Except the ones already at 100%, which go to sweep instead** — the `rtime` gate exists to protect `achieved`, and a finished game's `achieved` cannot move: more play cannot raise it. The only thing left that can change is `total`, which is precisely sweep's job, and `perfectGameMaxAgeDays` (3 days) was tuned for exactly that event. The **owned** copy of the same game already took that route; the unowned one was checked every run purely because we happen to lack an `rtime` for it — the one input that is irrelevant here. Measured: 10 of 19 unowned rows, i.e. 59 requests a run down to 50, and the daily load from those ten from ~20 checks to ~3. **The predicate is deliberately stricter than `maxAge`'s** — it requires `rate === 1` *and* `achieved === total` *and* `total > 0`, because the two error directions are not symmetric: a stale `rate` alone would freeze a still-moving `achieved` for three days, while a disagreement merely costs a few unnecessary requests. Both spellings agreed on all 317 rows when measured, which is the argument for taking the strict one rather than against it.
3. **sweep** — rows overdue for a re-check, capped at `sweepBudget` per run. This is the only thing that catches a retro-added achievement, so **do not remove it as an optimisation.**

Details that are load-bearing:

- **The sweep sorts by *overdue ratio* (`age / itsOwnDeadline`), not by absolute age.** Perfect games expire in 3 days and everything else in 7; sorting by raw age lets an 8-day-old ordinary game jump ahead of a 4-day-old perfect one, which makes the shorter deadline decorative. Pinned in `test/selection.test.js`.
- **`markStatsChecked` is never called on a `retry`.** Recording a rate-limited game as "just checked" would push it to the back of the queue and turn throttling into silent data loss.
- **A row with no baseline (`stats_checked_at IS NULL`) is always checked, uncapped.** The first run after this migration is therefore a full ~160 s sync; every run after is ~8 s. That is intended — there is nothing to compare against until the baseline exists.
- **No `playSnapshot` ⇒ check everything.** `node tracker.js sync` deliberately stays a true full sync; `sync --fast` and the Dashboard's auto-sync opt in by passing `selection`. Keep that escape hatch.
- **Thresholds are targets, not guarantees** — `sweepBudget` binds first, and the requirement is **Σ(1/each row's own deadline)**, not a fixed share of the library: measured at 313 unlocked rows, **143 of them at 100%** and therefore on the 3-day deadline, that comes to **72 rows/day** — the perfect games alone are 48 of it. The old default of 40 thus only broke even at ~2 Dashboard opens a day and compounded debt below that; it was found with **172 rows standing overdue**. **120** covers once-a-day use with headroom and in steady state never binds at all, because once every row is inside its deadline the pool is naturally small — so the cap only appears after an absence, which is exactly the case it exists for. **Do not remove the cap.** An uncapped sweep stamps every row with the same `stats_checked_at`, so they fall due together and the load herds into a spike every 3/7 days instead of staying spread; the cap is what keeps the rotation staggered. Converting rows to seconds needs the per-row cost, which was **~499 ms — 199 ms of network plus a 300 ms `requestDelayMs`** until that knob was split (see the pacing row below) and is now ~300 ms. Re-measure rather than quoting any of these.

### The 「立即同步」 button

A page refresh only re-reads SQLite — `getDashboardData()` never touches Steam — so the Dashboard has a manual sync button next to the "上次同步" line. It calls `api.startSync()` → `startBackgroundSync()` in `lib/server.js`, **the same function the startup auto-sync uses**. Keep it that way: one function means one concurrency guard, and the guard is the only thing stopping a click that lands during the startup sync from running two `fullSync`es over the same database.

Two deliberate asymmetries with `maybeAutoSync`: the button **ignores `syncStaleHours`** (that gate answers "should we sync unprompted", and a click has already answered it), and it still passes `selection`, so it's the ~8 s sampled sync, not the ~160 s full one. `node tracker.js sync` remains the way to force a true full pass.

Sharing one function is also what gives the button its checkbox ticking for free — the tick pass hangs off `startBackgroundSync`'s completion, so both the startup sync and the button get it without a second call site.

The button owns no progress UI of its own — `lib/rpc.js`'s existing 3-second poll drives its label and disabled state through a `window.onSyncState` hook, alongside the status bar and the post-sync `reloadDashboard()`. That hook fires **before** every branch in the poll handler, because two of those branches (sync failed, user mid-edit) return early; hanging it off the end would strand the button on "同步中..." forever. Same reasoning as `reloadDashboard`: the frontend reflects the server's real sync state rather than tracking its own, so a sync started from the CLI or a second tab greys the button out too.

**`stats.bumped` must stay visible.** It was computed and thrown away on the Dashboard path for a while (only the CLI printed it) — which is backwards, since a retro-added achievement is precisely the change you cannot notice on your own. It now reaches `syncState` → the status bar, and that notice deliberately does **not** auto-dismiss.

There is deliberately no destructive rebuild/reset command. `syncLibrary` reconciles against Steam without discarding rows, and a "wipe and repopulate from `GetOwnedGames`" helper would silently drop every family-shared and manually-maintained row — data the API cannot give back.

## Steam API quirks

These are verified and hard-won — don't re-derive them, and don't "simplify" the handling:

- `GetPlayerAchievements` HTTP **400** = this game genuinely has no stats for this account. A normal signal, **not** an error, do not retry.
- HTTP **429** = real rate limiting, retry next cycle. Everything else non-200 is also treated as transient.
- HTTP **403** `"Profile is not public"` can come back for *one specific game* even when the profile is public — a per-game "Game Details" privacy toggle on Steam's side. Falls in the retry bucket, but retrying never succeeds until the setting changes on Steam.
- `appdetails`'s `name` field **ignores the `l=` param** (Steam bug) — Chinese names require scraping the store page HTML (`fetchAppNameFromStorePage`), with age-verification cookies and a deliberately loose regex (the class attribute can carry multiple classes).
- Determining whether an owned appid is currently Unvetted **requires two `GetOwnedGames` calls** (`skip_unvetted_apps=false` minus `=true`). A single plain call silently returns the vetted-only view. `fetchOwnedGamesWithUnvettedFlag()` is the only correct way to ask.
- `GetOwnedGames` omits free games unless `include_played_free_games=true` (already set).
- A game can disappear from `GetOwnedGames` while `GetPlayerAchievements` keeps returning its full permanent stats. "Not owned" ≠ "no achievement data" — check achievements directly before concluding a game can't be tracked.
- Family Sharing achievements are recorded per **playing** account. If a shared game is actually played on someone else's account, your `steamId` will correctly and permanently show 0 on it. Not a bug to chase.

## Guide checkbox matching — do not loosen this

Matching an unlocked achievement to a guide checkbox is **exact equality against extracted title candidate segments**. Never substring, never prefix. Three rounds of false positives produced this rule:

1. an achievement name appearing inside an unrelated achievement's *description*;
2. a short achievement name being a strict *prefix* of a different, harder achievement's name — which mis-ticked the harder one once the short one's own box was already checked; and
3. **two achievements in the same game with genuinely identical names.** Exact matching cannot fix this one: the unlocked twin's box gets ticked, leaves the candidate pool, and the same name then matches the *other*, still-unearned box. `findAmbiguousNames()` therefore refuses any name shared by several achievements unless *all* of them are unlocked, and logs the skip rather than staying silent. This is not rare — a 310-game library had 12 such collisions across 11 games.

`extractTitleCandidates()` splits checkbox text into candidates (by line, then by colon/dash, plus the `中文名(English Name)` pattern, plus a trailing-punctuation-stripped variant of each) and requires the achievement name to *equal* one of them. Adding a new candidate-extraction rule is fine; weakening the equality check or removing the ambiguity gate is not.

Two rules about *how* to add one:

- **Append, never replace.** The trailing-punctuation rule adds `秘密食材` alongside `秘密食材。` rather than rewriting it — achievements like 「白手起家。」 and 「胜利！」 have punctuation in their real names, so replacing would turn working matches into misses. Stripped variants go last so exact ones win first.
- **Normalize the candidate side only, never the `defs` name index.** Adding stripped keys to the index would collide `X` with `X。`, and the ambiguity gate would then skip *both*. That trades "fails to tick" for "ticks the wrong one" — backwards from this project's whole bias.

**The gate closes per name, not per achievement** — a colliding Chinese name does not disqualify a unique English one. See "Same-name collisions" under Current state for why (most collisions are localization bugs) and what that does *not* license. `test/matching.test.js` pins all three failure modes — run `node --test` after touching `lib/guides.js`.

**The one way out of case 3 is the description.** `matchAchievements` runs two passes: ambiguous names first, resolvable *only* by the checkbox quoting the achievement's full description when that description is unique in the game (then the box is unambiguously about that achievement); then exact name matching for everything else. Description-first is deliberate — it is the more precise signal, so it claims its box before name matching could take it. This is why the guide-writing convention is `**name**` / verbatim official description / your own notes, and why paraphrasing the description has a real cost. See `.claude/skills/achievement-guide-writing/SKILL.md`.

The design deliberately prefers a missed checkbox over a wrong one.

**`flatCompare` is the one "is this the same text" predicate, and folding typographic quotes into it is normalization rather than loosening.** Reported as 「波西亚时光有一些成就 miss 了 description」. Measured first: of 91 achievements, **45 are quoted verbatim, 45 have no description on Steam at all** (every one `hidden=1`; asking Steam's schema directly returned **0** descriptions we were missing and **0** hidden achievements carrying one), and exactly 1 mismatched — 好家长, where the guide *had* copied the description and only the quote glyphs differed (Steam `“幸福的孩子”`, guide `"幸福的孩子"`). So the reported symptom was overwhelmingly Steam's, and the real defect was ours being stricter than the content warranted. Across the library that is **14 of 791** mismatches; the other **777 are genuine paraphrases in hand-written guides and must stay untouched**, which is exactly why `paraphrased-description` is a warn. Folding `“”„‟＂` → `"` and `‘’‚‛＇` → `'` cannot make two *different* descriptions equal, only two spellings of the same one — the same category as the whitespace collapse already there — and the pathological case (two achievements differing only by quote style) makes the description count 2, so neither matches, landing on this project's chosen side. **Dashes and the ellipsis are deliberately not folded**: no evidence demanded it and their variants can differ in meaning; the cost is visible and accepted, since the pre-measurement predicted 14 and folding quotes alone recovered 13. Live effect: **595 → 582 warns, and two more guides went completely clean**. The extraction matters as much as the fold: the predicate existed as **three** private copies, and only two of them were the same question — `resolveTodoToAchievement` and `guidelint` (write-side, now both `flatCompare`), while `nameGroupAlreadySatisfied`'s is **deliberately looser and must not be merged**, because it decides whether to print a log line and never what to write. `matching.test.js` pins that the two write-side callers do not re-inline it, and that the fold stops at quotes.

**Always `checkbox-sync --dry-run` before a manual full run.** Ticking a Notion box can't be undone automatically, and failure mode 3 above was caught by a dry run before it wrote anything. Sync only ever ticks, never unticks, so it cannot repair its own mistakes.

### Automatic checkbox ticking (the one unattended write path)

`serve` and the 立即同步 button both run a tick pass after the achievement sync (`runCheckboxSync` in `lib/server.js`, off via `checkboxSyncOnServe: false`). **This is the only place in the project that writes to Notion without a dry-run in front of it**, so every narrowing below is load-bearing — do not widen one without replacing the safety it provided:

- **`appids` whitelist, not the full candidate set.** Only rows whose `achieved`/`total` actually moved this run (`stats.changedAppids`, fed by the new `gained` flag out of `updateGameStats`) plus guide pages registered for the first time this run. A full pass is ~40 games × (1 Steam call + 1 Notion page read + 350 ms) on *every* Dashboard open, nearly always to find nothing. **`appids: []` means "run nothing", never "no filter"** — writing `appids?.length ? … : everything` turns the common case (nothing changed) into a full scan and silently undoes the whole design. Pinned in `test/checkbox-selection.test.js`.
- **`gained` is false when there's no baseline.** On the first sync of a row, `achieved` goes `NULL → n`; counting that as "gained" would make the entire library a candidate on the run where that's most expensive.
- **Cascade off by default here** (`checkboxSyncOnServeCascade`), unlike the CLI. The cascade is the one deliberately over-ticking path, and this route has no human gate in front of it.
- **A game that hit 100% *this run* is still visited.** The 100%-skip must stay decoupled from `cascade` — folding them into one expression is a real bug, not a tidy-up. With cascade off, the achievement that *completes* a game could never be ticked automatically — by the next run the game is at 100% and is skipped, forever. The `achievementsFor(...).length > 0` guard still applies (the 55/55 no-schema case), so this costs nothing on the games that rationale was about.
- **Failures are soft and separate.** Errors go to `syncState.tickError`, never `syncState.error`. A dead Notion token must not present as "achievement sync failed" when the achievement data synced fine.

Review is `sync_log` + `node tracker.js log` — the auto path writes the same rows the CLI does. The Dashboard also raises a notice naming the first few ticks, and like the `bumped` notice it **does not auto-dismiss**: it is reporting a write to the user's own notes.

### Guide page status (`Done` ⇄ `Staged`)

The Notion guide page's `Status` property is kept in step with completion, **both directions** — `syncGuideStatuses` in `lib/guides.js`, run by `node tracker.js guide-status` and, on the serve path, right after the tick pass (`guideStatusOnServe`).

- 100% and not `Done` → **`Done`**.
- Below 100% and currently `Done` → **`Staged`**. Effectively always a developer patch adding achievements, which is the one kind of change that happens without you playing.

Load-bearing details:

- **It converges on state; it does not watch for the transition.** Crossing 100% (in either direction) exists only for the instant `updateGameStats` writes it. Any run that observes it but cannot write — a CLI `sync` on a box with no Notion token, an interrupted process, an expired token — loses it permanently, because every later run sees the same value on both sides and can infer nothing. The rules are therefore stated over current state, which is idempotent, self-healing and re-runnable. **Do not "optimise" this into transition detection.** (The 🔔 columns `perfect_lost_date` / `ach_added_date` *do* detect transitions, and that is not a contradiction — they answer "what changed recently", which current state genuinely cannot answer, and they pay the matching price: a missed observation is lost forever. This rule applies where current state *is* a sufficient answer, and there it always wins.) Measured proof: the one page that needed demoting (Supermarket Together, 28/51) has `new_ach_date = NULL`, so a rule gated on "we saw `total` grow" would never have fired for it at all.
- Convergence is nearly free because `queryGuideDatabase` already pages through the whole database; it only has to stop throwing the `Status` property away. Cost is ~3 API calls per run total, not per game.
- **The two directions are deliberately asymmetric in how aggressive they are.** Promotion overwrites *everything* except `Done`, `Differed` included — completion beats a hand-set workflow state. Demotion touches *only* `Done`. A sub-100% page sitting at `Paused` / `In progress` / `Not started` / `Differed` is a state you chose, and rewriting it on every Dashboard open would put you and the tool in a loop overwriting each other. Pinned in `test/guide-status.test.js`.
- The two rules are mutually exclusive by construction (`achieved >= total` vs `<`), so a page can never satisfy both and oscillate.
- **A `total` of `NULL` is not "dropped below 100%".** `markNoAchievements` clears `total` when Steam says a game has no stats, and rate-limits/403s take the `retry` path and write nothing at all — so the `total > 0` guard is what stops a Steam hiccup from demoting a finished page.
- **The property's *type* is read, never assumed.** Notion's `status` and `select` are different property types whose write payloads differ (`{status:{name}}` vs `{select:{name}}`), and the wrong one is rejected. `fetchGuideStatusSchema` reads name, type and options; **both** `Done` and `Staged` are validated up front, so a database missing one fails with a readable message instead of a Notion 400 halfway through.
- Notion-kind guides only — local markdown has no status property. Failures are soft and land in `syncState.statusError`; `syncGuideStatuses` returns `applied` (writes that actually succeeded) so callers report direction without parsing log text.

Ordering matters: status runs **after** the tick pass, so a game that just completed gets its last boxes ticked before the page is marked done. Marking a page `Done` over unticked boxes is the wrong end state.

### Nested sub-step checkboxes (`collectSubStepTicks`)

Guides nest sub-steps under an achievement — individual shrines, individual techniques, one line per side-quest. Two things were true and both were wrong:

1. **The backends disagreed.** `loadTodos`'s regex is `/^\s*[-*]\s*\[/`, so local markdown always read indented boxes; `fetchAllToDoBlocks` pushed a `to_do` and `continue`d, so Notion never descended into one. Identical guide content behaved differently by backend. Notion now recurses, and both backends set `parent` on each todo (Notion: the enclosing to-do's block id; markdown: inferred from an indentation stack). Containers like `toggle` pass `parent` through unchanged — a checkbox inside a toggle inside an achievement is still that achievement's sub-step.
2. **Sub-steps could never be auto-ticked.** They aren't achievements; Steam has no data for them and their names match nothing. Name matching can't reach them, ever.

So `collectSubStepTicks` ticks them by **inheritance**: if the parent achievement is known unlocked, its nested boxes get ticked. Evidence of "known unlocked" is only ever (a) a match made this run, or (b) an already-ticked box that `resolveTodoToAchievement` maps to a uniquely-identified, genuinely unlocked achievement. Without (b) the feature would be useless — most achievements were ticked in earlier runs.

**This is the one place in the codebase that prefers over-ticking, and it is deliberately inconsistent with the rule above.** The assumption "parent unlocked ⇒ every listed sub-step was done" holds for *all-of* achievements ("fail every technique at least once") and **fails for *any-of* achievements** — "reach an ending" with nine endings listed underneath would falsely tick eight. The code cannot distinguish them. Mitigations, all of which should stay: cascade is skippable with `--no-cascade`, every cascaded tick is logged as `已勾选子步骤(父成就已解锁)` so `sync_log` can be re-read afterwards, and `--dry-run` lists them separately. If you write a guide whose sub-steps are alternatives rather than requirements, don't nest them under the achievement.

Two consequences elsewhere. `checkboxSync` will consider a 100%-complete game when cascade is on — all achievements unlocked is exactly when sub-steps are most likely ticked-worthy — **but only if that game has rows in `achievements`**, because recognising a parent needs `resolveTodoToAchievement`, which needs names/descriptions. `syncAchievementSchema` deliberately skips games at exactly 100%, and measured against the real database **55 of 55** guide-having perfect games have no schema at all. Widening the filter unconditionally cost 55 wasted page reads plus 55 Steam calls per run and could never tick anything; the `achievementsFor(...).length > 0` guard keeps the candidate count at 42 and starts including a perfect game automatically if its schema ever gets synced. Second, `auditGuideTicks` ignores ticked sub-step boxes that resolve to no achievement — counting them as "undetermined" would drown the one number that measures real audit coverage. A nested box that *does* resolve to an achievement is still audited normally.

## Reverse lookup (the `audit` command)

`checkbox-sync` asks "where does this achievement go?"; `audit` asks the opposite — "which achievement is this ticked box about, and is it actually unlocked?" That's `resolveTodoToAchievement()`, and it accepts only two unambiguous handles: the achievement's full description when unique in the game, or a name that maps to exactly one achievement. Anything else is reported as undetermined rather than guessed, and **the undetermined count is always printed** — "0 wrong" would otherwise imply coverage the audit doesn't have.

**Never map by description *prefix*.** A first draft of this matched the first 14 characters, which collapses tiered achievement families ("deal 100/500/1000 damage", "fill in every page of X's report card"): a correctly-ticked easy tier gets attributed to its locked harder sibling. On real data that produced 4 false findings out of 5 — the same bug class as the name-prefix one above, in a different disguise. `test/matching.test.js` pins the tiered-family case.

## Don't cry wolf in the log

When the sync can't act, think about whether that's *actionable* before logging it. Ambiguous-name groups whose boxes are already correctly ticked must not log "needs manual review" — on every run that is a permanent false alarm, which is worse than no alarm because it trains you to ignore the log. `nameGroupAlreadySatisfied()` now silences those, and they speak up again if a second same-named achievement gets unlocked without its box ticked.

That helper uses loose substring matching, which is banned in the tick path. The distinction is intentional and commented at the call site: **it decides whether to print a line, never whether to write.** Getting it wrong costs one log line; getting the tick path wrong corrupts the user's notes. Keep new heuristics on the correct side of that line.

- **The 🎮 recently-played badge can never appear on a family-shared / delisted row.** It derives from `last_played`, which comes from `GetOwnedGames`; rows absent from that response have no timestamp at all and Steam offers no other source. Looks like a bug, isn't one.
- **Games with `has_achievements = 0` are retried**, not permanently excluded. They get re-marked if Steam still says no stats; harmless. `GetOwnedGames`'s `has_community_visible_stats` flag predicts this set exactly and skipping them would save a few dozen calls per full pass — **considered and deliberately rejected, don't re-propose it.** The moment a game adds achievements is the moment that flag flips, and by then we'd have stopped asking.

  Every one of these fails quietly in production. That is the entry criterion.
- **`syncGuidesFromMarkdown`'s `added` includes re-registrations, not just new guides.** It re-upserts every local `.md` on each run and pushes all of them, with `action: 'appended' | 'updated'` telling them apart. `syncGuides` filters to `'appended'` before feeding the tick pass — without that filter every local guide looks newly-discovered on every start and the targeted tick degrades into a full local scan. The Notion side's `added` is already genuinely new-only (filtered by `existingIds`).
- **Native dialogs are unusable in this app — in *either* process.** A native dialog appears and vanishes before it can be clicked in the packaged build, so every action gated behind one is unreachable; `dialog.showMessageBox` from the main process returns instantly with `response: 420`, a value outside the button range. The boundary is native-vs-page, not renderer-vs-main. **Do not add a native dialog anywhere in this project** — it fails silently, and a non-zero response reads as "user declined". `askConfirm({title, body, okText, danger, notifyOnly})` is the in-page replacement, identical in browser and package. It returns a **Promise**, so every call site must `await` it: a forgotten `await` makes `if (!askConfirm(...)) return` never return, silently green-lighting the dangerous action. Both rules are pinned in `guidegen.test.js`.
- **`sync_locked = 1` rows are never touched by any sync phase.** If a row "won't update," check that first.
- **Notion page identity must use the normalized UUID**, never raw URL text — Notion sometimes prefixes URLs with a title slug, so the same page's URL differs between queries. Comparing raw URLs once caused already-linked pages to be treated as new and overwrite curated names (`normalizeNotionId` in `lib/notion.js`).
- **One appid, one guide backend.** Markdown discovery won't overwrite a registered Notion guide unless `--force`.
- **Local guide paths are contained to `guidesDir`** (`resolveGuidePath`, over `pathsafe.isInside`). Keep that check if you touch it — `guides.url` is data, and `guidepatch.landPatchLocal` **writes** to what it returns, so a hole there is a write primitive, not just a read one.
- **Defence in depth defeats single-mutation testing, and that is not a reason to remove a layer.** `safeGuidePath` and `containedPath` each hold several checks that overlap; deleting any *one* leaves the rest still blocking every hostile input, so the mutation comes back green. The honest mutation there is replacing the whole function with the version that shipped the bug — do that instead of concluding the assertions are fake, and do not thin the checks to make them individually observable.
- **Documentation drifting from code is a real failure mode here.** A secret once sat hardcoded in this public repo for months while three separate docs claimed it was read from config. Verify against code, not docs.
- **`localDate()` not `toISOString().slice(0,10)`** for user-facing dates — the latter is UTC and will be off by a day in the evening.
- **Strip comments before any source assertion — including `//`, not just `/* */`.** This codebase's comment density is its own hazard: an assertion that greps for a symbol gets satisfied by the *comment explaining that symbol* sitting beside the code, so deleting the code changes nothing and the check passes forever. **Write the assertion, then break the thing it guards and watch it go red.** A source assertion that has never been seen failing is not evidence of anything.
- **Strip line comments *before* block comments, not after.** A `//` line in this codebase can legitimately contain `/api/` followed by a star, and the block-comment regex reads that as an opening delimiter, then deletes everything up to the next closing one — **including real code**. Measured here: a source assertion sliced the right function, the strip silently ate the line under test, and mutating `appendChild` to `innerHTML +=` left the test green. Strip `^\s*//.*$` first and the false opener is gone before the block pass runs. (A related hazard when writing *about* this: a JSDoc comment containing a closing block-comment marker terminates itself.)
- **A source assertion must slice to the block it means — never `indexOf(anchor)` plus a byte count.** A fixed window drifts as the code between the markers grows, and the dangerous direction is the quiet one: a window that still contains both markers while the code between them has changed. Slice between two real anchors and assert both exist, so losing one is a loud failure rather than a silently narrowed check.
- **UI state that hangs on a single un-retried async call whose failure is swallowed will eventually be wrong on screen, and only on a slow day.** Both known cases were invisible in development, where the server is always warm and always up: a flag whose repaint depended on one request beating another, and a page load with no `catch` against a server that wasn't listening yet. **Ask what the screen looks like when that call is slow, and when it throws.** Prefer re-rendering from state already in memory over re-fetching to flip a flag.
- **An author `display:` silently defeats the `hidden` attribute.** `[hidden] { display: none }` comes from the *user-agent* stylesheet, so any author rule outranks it and turns that element's `hidden` into decoration — JS keeps setting `.hidden = true`, the element keeps showing, nothing errors. Both pages carry a global `[hidden] { display: none !important }` and `html-smoke.test.js` pins it. Patching per element is whack-a-mole; the next `display:` rule opens a fresh hole just as quietly.
- **Guide text never goes in the database** — only a pointer. Guides have to stay human-editable and tickable where they live; the `guides` table tracks *where*, never *what*.

## Current state and open items

The core pipeline (library sync, achievement counts, achievement detail, Dashboard, ♥/★ flags) is done and in daily use. Guide sync works against both backends, checkbox ticking happens automatically on Dashboard open and on 立即同步, and the same chain keeps each guide page's `Status` in step with completion. The working corpus lives in Notion; the local markdown path is fully supported and is what `guides/` is for.

**Re-measure, don't quote.** Corpus figures — how many guides, how many collisions, how many ticked boxes — go stale silently, and every one ever written into this file did. Run `audit`, `guide-lint` or a SELECT when you need a number.

Four readings that have been got wrong and will be again:

- **`checkbox-sync --dry-run` proposing 0 ticks is not evidence that Notion and Steam agree.** A dry run only proposes ticks for achievements it can *match*; a guide whose boxes match nothing produces the same silent 0. `guide-lint` measures that gap — an achievement with no reachable checkbox could never have been ticked and never shows up here. `audit` doesn't catch it either: it only inspects boxes already ticked. Read 0 as "nothing actionable found".
- **A clean recorded baseline is not evidence the sync is running.** A machine with no Notion token configured errors nothing — `checkbox-sync` simply never runs. Check `sync_log` has recent rows before believing it.
- **A description cannot make an achievement stop being ambiguous.** The gate reads names only. Quoting the description satisfies the description pass; it does not un-collide a name.
- **The gate closes per *name*, not per achievement.** `safeNamesOf()` drops only the names actually in `unsafeNames` and lets pass 2 match on whatever is left, so an achievement whose Chinese name collides can still be matched by its unique English name — most collisions are Steam localization bugs in one language, not genuine twins. The equality rule is untouched: still exact, no substring, no prefix, and the colliding name itself is still never usable. Don't confuse "stop discarding a unique name" with "loosen matching". Pass 1 cannot finalise a skip, since pass 2 may rescue the achievement.

**`config.json` is per-machine and gitignored.** The guide database ID lives there as `notion.overviewDbId` and stays out of this repo — read it from config rather than pasting it into a tracked file. An empty `sync_log` plus a quiet Notion feature means the token, not a bug. `saveConfig` requests mode `600`, which Windows does not honour.

Known outstanding items:

- **Guides not yet written** — some pages exist in the Notion guide database with no `appid:` line, so guide discovery skips them every run (expected, not an error). If they are also *empty*, `guide-gen` adopts and fills them rather than creating a second page.
- **Leftover spreadsheet automation** — a few daily jobs still update an old Google Sheet as a secondary backup. To retire them, delete the triggers in that Apps Script project; run `node tracker.js export` first, since the sheet stops updating afterwards.
- **The Notion landing path has run live, and reading the page afterwards is still the step that finds things.** The fake-client tests pin the refusals and the read-back but cannot say whether Notion renders our blocks the way we think — and twice now it did not. 罗曼圣诞探案集 landed with a blank line inside 28 of its 50 checkboxes (empty Steam descriptions), and 加利宅邸悬案 landed with four literal `<details>` / `</details>` paragraphs. Both were reported by the owner from the rendered page; no test and no read-back verdict caught either. **Read the page after a landing.**
- **`--only` has never completed a verified live run.** Its first attempt failed and was fixed; nothing has gone end to end since. Run it on a **local** guide first if there is one, with `--dry-run` before anything that spends.
- **Ideas, not commitments** — write the missing guides, enrich the Dashboard, or add a launchd plist if sync-on-open isn't enough.

### The AI guide commands

- `node tracker.js ai-check [appid]` exercises the whole provider chain against the real API and prints stop reason, server-tool calls, `pause_turn` continuations and token usage. `--dry` assembles the request and prints it **without sending and without needing a key**.
- `node tracker.js guide-gen <appid>` runs the whole pipeline; `--dry-run` prints the assembled prompt and the landing plan without sending anything. It confirms before spending unless you pass `--yes`, and takes `--effort low|medium|high`. Every refusal reason is raised up front in `planGuide()` — never halfway through, after you have paid.
- **`--overwrite` regenerates over an existing guide.** Without it a registered appid is refused, and the refusal says what to type instead. Three rules are load-bearing: the backup is a *precondition* (it fails ⇒ nothing is written); `landToNotion` deletes exactly the blocks the backup returned rather than re-reading the page, so nothing can be deleted that was not captured; and **overwrite writes back to the guide's own backend** — changing backend is `guide-to-notion`'s job.
  - **What overwriting costs the user:** achievement checkboxes are reconstructed exactly from the database by `computeCheckedKeys`, but **sub-step boxes are not** — they match no achievement, so a hand-ticked box comes back unticked. That is the only irreversible loss in the operation, which is why it is computed from the *old* guide alone and shown before the spend.
  - **The Dashboard offers the same thing on the same terms.** ♻ 重写 appears only when AI is configured and the game has achievements; 生成 vs 重写 are mutually exclusive by construction. **The GUI gate is not allowed to be looser than the CLI's** — `previewGuideRewrite` runs the same `overwritePreflight` but returns **numbers, not a formatted sentence**: the shared thing is the computation, not the wording.
- **`--only` rewrites part of a guide instead of all of it.** `guide-gen <appid> --only <selector> [--note "…"]`; see the `lib/guidescope.js` and `lib/guidepatch.js` rows. It exists because a full rewrite discards every hand-edited passage and every hand-ticked sub-step box, and re-rolls the dice on the parts that were already right. Selectors are computed, not parsed by a model: `rare[:pct]` (`RARE_PCT`, imported by `rarityTag` so the two cannot disagree), `locked`, `section:<heading>` (local only), or a name/`api_name` list. **That set is exactly what the Dashboard dialog offers**, on the rule that a selector which cannot be drawn as a button is telling you something about the selector; `test/guidepatch.test.js` pins that the removed ones are *unrecognised* rather than merely absent.
- `node tracker.js guide-lint [appid]` runs the linter over real guides (read-only). `lintAllGuides` is the network half — the pure/network split mirrors `matchAchievements` vs `checkboxSync`. Steam unlock state is **opt-in** via `--checked`: "unlocked but unticked" is `checkbox-sync`'s job rather than a guide-quality defect, so reporting it by default would bury the content problems.
- **Cost accounting deliberately stops at model tokens.** Search-tool billing is unmeasured, so the search count is reported as a count and never folded into the dollar figure, and a model with no price-table entry reports `null` rather than `$0.00`.

Design rationale for the guide pipeline is in [docs/ai-guide-writing.md](docs/ai-guide-writing.md); self-update rationale is in [docs/self-update.md](docs/self-update.md). **Read those before redesigning either** — they record which alternatives were excluded and why.


## Working on this efficiently

1. **Bulk repetitive external calls are disproportionately expensive.** Notion has no batch-update API, so "add one line to forty pages" is forty round trips — and each one carries the whole conversation history. Before starting that kind of job, say roughly how many calls it will take and offer to do it in a fresh session.
2. **Rule of thumb for a fresh session:** if the content to read/write clearly exceeds what's already in context, or the task is purely repetitive and needs no history, suggest starting clean. Small one-off edits are fine inline.
3. **Verification beats assumption.** A successful tool call does not mean the content is right — see the Notion page-ID and documentation-drift pitfalls above. Re-read results after bulk writes or overwrites, and prefer a read-only preview (`--dry-run`, a SELECT) before anything that writes outside this repo.
