# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Steam achievement auto-tracker, running **entirely locally**: SQLite data store + Node CLI + a local HTTP server for the HTML Dashboard. Tracks achievement completion across the user's whole Steam library.

User-facing docs live in `docs/` (`configuration.md`, `data.md`, `guides.md`). `README.md` covers **setup and everyday use** — including "What runs when", the trigger/cadence table for the automatic jobs, since knowing what the tool does on its own is part of using it day to day. Reference material (every config option, the data model, how matching works) goes in `docs/`. Task-scoped guides for specific jobs are in `.claude/skills/`.

## Stack constraints

- **The runtime still has zero npm dependencies** — `dependencies: {}`, no root `node_modules`, Node built-ins only: `node:sqlite` for storage, global `fetch` for HTTP, `node:http` for the server, `node:test` for tests. **"No install step" is still true and still worth keeping**, because it is what makes `git clone && node tracker.js` work and what keeps the packaged build's `extraResources` an allow-list of plain files.
- **The blanket "never add a dependency" rule was lifted 2026-08-16** (owner's call). It was doing two jobs and only one of them was earning its keep: keeping the *runtime* free of install steps (good, kept) and forbidding npm as a *build-time tool* (not actually necessary). The font under `assets/fonts/` came from `npm install @fontsource-variable/noto-sans-sc`, and then **the files were committed and the package thrown away** — npm was the delivery mechanism, not a dependency. Prefer that shape: fetch with npm, vendor the artefact, keep the runtime clean. A real runtime dependency is now *allowed* but still needs an argument.
- **"Offline-only" was never true and should not be quoted as a constraint.** The Dashboard loads 167 capsule images per page from `cdn.akamai.steamstatic.com`, and has for as long as the gallery has existed. What is genuinely local is the *data* (SQLite, no telemetry, server bound to 127.0.0.1). Say that instead.
- Requires **Node 24+** (`node:sqlite` availability).
- ES modules (`"type": "module"`).

## Development workflow

```bash
node tracker.js <command>                # everything is a subcommand; see tracker.js header or `node tracker.js help`
node --test --test-reporter=dot          # test suite — 663 tests in 40 lines
node --check lib/foo.js                  # syntax check (silent on success)
```

**Run the tests with `--test-reporter=dot`.** The default `spec` reporter prints a line per
test — ~600 lines of green ticks to say what `dot` says in six, and the one line that matters
gets buried in them. On a failure `dot` still prints the whole `Failed tests:` block: test
name, message, stack, and the actual/expected diff. Nothing diagnostic is lost.

**What it does not print is a summary line.** There is no `tests 541 / pass 541 / fail 0`
tail — `dot` emits the dots and stops, so **the green signal is the exit code plus the absence
of an `X`**, not a sentence. Two consequences. Do not pipe it through `tail` and then report
"all tests pass" because nothing looked wrong: `| tail -4` on a red run shows dots and hides
the failure block that was printed above them. And when a count is what you actually want —
"did the suite grow?" — use the default reporter for that run rather than counting dots.

Commit messages are Chinese or English, whichever suits the change. This is settled — don't raise it.

There is no build, no push, no deploy. Editing a file and re-running the command is the whole loop. `serve` does not hot-reload — restart it after changing `lib/` (`Dashboard.html` and `lib/rpc.js` are re-read per request, so a browser refresh picks those up).

| ↳ what `effort` trades away, measured by reading the prose rather than counting it | A same-input A/B on Return of the Obra Dinn (16 achievements, one shard, back to back): `high` 280 s / 5 searches / 1643 chars, `low` **35 s** / 2 searches / 1633 chars. **Every automatic number says the 8× was free.** Total prose: equal. The only thing that surfaced it was reading both guides end to end |

| ↳ what's structural | Three things are impossible-by-construction rather than checked: the model only ever writes `- [ ]` (ticking is `computeCheckedKeys` against the DB, and unlock state is never sent to the model); the `# 游戏名` / `appid:` header is written **by the program and any model-written one is stripped** (a mis-transcribed appid would register the guide against a *different game*, silently); drafts land in `guides/.drafts/`, which `syncGuidesFromMarkdown` cannot see because it is `readdirSync` (non-recursive) + `.md` only — verified against the source, and pinned by a test that runs the real discovery function over a draft |

The exemption is per *name*, not per achievement — a Chinese collision with a unique English name still ticks fine (9 of the 12 collision games are that shape), and over-exempting would hide real defects |
| ↳ the second exemption: a collided name whose Steam description is *empty* | `splitFindings` now also routes `ambiguous-empty-description` to `expected`, and the test of whether a finding belongs there is sharp: **is there any action, by anyone, that would clear it?** Quoting the verbatim description is the only handle that separates two same-named achievements, and for these Steam returns an empty string — so no rewrite, no config change and no guide edit can ever satisfy it. Blocking on it threw away a **complete** guide: measured on KINGDOM HEARTS -HD 1.5+2.5 ReMIX- (a four-game compilation, so KH1 / Re:CoM / KH2 / BbS each ship their own `Proud Player`, `Hero of the Coliseum`, `Treasure Hunter` — 16 names collide, 15 achievements have no description), where a 197/197-covered draft was refused while its own message read 「不是攻略的错」. **The flag marking this was already being computed and nothing read it** — `fixable: Boolean(d.description)` was set in `guidelint.js` and referenced only by a test asserting it was set, which is how the contradiction survived: the knowledge existed, the wiring didn't. The fix splits the finding into **two codes** rather than reading that boolean, because "can this be recovered from" is dispatched on `code` everywhere else in this codebase (`MODEL_FIXABLE`, `splitFindings`, `CLI_HINTS`), and a boolean only one rule sets is a second mechanism answering the same question. `ambiguous-no-description` (description exists, guide didn't quote it) **stays blocking and stays fed back** — that one a rewrite genuinely fixes, and it is the only handle same-name achievements have. Note this exemption deliberately does *not* consult `unnameable`, unlike the `checked-mismatch` one: that rule fires for every achievement so it needs the gate, while this rule's own precondition already includes the collision. Reporting is where the work went, since **not blocking must not become not mentioning**: those boxes will never auto-tick, so the CLI lists the names and the Dashboard's *success* bar carries them (`unsyncable`) — without that, "15 boxes that never move" is something the user discovers months later and reads as a broken sync. | ↳ difficulty signal | Steam's `GetGlobalAchievementPercentagesForApp` (**no API key**) gives each achievement's global unlock rate, and it is fed into the prompt as `🔴 全球仅 1.1% —— 这类要写深` / `⚪ 64.5% —— 一两句带过`. Without it the model can't tell hard from trivial and spreads effort evenly. Measured on 部落幸存者: 1.1% to 64.5%, a 60× spread. Soft — if Steam won't answer, generation proceeds with no rarity text at all (mentioning the scheme with no data behind it only confuses the model) |
| ↳ **round 1 writes the shards concurrently** (`ai.concurrency`, default 3) | The shards have no ordering dependency — each is handed a disjoint, explicitly numbered achievement range — so they queued only because *one session is one chain*. Each shard now gets its own session and they run in a bounded pool, turning round 1 from "the sum of the shards" into "the slowest shard". Verified against the live endpoint: three concurrent requests, no 429, and the pipeline's own tests pin the overlap directly, because **段数 / 请求数 / 攻略内容 all stay identical — the only difference is wall-clock**, so reverting the pool to a `for` loop would otherwise break nothing. Four things had to move with it. **(1) Splitting can no longer touch a shared array**: `chunks.splice(i, 1, a, b)` was safe when one loop walked it and is a data race now — a shard halving itself would renumber the shards already in flight, silently, corrupting prompt numbering, failure reports and the next round's rewrite targets. Each shard splits inside its own slot and the flat list is rebuilt afterwards, ordered by `(shard, sub)` so it never depends on who finished first. **(2) Failure positions are computed after the pool, not at throw time** — the old code could record "shard 3" safely because splits only happened at or after the current index and the loop only moved forward; neither holds now. **(3) Whichever error surfaces must be the lowest shard index, not the first rejection** — a bad key fails every in-flight request and which one rejects first is down to network jitter, so "first" means the same input reports different causes on different runs. **(4) Usage is summed across sessions**; reporting only the first would swallow most of the run's tokens, and that number is the one thing that reconciles against a provider bill. Rewrite rounds stay sequential on purpose: they are usually one or two shards, and a split shard shares its parent's session, so running them concurrently would have two requests writing one `messages` array |
| ↳ verified on a real run, and it hit the dangerous path by itself | Raft (104 achievements, 3 shards, concurrency 3, 2026-08-18) through the production path — real `planGuide`, real unlock state, mechanical ticking, lint, landed in Notion and read back: **ok, one round, zero rewrites, 104/104 checkboxes, 51 ticked against Steam's 51**. Instrumented at `provider.send`: **peak 3 in flight, 650 s wall against 1192 s of summed request time — 1.83×**. The valuable part is that shard 3 hit `max_tokens` and **split at 375 s, after the other two shards had already finished** — precisely the case the `shardChunks` redesign exists for, since the old `chunks.splice(i, 1, a, b)` would have renumbered shards that were no longer running and corrupted nothing visibly. It came out correct, so that design is now *measured* rather than argued. **It also explains why 1.83× rather than ~3×**: the two halves of a split shard run sequentially, sharing the parent's session, and they run as a tail *after* everything else — without the split this run would have been ~375 s wall / ~932 s summed, i.e. **2.5×**. One split costs more speedup than anything else in the system. Lifting that would mean giving each half its own session, which throws away context exactly where it is most needed (adjacent halves are the pair most likely to repeat each other) — deliberately not done |
| ↳ what the shared session was actually buying, and how it is paid for now | Cross-shard visibility bought exactly two things. **Duplicate achievements** were never really its doing — each shard's prompt names its own numbered range and first/last achievement, so disjointness is structural. **Duplicate section headings** were: shards 1 and 2 both covering 主线 will now each open `## 主线`. ### The frontend ↔ backend contract

`Dashboard.html` makes **22** calls shaped like `rpc.withSuccessHandler(fn).withFailureHandler(fn).method(args)`, served by `lib/rpc.js`. (This said 12 for a while, then 17 — and 17 was *already* wrong before `previewGuidePatch` was added, so it has now drifted twice, exactly like the test-file count below. **Count it, don't trust it**, and count the chain's entry point rather than its tail: `withSuccessHandler(` appears once per chain, while grepping method names sweeps in `getElementById` and misses any chain whose method sits far from the handler.) **Keep the contract:** a method that returns `{error: '...'}` is a *successful* call (the frontend inspects `result.error` itself); only network/thrown failures reach the failure handler. Adding a Dashboard method means adding it to `lib/api.js` — `rpc.js` proxies any name and needs no changes.

`Setup.html` uses the same `/api/<method>` contract via a plain `fetch`, not `rpc.js` (no need for the shim's sync-status polling). Its methods — `completeSetup`, `getSetupStatus`, `getSettings`, `saveNotionConfig`, `listNotionParents`, `createNotionGuideDb`, `repairNotionGuideDb` — are (bar the last) the only ones in `lib/api.js` that mutate `config`/`steam` in place rather than only touching `db`. `repairNotionGuideDb` is the odd one out and worth knowing about: it touches no local state at all, it writes to the **user's Notion database** (appending missing status options), which is why it is only ever reached from a button the user pressed and never from the save path. (`createNotionGuideDb` saves the new database's ID itself rather than handing it back for the page to submit later: the database already exists by then, and a user who forgets to press save is left with an orphan database in Notion and a tool that says Notion isn't configured.) That is required because `SteamClient` copies `steamApiKey`/`steamId` into instance fields at construction (`lib/steam.js`), so writing `config.json` alone leaves the running process unusable until restart. `NotionClient` is built fresh at each call site, so updating `config.notion` is enough there. Any future path that accepts credentials at runtime hits the same trap.

**Blank secret means "keep", never "clear".** Both `completeSetup` (API key) and `saveNotionConfig` (integration secret) treat an empty field as *unchanged*, because the settings page pre-fills the non-secret values: without that rule, opening settings to change a SteamID and pressing save would wipe the Notion token. `Setup.html` also compares the DB id against its loaded value and skips `saveNotionConfig` entirely when nothing Notion-related changed, so an unrelated edit never blocks on a Notion round-trip or fails because Notion happens to be down. Clearing a secret is deliberately a `config.json` edit.

## Data model (`games` table)

`appid` (PK) / `name` / `achieved` / `total` / `has_achievements` / `rate` / `status` / `sync_locked` / `favorite` / `priority` / `family` / `new_ach_date` / `updated_at` / `last_played` / `stats_checked_at` / `perfect_lost_date` / `ach_added_date`

- `status`: `''` (normal), `'Unvetted'` (Steam Profile Features Limited), `'Manual'` (hand-maintained).
- **`Manual` is the 🔒 lock in the UI — same column, different vocabulary** (renamed 2026-08-13). The word never described what it does; locking a row does. Do not rename the column to match: `status` values reach CSV import/export and the user's spreadsheet, so the storage name is a compatibility surface. **`addGame` no longer forces `Manual`** either — it used to set `status:'Manual', syncLocked:1` on every hand-added row, which is backwards for the commonest reason to add one: a family-shared game *is* the case where Steam returns real progress, so locking it freezes the numbers at the moment of adding. New rows sync normally; the lock is one click away if Steam turns out to have nothing.
- `has_achievements = 0` replaces the old `'N/A'` string in the numeric total column. `NULL` means "not synced yet".
- **`sync_locked` is what the sync actually checks**, not `status`. They are separate columns because "skip the daily achievement sync" and "pin this row's label against Steam re-classifying it Unvetted" are different wishes — conflate them and you cannot have one without the other. The Dashboard moves both together (`setManualStatus` sets both); diverge them by hand when you actually want to.
- `family` is purely informational and never affects sync behavior. It exists because "not in `GetOwnedGames`" and "should skip achievement sync" are two *different* facts.
- **`last_played` / `stats_checked_at` are the sampling state for phase 2** (see below). `last_played` is `rtime_last_played` as of the last *successful* read; `stats_checked_at` is when that read happened. `updated_at` cannot substitute — it moves on any row change, including a ♥ toggle from the Dashboard, so it can't answer "when did we last ask Steam". Written by `markStatsChecked()`, never on a `retry`.
- **`perfect_lost_date` / `ach_added_date` are the 🔔 notifications, and they are this project's *only* deliberate transition detection.** They record "you had this at 100% and the developer added achievements" and "Steam used to say this game had no achievement system, now it does". Both are stamped inside `updateGameStats`, the one moment `prev` is still readable — afterwards a sub-100% row is indistinguishable from one that was never perfect, and `has_achievements` has already been overwritten with `1`. Two guards carry them: `wasPerfect` requires a real numeric baseline (so the first sync of a row can't fire it), and `achAdded` matches **only an explicit `0`**, never `NULL` — `NULL` means "never synced", and treating it as the transition would dump the entire library into the bell on the first full sync. Read the contrast with "Guide page status" below before touching either: that rule forbids transition detection because its question ("what should this page's status be *now*") is answerable from current state; this one requires it because its question ("what changed recently") is not. The cost is accepted and unavoidable — an event observed by a run that fails to write is gone, and an existing database starts with an empty bell because nothing recorded these events before the columns existed. Pinned in `test/notifications.test.js`.
- New columns need `ALTER TABLE`, not just an edit to `SCHEMA`. `SCHEMA` is `CREATE TABLE IF NOT EXISTS` and does nothing to an existing table — `migrate()` in `lib/db.js` walks `ADDED_COLUMNS` against `PRAGMA table_info`. Add to **both** when adding a column.

## Sync behavior

`fullSync` runs three phases in order over the whole library, with no cursor and no runtime cap. Ctrl+C mid-run is safe — each game is committed as it completes, so re-running only redoes work that was in flight.

1. **`syncLibrary`** — new owned games get inserted (with a name lookup); existing *owned* rows get their `Unvetted` stamp refreshed, except `'Manual'` ones. Rows whose appid is **not** in the current `GetOwnedGames` snapshot are left completely untouched — that's the preservation rule (it keys off ownership, not `status`).
2. **`syncAchievementStats`** — refreshes counts for rows with `sync_locked = 0`. A total higher than last time stamps `new_ach_date` (the Dashboard's "new achievements" badge). **Which rows get checked is decided by `selectStatsTargets()` — see "Phase 2 sampling" below.**
3. **`syncAchievementSchema`** — per-achievement detail for games that are new to the `achievements` table or bumped in the last 7 days; skips games at exactly 100% and games with no achievement system.

**`serve` also runs guide discovery on start** (`syncGuides()` in `lib/server.js`, off via `syncGuidesOnServe: false`) — the same work as `node tracker.js guides`. It is deliberately **outside** the `syncStaleHours` gate and needs no Steam credentials: a guide page created minutes after a sync must show its Dashboard link immediately, and gating it on staleness would hide new pages for hours. `fullSync` itself does **not** touch guides — a new Notion page will never be discovered by achievement syncing alone, which is why this hook exists at all. Failures are logged and swallowed; a dead Notion token must not take the Dashboard down with it.

**The three startup jobs are sequenced, not concurrent** (`startupJobs()`). They used to be two fire-and-forget calls; they can't be any more, because each step feeds the next: discovery must finish before the sync knows which guide pages are new, and the tick pass must run after the achievement refresh or it matches against last run's unlock state. Still off the `listen` callback's critical path — the page opens immediately either way.

### Phase 2 sampling — `achieved` and `total` do not change for the same reasons

This is the whole design, and getting it wrong loses data *silently* (a skipped row doesn't error, it just leaves a stale number on the Dashboard forever):

- **`achieved` is a fact about the account.** It cannot change unless you played. Gating on `rtime_last_played` is exactly correct for it.
- **`total` is a fact about the game.** A developer patch adds achievements with zero playtime, which drops a 100% game below 100%. **Gating that on `rtime` is simply wrong**, and was the flaw in the first version of this design.

So `selectStatsTargets()` unions three groups:

1. **played** — `rtime_last_played` exceeds the stored `last_played`. Keeps `achieved` exact.
2. **unowned** — appid absent from the `GetOwnedGames` snapshot (family-shared / delisted / hand-added). No timestamp exists for these, so they are checked every run. Freezing them out would contradict the "a game can vanish from `GetOwnedGames` while `GetPlayerAchievements` keeps working" quirk below.
3. **sweep** — rows overdue for a re-check, capped at `sweepBudget` per run. This is the only thing that catches a retro-added achievement, so **do not remove it as an optimisation.**

Details that are load-bearing:

- **The sweep sorts by *overdue ratio* (`age / itsOwnDeadline`), not by absolute age.** Perfect games expire in 3 days and everything else in 7; sorting by raw age lets an 8-day-old ordinary game jump ahead of a 4-day-old perfect one, which makes the shorter deadline decorative. Pinned in `test/selection.test.js`.
- **`markStatsChecked` is never called on a `retry`.** Recording a rate-limited game as "just checked" would push it to the back of the queue and turn throttling into silent data loss.
- **A row with no baseline (`stats_checked_at IS NULL`) is always checked, uncapped.** The first run after this migration is therefore a full ~160 s sync; every run after is ~8 s. That is intended — there is nothing to compare against until the baseline exists.
- **No `playSnapshot` ⇒ check everything.** `node tracker.js sync` deliberately stays a true full sync; `sync --fast` and the Dashboard's auto-sync opt in by passing `selection`. Keep that escape hatch.
- **Thresholds are targets, not guarantees** — `sweepBudget` binds first. At 40 with the Dashboard opened ~twice daily the cycle lands on the intended 3/7 days; at once daily it stretches to ~5/11.5. Measured, not estimated.

### The 「立即同步」 button

A page refresh only re-reads SQLite — `getDashboardData()` never touches Steam — so the Dashboard has a manual sync button next to the "上次同步" line. It calls `api.startSync()` → `startBackgroundSync()` in `lib/server.js`, **the same function the startup auto-sync uses**. Keep it that way: one function means one concurrency guard, and the guard is the only thing stopping a click that lands during the startup sync from running two `fullSync`es over the same database.

Two deliberate asymmetries with `maybeAutoSync`: the button **ignores `syncStaleHours`** (that gate answers "should we sync unprompted", and a click has already answered it), and it still passes `selection`, so it's the ~8 s sampled sync, not the ~160 s full one. `node tracker.js sync` remains the way to force a true full pass.

Sharing one function is also what gives the button its checkbox ticking for free — the tick pass hangs off `startBackgroundSync`'s completion, so both the startup sync and the button get it without a second call site.

The button owns no progress UI of its own — `lib/rpc.js`'s existing 3-second poll drives its label and disabled state through a `window.onSyncState` hook, alongside the status bar and the post-sync `reloadDashboard()`. That hook fires **before** every branch in the poll handler, because two of those branches (sync failed, user mid-edit) return early; hanging it off the end would strand the button on "同步中..." forever. Same reasoning as `reloadDashboard`: the frontend reflects the server's real sync state rather than tracking its own, so a sync started from the CLI or a second tab greys the button out too.

**`stats.bumped` must stay visible.** It was computed and thrown away on the Dashboard path for a while (only the CLI printed it) — which is backwards, since a retro-added achievement is precisely the change you cannot notice on your own. It now reaches `syncState` → the status bar, and that notice deliberately does **not** auto-dismiss.

There is deliberately no destructive rebuild/reset command. `syncLibrary` reconciles against Steam without discarding rows, and a "wipe and repopulate from `GetOwnedGames`" helper would silently drop every family-shared and manually-maintained row — data the API cannot give back.

## Steam API quirks

These are verified and hard-won — don't re-derive them, and don't "simplify" the handling:

- `GetPlayerAchievements` HTTP **400** = this game genuinely has no stats for this account. A normal signal, **not** an error, do not retry.
- HTTP **429** = real rate limiting, retry next cycle. Everything else non-200 is also treated as transient.
- HTTP **403** `"Profile is not public"` can come back for *one specific game* even when the profile is public — a per-game "Game Details" privacy toggle on Steam's side. Falls in the retry bucket, but retrying never succeeds until the setting changes on Steam.
- `appdetails`'s `name` field **ignores the `l=` param** (Steam bug) — Chinese names require scraping the store page HTML (`fetchAppNameFromStorePage`), with age-verification cookies and a deliberately loose regex (the class attribute can carry multiple classes).
- Determining whether an owned appid is currently Unvetted **requires two `GetOwnedGames` calls** (`skip_unvetted_apps=false` minus `=true`). A single plain call silently returns the vetted-only view. `fetchOwnedGamesWithUnvettedFlag()` is the only correct way to ask.
- `GetOwnedGames` omits free games unless `include_played_free_games=true` (already set).
- A game can disappear from `GetOwnedGames` while `GetPlayerAchievements` keeps returning its full permanent stats. "Not owned" ≠ "no achievement data" — check achievements directly before concluding a game can't be tracked.
- Family Sharing achievements are recorded per **playing** account. If a shared game is actually played on someone else's account, your `steamId` will correctly and permanently show 0 on it. Not a bug to chase.

## Guide checkbox matching — do not loosen this

Matching an unlocked achievement to a guide checkbox is **exact equality against extracted title candidate segments**. Never substring, never prefix. Three rounds of false positives produced this rule:

1. an achievement name appearing inside an unrelated achievement's *description*;
2. a short achievement name being a strict *prefix* of a different, harder achievement's name — which mis-ticked the harder one once the short one's own box was already checked; and
3. **two achievements in the same game with genuinely identical names.** Exact matching cannot fix this one: the unlocked twin's box gets ticked, leaves the candidate pool, and the same name then matches the *other*, still-unearned box. `findAmbiguousNames()` therefore refuses any name shared by several achievements unless *all* of them are unlocked, and logs the skip rather than staying silent. This is not rare — a 310-game library had 12 such collisions across 11 games.

`extractTitleCandidates()` splits checkbox text into candidates (by line, then by colon/dash, plus the `中文名(English Name)` pattern, plus a trailing-punctuation-stripped variant of each) and requires the achievement name to *equal* one of them. Adding a new candidate-extraction rule is fine; weakening the equality check or removing the ambiguity gate is not.

Two rules about *how* to add one, both learned the hard way (2026-08-10):

- **Append, never replace.** The trailing-punctuation rule adds `秘密食材` alongside `秘密食材。` rather than rewriting it — achievements like 「白手起家。」 and 「胜利！」 have punctuation in their real names, so replacing would turn working matches into misses. Stripped variants go last so exact ones win first.
- **Normalize the candidate side only, never the `defs` name index.** Adding stripped keys to the index would collide `X` with `X。`, and the ambiguity gate would then skip *both*. That trades "fails to tick" for "ticks the wrong one" — backwards from this project's whole bias.

**The gate closes per name, not per achievement** — a colliding Chinese name does not disqualify a unique English one. See "Same-name collisions" under Current state for why (most collisions are localization bugs) and what that does *not* license. `test/matching.test.js` pins all three failure modes — run `node --test` after touching `lib/guides.js`.

**The one way out of case 3 is the description.** `matchAchievements` runs two passes: ambiguous names first, resolvable *only* by the checkbox quoting the achievement's full description when that description is unique in the game (then the box is unambiguously about that achievement); then exact name matching for everything else. Description-first is deliberate — it is the more precise signal, so it claims its box before name matching could take it. This is why the guide-writing convention is `**name**` / verbatim official description / your own notes, and why paraphrasing the description has a real cost. See `.claude/skills/achievement-guide-writing/SKILL.md`.

The design deliberately prefers a missed checkbox over a wrong one.

**Always `checkbox-sync --dry-run` before a manual full run.** Ticking a Notion box can't be undone automatically, and failure mode 3 above was caught by a dry run before it wrote anything. Sync only ever ticks, never unticks, so it cannot repair its own mistakes.

### Automatic checkbox ticking (the one unattended write path)

`serve` and the 立即同步 button both run a tick pass after the achievement sync (`runCheckboxSync` in `lib/server.js`, off via `checkboxSyncOnServe: false`). **This is the only place in the project that writes to Notion without a dry-run in front of it**, so every narrowing below is load-bearing — do not widen one without replacing the safety it provided:

- **`appids` whitelist, not the full candidate set.** Only rows whose `achieved`/`total` actually moved this run (`stats.changedAppids`, fed by the new `gained` flag out of `updateGameStats`) plus guide pages registered for the first time this run. A full pass is ~40 games × (1 Steam call + 1 Notion page read + 350 ms) on *every* Dashboard open, nearly always to find nothing. **`appids: []` means "run nothing", never "no filter"** — writing `appids?.length ? … : everything` turns the common case (nothing changed) into a full scan and silently undoes the whole design. Pinned in `test/checkbox-selection.test.js`.
- **`gained` is false when there's no baseline.** On the first sync of a row, `achieved` goes `NULL → n`; counting that as "gained" would make the entire library a candidate on the run where that's most expensive.
- **Cascade off by default here** (`checkboxSyncOnServeCascade`), unlike the CLI. The cascade is the one deliberately over-ticking path, and this route has no human gate in front of it.
- **A game that hit 100% *this run* is still visited.** The 100%-skip used to be coupled to `cascade` in one expression; decoupling it was a real bug fix, not a tidy-up. With cascade off, the achievement that *completes* a game could never be ticked automatically — by the next run the game is at 100% and is skipped, forever. The `achievementsFor(...).length > 0` guard still applies (the 55/55 no-schema case), so this costs nothing on the games that rationale was about.
- **Failures are soft and separate.** Errors go to `syncState.tickError`, never `syncState.error`. A dead Notion token must not present as "achievement sync failed" when the achievement data synced fine.

Review is `sync_log` + `node tracker.js log` — the auto path writes the same rows the CLI does. The Dashboard also raises a notice naming the first few ticks, and like the `bumped` notice it **does not auto-dismiss**: it is reporting a write to the user's own notes.

### Guide page status (`Done` ⇄ `Staged`)

The Notion guide page's `Status` property is kept in step with completion, **both directions** — `syncGuideStatuses` in `lib/guides.js`, run by `node tracker.js guide-status` and, on the serve path, right after the tick pass (`guideStatusOnServe`).

- 100% and not `Done` → **`Done`**.
- Below 100% and currently `Done` → **`Staged`**. Effectively always a developer patch adding achievements, which is the one kind of change that happens without you playing.

Load-bearing details:

- **It converges on state; it does not watch for the transition.** Crossing 100% (in either direction) exists only for the instant `updateGameStats` writes it. Any run that observes it but cannot write — a CLI `sync` on a box with no Notion token, an interrupted process, an expired token — loses it permanently, because every later run sees the same value on both sides and can infer nothing. The rules are therefore stated over current state, which is idempotent, self-healing and re-runnable. **Do not "optimise" this into transition detection.** (The 🔔 columns `perfect_lost_date` / `ach_added_date` *do* detect transitions, and that is not a contradiction — they answer "what changed recently", which current state genuinely cannot answer, and they pay the matching price: a missed observation is lost forever. This rule applies where current state *is* a sufficient answer, and there it always wins.) Measured proof: the one page that needed demoting (Supermarket Together, 28/51) has `new_ach_date = NULL`, so a rule gated on "we saw `total` grow" would never have fired for it at all.
- Convergence is nearly free because `queryGuideDatabase` already pages through the whole database; it just used to throw the `Status` property away. Cost is ~3 API calls per run total, not per game.
- **The two directions are deliberately asymmetric in how aggressive they are.** Promotion overwrites *everything* except `Done`, `Differed` included — completion beats a hand-set workflow state. Demotion touches *only* `Done`. A sub-100% page sitting at `Paused` / `In progress` / `Not started` / `Differed` is a state you chose, and rewriting it on every Dashboard open would put you and the tool in a loop overwriting each other. Pinned in `test/guide-status.test.js`.
- The two rules are mutually exclusive by construction (`achieved >= total` vs `<`), so a page can never satisfy both and oscillate.
- **A `total` of `NULL` is not "dropped below 100%".** `markNoAchievements` clears `total` when Steam says a game has no stats, and rate-limits/403s take the `retry` path and write nothing at all — so the `total > 0` guard is what stops a Steam hiccup from demoting a finished page.
- **The property's *type* is read, never assumed.** Notion's `status` and `select` are different property types whose write payloads differ (`{status:{name}}` vs `{select:{name}}`), and the wrong one is rejected. `fetchGuideStatusSchema` reads name, type and options; **both** `Done` and `Staged` are validated up front, so a database missing one fails with a readable message instead of a Notion 400 halfway through.
- Notion-kind guides only — local markdown has no status property. Failures are soft and land in `syncState.statusError`; `syncGuideStatuses` returns `applied` (writes that actually succeeded) so callers report direction without parsing log text.

Ordering matters: status runs **after** the tick pass, so a game that just completed gets its last boxes ticked before the page is marked done. Marking a page `Done` over unticked boxes is the wrong end state.

### Nested sub-step checkboxes (`collectSubStepTicks`)

Guides nest sub-steps under an achievement — individual shrines, individual techniques, one line per side-quest. Two things were true and both were wrong:

1. **The backends disagreed.** `loadTodos`'s regex is `/^\s*[-*]\s*\[/`, so local markdown always read indented boxes; `fetchAllToDoBlocks` pushed a `to_do` and `continue`d, so Notion never descended into one. Identical guide content behaved differently by backend. Notion now recurses, and both backends set `parent` on each todo (Notion: the enclosing to-do's block id; markdown: inferred from an indentation stack). Containers like `toggle` pass `parent` through unchanged — a checkbox inside a toggle inside an achievement is still that achievement's sub-step.
2. **Sub-steps could never be auto-ticked.** They aren't achievements; Steam has no data for them and their names match nothing. Name matching can't reach them, ever.

So `collectSubStepTicks` ticks them by **inheritance**: if the parent achievement is known unlocked, its nested boxes get ticked. Evidence of "known unlocked" is only ever (a) a match made this run, or (b) an already-ticked box that `resolveTodoToAchievement` maps to a uniquely-identified, genuinely unlocked achievement. Without (b) the feature would be useless — most achievements were ticked in earlier runs.

**This is the one place in the codebase that prefers over-ticking, and it is deliberately inconsistent with the rule above.** The assumption "parent unlocked ⇒ every listed sub-step was done" holds for *all-of* achievements ("fail every technique at least once") and **fails for *any-of* achievements** — "reach an ending" with nine endings listed underneath would falsely tick eight. The code cannot distinguish them. Mitigations, all of which should stay: cascade is skippable with `--no-cascade`, every cascaded tick is logged as `已勾选子步骤(父成就已解锁)` so `sync_log` can be re-read afterwards, and `--dry-run` lists them separately. If you write a guide whose sub-steps are alternatives rather than requirements, don't nest them under the achievement.

Two consequences elsewhere. `checkboxSync` will consider a 100%-complete game when cascade is on — all achievements unlocked is exactly when sub-steps are most likely ticked-worthy — **but only if that game has rows in `achievements`**, because recognising a parent needs `resolveTodoToAchievement`, which needs names/descriptions. `syncAchievementSchema` deliberately skips games at exactly 100%, and measured against the real database **55 of 55** guide-having perfect games have no schema at all. Widening the filter unconditionally cost 55 wasted page reads plus 55 Steam calls per run and could never tick anything; the `achievementsFor(...).length > 0` guard keeps the candidate count at 42 and starts including a perfect game automatically if its schema ever gets synced. Second, `auditGuideTicks` ignores ticked sub-step boxes that resolve to no achievement — counting them as "undetermined" would drown the one number that measures real audit coverage. A nested box that *does* resolve to an achievement is still audited normally.

## Reverse lookup (the `audit` command)

`checkbox-sync` asks "where does this achievement go?"; `audit` asks the opposite — "which achievement is this ticked box about, and is it actually unlocked?" That's `resolveTodoToAchievement()`, and it accepts only two unambiguous handles: the achievement's full description when unique in the game, or a name that maps to exactly one achievement. Anything else is reported as undetermined rather than guessed, and **the undetermined count is always printed** — "0 wrong" would otherwise imply coverage the audit doesn't have.

**Never map by description *prefix*.** A first draft of this matched the first 14 characters, which collapses tiered achievement families ("deal 100/500/1000 damage", "fill in every page of X's report card"): a correctly-ticked easy tier gets attributed to its locked harder sibling. On real data that produced 4 false findings out of 5 — the same bug class as the name-prefix one above, in a different disguise. `test/matching.test.js` pins the tiered-family case.

## Don't cry wolf in the log

When the sync can't act, think about whether that's *actionable* before logging it. Ambiguous-name groups whose boxes are already correctly ticked used to log "needs manual review" on every single run — a permanent false alarm, which is worse than no alarm because it trains you to ignore the log. `nameGroupAlreadySatisfied()` now silences those, and they speak up again if a second same-named achievement gets unlocked without its box ticked.

That helper uses loose substring matching, which is banned in the tick path. The distinction is intentional and commented at the call site: **it decides whether to print a line, never whether to write.** Getting it wrong costs one log line; getting the tick path wrong corrupts the user's notes. Keep new heuristics on the correct side of that line.

## Known pitfalls

- **The 🎮 recently-played badge can never appear on a family-shared / delisted row.** It derives from `last_played`, which comes from `GetOwnedGames`; rows absent from that response have no timestamp at all and Steam offers no other source. Looks like a bug, isn't one.
- **Games with `has_achievements = 0` are retried**, not permanently excluded. They get re-marked if Steam still says no stats; harmless. `GetOwnedGames`'s `has_community_visible_stats` flag predicts this set exactly (verified 26/26 on the real library) and skipping them would save 26 calls per full pass — **this was considered and deliberately rejected.** The moment a game adds achievements is the moment that flag flips, and by then we'd have stopped asking. Trading a permanent blind spot for ~11 s is a bad deal.
- **The twenty-five test files cover different failure classes.** (**Count them, don't trust this number** — `ls test/*.test.js | wc -l`. It read "fifteen" while the list below described fourteen, then "sixteen" describing fifteen, then sat at "sixteen" while there were eighteen and the list described sixteen: the count has now drifted **four** separate times, each by someone editing the sentence instead of running the command — the fourth was 2026-08-18, when it sat at "twenty" against 24 files while the test total said 640 against 663. Run the command.) `matching.test.js` protects the user's *notes* (a wrong tick corrupts a guide) — and, since the Dashboard started showing guide text per achievement, the *display* side of the same reverse lookup (`mapAchievementGuides`), where the failure is a solution filed under the wrong achievement rather than a wrong tick. One of those cases shipped green and empty on the first run: "an achievement mentioned twice keeps the first" passed because the second checkbox never resolved at all, so it pinned nothing. It now asserts the second one resolves *before* asserting first-wins — the same silently-passing shape this file's other entries keep producing, caught the same way, by mutation. `selection.test.js` protects the user's *data* (a skipped row silently freezes a number). `checkbox-selection.test.js` protects *which guide pages get opened* — too wide burns dozens of Notion/Steam calls per Dashboard open, too narrow silently never ticks. `guide-status.test.js` protects *idempotency* — the status pass runs on every Dashboard open, so a rule that isn't a no-op the second time means repeated writes to Notion. It also pins the **network** half, which was an outright gap until 2026-08-14: `syncGuideStatuses`'s up-front "which option is missing" check could be deleted whole and the entire suite stayed green (found by mutation, not by reading). Losing it doesn't error — it degrades into a per-page Notion 400 that this path's own `catch` files into `sync_log` before moving on, on a route that runs unattended on every Dashboard open, so the visible symptom is a log quietly filling with an unreadable 400. That is the same failure the `Paused` report ran into from the other side, and the create path (`planNotionTarget`) had been pinned against it all along. Both directions are pinned, because a check hard-wired to always throw would satisfy a refusal-only test while making a correctly configured database unusable. `guidelint.test.js` protects against **false positives** — the linter is meant to gate AI-generated guides, and a rule that cries wolf either blocks good guides or trains you to ignore the report; its cases are mostly "looks like it should be reported, and must not be" (a same-name achievement's box exists, sub-steps aren't achievements, an empty Steam description isn't the guide's fault — and since 2026-08-17 that case carries its own code, `ambiguous-empty-description`, because the old shared code let an unfixable finding block a complete guide; the test that used to assert the dead `fixable` flag now asserts the code, which is the thing production actually dispatches on). `ai.test.js` protects *the bill and the "it looked like it worked" failures* — usage double-counting (nothing errors, the number is just always high), a silent `$0.00` for an unpriced model, a rate-limited search read as an empty result, a truncated guide read as a finished one, **and the mirror-image case that actually shipped — a successful `web_fetch` read as a tool error, because its success payload is an object where `web_search`'s is an array.** `guidegen.test.js` protects *the gates* — that an unvalidated draft can never be discovered and registered (which would hand `checkbox-sync` an unverified guide to tick the user's notes from), that the `appid:` line is ours and not the model's, that `checked-mismatch` is never fed back, that an unfixable same-name finding neither blocks landing nor reaches the model while the *fixable* variant still does both, and that the same-name exemption is per name rather than per achievement. `ai-gemini.test.js` protects *the things a wrong guess would break silently* — that provider was written from memory with no docs available, so it pins only the failures that don't announce themselves: reasoning parts leaking into guide prose, usage fields mapped wrong, an unrecognised finish reason passing as success. Anything a bad guess would make **error loudly** (endpoint, model name, tool name) is deliberately untested and made configurable instead — the first real call is a better check than a test asserting my memory back to me. `ai-deepseek.test.js` protects *the one property that matters most about that provider* — that `canSearch: false` propagates all the way through (prompt swaps to the no-research variant, the result carries the flag), because a guide silently written without research is exactly the quality difference the admission rule exists to prevent. `notionblocks.test.js` protects *content survival through a format change* — the converter's failure mode is losing a line or splitting an achievement into three blocks, and both produce a page that looks fine. `guidegen-notion.test.js` protects *the user's existing Notion pages and the "it wrote successfully" illusion* — that a page with content is never appended to, that an adopted empty page keeps its title/status (and its icon *if it has one* — a blank icon slot is filled, which is the one documented exception), and that a failed read-back or an unreadable `appid:` line raises instead of reporting success. `guidemigrate.test.js` protects *the original*: that fidelity mismatches (text changed, count changed, and especially **checked state changed**) actually fail, and that every one of those failures leaves the local file untouched. `guideoverwrite.test.js` protects *the guide you already had*: that overwriting refuses without `--overwrite`, that the backup happens before any write and a failed backup stops the run, that Notion blocks are never deleted without a backup in hand, that overwriting a local guide doesn't silently relocate it to Notion, and that the one genuinely unrecoverable loss — a hand-ticked sub-step box — is named **before** the spend confirmation. It caught a real defect on its first run: `coverageOf` read `api_name` off `resolveTodoToAchievement`'s `{def, via}` wrapper instead of off `def`, which would have reported *every* achievement as lost on *every* overwrite. `guidepatch.test.js` protects *the bytes the user did not ask to change* — the failure class unique to partial rewrite, and the one with no machine that can notice it afterwards: a guide that lost a hand-edited passage, gained an entry nobody named, or quietly skipped one of the entries that were named **still looks complete**. So nearly every assertion in it is about what did *not* change: after splicing one entry, the remaining lines are compared **line by line for equality** (not "same length", not "looks similar"); the `<details>` block sitting immediately after an achievement must survive, since eating one line too many is a silent deletion; an achievement the model returned without being asked for must be reported *and discarded*, verified by splicing and then asserting the untouched entry is still verbatim; and a **named entry the model failed to return must make the whole run not-ok** — that case is pinned by first asserting `lintGuide` reports *zero* errors for it, which is exactly why it cannot be left to the validator (the skipped achievement's old checkbox is still sitting there, perfectly valid). Also pins that a same-name achievement is **unresolvable by name** rather than guessed, and that a `rare` selector with no rarity data *throws* instead of quietly selecting nothing — an empty selection is indistinguishable from "this game has no hard achievements" while the truth is that Steam did not answer. Pure functions only, no network and no database, deliberately: whether a splice lands in the right place has to be checkable with no key, no provider and no Notion. `notionsetup.test.js` protects *the onboarding path from moving the wall instead of removing it*: that `GUIDE_STATUS_OPTIONS` covers every value `newGuideStatus` and the status convergence can write (a drift check — miss one and that branch is refused by `planNotionTarget` at write time, minutes into a `guide-gen` the user no longer connects to setup), that `createGuideDatabase` verifies by reading back rather than trusting the 200 (Notion demonstrably ignores parts of that payload in silence), and that `searchPages` filters out database rows — unfiltered, the parent picker is 99% the user's own guide pages with the one usable page buried at the bottom. It now also covers `inspectGuideDb` / `probeGuideDbWrite` / `repairGuideDb`, whose sharpest case is the one this codebase has already been bitten by: **a PATCH that returns 200 and changes nothing must be reported as a failure**, since "you pressed the button, it said fixed, and `guide-gen` still refuses" is strictly harder to diagnose than "it couldn't be fixed". Alongside it: a stale option set must never be clobbered rather than appended to, a write probe must not run against a database already known to be misconfigured (don't leave pages in it), and "no status property" must stay a warning rather than an error, or a perfectly usable database gets reported as broken. `notifications.test.js` protects *the two events that get exactly one chance to be noticed* — `updateGameStats` is the last moment the previous values exist, so a wrong predicate there doesn't error, it just leaves the 🔔 permanently empty while the user reads that as "nothing happened". Its cases are mostly the false positives that would make the bell useless in the other direction: a game bumped while *not* at 100% (routine, and crying wolf about it trains you to ignore the bell), and `has_achievements IS NULL` read as the no-achievements→achievements transition (which would dump the whole library into the bell on the first full sync). It also pins that a repeat event refreshes the stamp rather than keeping the first — and that test itself had to be rewritten after failing on its first run for comparing two real writes that landed in the same millisecond. `html-smoke.test.js` protects *the two HTML files, which nothing else touches* — `Dashboard.html` and `Setup.html` are one big string each, so renaming an id or deleting an element **raises nothing**: the reference just resolves to `null` at runtime, or a CSS rule silently stops matching. It is **not a behaviour test** and must not be read as one — there is no DOM in the test runner, so clicks, focus and cascade are still only checked by hand in a browser. (That is now a *choice* rather than a constraint: jsdom or Playwright could be added since the dependency ban was lifted. Nobody has, and the manual-check note stands until someone does.) What it does check is referential integrity (every `getElementById`/`querySelector` target still exists, every CSS type selector still has a tag) plus the rules distilled from bugs actually shipped here — including, since 2026-08-16, five covering the self-hosted font (see the `assets/fonts/` rows): no `required` inside the stepped form (a hidden required control makes the browser refuse to submit with only a console message), `classList.toggle`'s second argument must be Boolean-coerced (`undefined` *flips* instead of clearing), `onSyncState` must never write the sync button's `textContent`, **both pages must carry a global `[hidden] { display: none !important }`** (added 2026-08-14), and — added 2026-08-15 with the UI rebuild — **the two pages' `:root` design-token blocks must match declaration for declaration**, since they are one system stored twice and an undefined variable fails silently rather than loudly. That last one is the same trap as `classList.toggle`, one level down in the stack: the browser's `[hidden] { display: none }` lives in the *user-agent* stylesheet, so any author `display:` outranks it and silently demotes that element's `hidden` attribute to decoration — JS still sets `.hidden = true`, the element still shows, nothing errors. A sweep found three already live: `.gallery { display: grid }` (switch back to table view and the grid stays parked under the table, because `render` early-returns and never repaints `#gallery`), plus `.steps` and `.step-actions` in the setup page, where it put all three wizard buttons on screen at once. A `.step[hidden]` patch was *already* in the file, which is the tell: patching per element is whack-a-mole, and the next `display:` rule opens a fresh hole just as quietly, so the fix is one global rule and the test pins the rule rather than the elements. The sibling check names the specific casualties when that rule goes missing, so whoever deleted it can see what it was holding up. Setup.html also pins that `getSettings` is wrapped in `try`/`catch`: `call` **throws** when the server isn't up yet rather than returning `{error}`, the `if (s.error)` fallback never runs, and `initSteps()` is skipped — which is precisely the packaged-app window where Electron opens the window before the child process is listening. **Every one of its checks was mutation-tested** — deliberately break the thing, confirm the test goes red — because three of them were silently passing at first: two from bad extraction (CSS comments parsed as selectors; markup built in JS strings being invisible to a static-markup-only search) and one from a rule too weak to bite (`\b` treats `-` as a boundary, so looking for class `step` was satisfied by `class="step-title"`). `guidequeue.test.js` protects *tasks not vanishing* — generating a guide takes 2–4 minutes, so "queue three and go do something else" is a real usage pattern, and every failure on that path is silent: a job dropped, a queue wedged after one failure, the same game queued twice and written twice. Its sharpest case is a source assertion, because the wiring it guards (`drainNext` on **both** `.then` and `.catch`) lives in `serve()`'s closure where no unit test can reach it — hang it on `.then` alone and one failed generation stalls everything behind it forever, with no error and no timeout. `tray.test.js` protects *the app staying quittable and the sync still firing* — `launcher/main.js` needs Electron to import, so it too is mostly source assertions, aimed at three reversions that all look correct: `window-all-closed` quitting again (silently undoes background residency, because quitting **is** Electron's default when that listener is absent), the `close` handler losing its `isQuitting` pass-through (`preventDefault` then makes the app impossible to exit), and `api.maybeSync` decaying into `startSync` (which bypasses `syncStaleHours` on purpose, so every window-raise would run a full sync). Its assertions **strip comments before matching**, which is not fastidiousness: the first version of the "is `maybeAutoSync` wired in" check passed against the word appearing in the comment beside the wiring, so deleting the actual code changed nothing. Mutation testing caught that; reading it did not. `selfupdate.test.js` protects *the one component that cannot be fixed by shipping a fix* — a broken updater is already on the user's machine, and the repaired version has to travel through it. Its cases are the three constraints made mechanical: that deletion goes by the manifest and never by a keep-list, that it runs **before** extraction (which is what makes over-deleting self-repairing), that only files are removed and only empty directories pruned, that a missing manifest falls back to overwriting instead of guessing, and that a missing `digest` **refuses** the update rather than skipping verification — the quiet degradation where the update still "succeeds". It also parses the generated PowerShell with `[Parser]::ParseFile` on Windows, because that script runs in a detached process with no console: a template-literal escaping slip there is invisible, and what the user sees is the app quitting and never coming back. **Every assertion in it was mutation-tested**, and that caught one silently-passing check of exactly the kind this file keeps producing — `-PathType Leaf` was asserted against the whole script, so deleting the guard from the delete loop still matched the copy on the manifest-existence check. Same failure as the comment-satisfied assertion in `tray.test.js`, wearing a different disguise: the fix is to slice to the block you mean before matching. `version.test.js` protects *the only version number a user can read off their own disk* — the repo writes one in four places (root `package.json`, `launcher/package.json`, and twice inside `launcher/package-lock.json`) and **only the launcher's has a runtime reader**, so the other three can sit wrong through release after release with nothing erroring. The root value is the one that ships, as `resources/tracker/package.json`; while it ran on its own counter (tracker 2.x vs app 1.x — merged 2026-08-14, see `launcher/README.md`) a bug report was diagnosed against it as though the two numbers were independent facts, which is the actual failure mode here: a wrong version number never errors, it misdirects. The lockfile half is the same shape one step down — `npm install --package-lock-only` fixes it and forgetting that step fails nothing. All four assertions were mutation-tested. What it **cannot** reach is the git tag, so "tag equals the launcher version" is still carried by the release checklist alone. All twenty fail quietly in production, which is why all twenty are pinned.
- **`syncGuidesFromMarkdown`'s `added` includes re-registrations, not just new guides.** It re-upserts every local `.md` on each run and pushes all of them, with `action: 'appended' | 'updated'` telling them apart. `syncGuides` filters to `'appended'` before feeding the tick pass — without that filter every local guide looks newly-discovered on every start and the targeted tick degrades into a full local scan. The Notion side's `added` is already genuinely new-only (filtered by `existingIds`).
- **Native dialogs are unusable in this app — in *either* process.** In the packaged build a native dialog appears and vanishes before it can be clicked, so every action gated behind one is simply unreachable — 「生成攻略」 was dead in the packaged build while working perfectly in a browser, which is why it survived testing. This rule used to end "native dialogs belong to the main process; the renderer cannot hold them open", and **that half was wrong**: the self-update prompt hit exactly the same failure from the *main* process using `dialog.showMessageBox`, which returns instantly with `response: 420` — a value outside the button range. Ten variants were measured (no checkbox, no `noLink`, no ids, bare `{message}`, `showMessageBoxSync`, with and without a parent window): **all 420**, while a plain Win32 `MessageBox` on the same machine stayed up indefinitely. So the boundary is not renderer-vs-main, it is native-vs-page. The updater's prompt is therefore a real web page in a small `BrowserWindow` (`renderUpdatePromptHtml`, result returned via `document.title` so it needs no preload and no privileges). **Do not "restore" a native dialog anywhere in this project** — it fails silently, and a non-zero response reads as "user declined". `askConfirm({title, body, okText, danger, notifyOnly})` is the in-page replacement — one component, identical in browser and package, and it can format a body that `\n`-joined `confirm()` text never could. It returns a **Promise**, so every call site must `await` it: a forgotten `await` makes `if (!askConfirm(...)) return` never return, silently green-lighting the dangerous action. Both rules are pinned in `guidegen.test.js`.
- **`sync_locked = 1` rows are never touched by any sync phase.** If a row "won't update," check that first.
- **Notion page identity must use the normalized UUID**, never raw URL text — Notion sometimes prefixes URLs with a title slug, so the same page's URL differs between queries. Comparing raw URLs once caused already-linked pages to be treated as new and overwrite curated names (`normalizeNotionId` in `lib/notion.js`).
- **One appid, one guide backend.** Markdown discovery won't overwrite a registered Notion guide unless `--force`.
- **Local guide paths are contained to `guidesDir`** (`resolveGuidePath`). Keep that check if you touch it — `guides.url` is data.
- **Documentation drifting from code is a real failure mode here.** A secret once sat hardcoded in this public repo for months while three separate docs claimed it was read from config, because nobody checked the source. Verify against code, not docs.
- **`localDate()` not `toISOString().slice(0,10)`** for user-facing dates — the latter is UTC and will be off by a day in the evening.
- **Strip comments before any source assertion — including `//`, not just `/* */`.** This codebase's comment density is its own hazard: an assertion that greps for a symbol gets satisfied by the *comment explaining that symbol* sitting right beside the code, so deleting the code changes nothing and the check passes forever. `tray.test.js` found this first (a `maybeAutoSync` check fed by the comment next to the wiring). It recurred twice on 2026-08-14 — a `doesNotMatch(/loadDashboard\(\)/)` fed by the `//` comment that explains why `loadDashboard` is wrong there, and a throwaway CSS scanner whose selectors were glued to the preceding comment, which made it report both HTML files clean when three elements were broken. The pattern is stable enough to plan around: **write the assertion, then break the thing it guards and watch it go red.** A source assertion that has never been seen failing is not evidence of anything.
- **A source assertion must slice to the block it means — never `indexOf(anchor)` plus a byte count.** `guidequeue.test.js` took `src.slice(start, start + 2600)` from `const drainNext` to check that `drainNext()` hangs off both `.then` and `.catch`; adding three progress branches to `runGuideGen`'s `onProgress` on 2026-08-17 pushed `.then` outside the window, and it failed with "can't find generateGuide's then/catch" while both were plainly there. **Raising the number only moves the tripwire**, and the dangerous direction is the opposite one: a window that still happens to contain both markers while the code between them has changed. It now slices between two real anchors (`const drainNext` → `return { started: true`) and asserts both exist, so losing one is a loud failure rather than a silently narrowed check. Same family as the comment rule above, and the same fix as `selfupdate.test.js`'s `-PathType Leaf` case: **slice to the block you mean, then match.**
- **UI state that hangs on a single un-retried async call whose failure is swallowed will eventually be wrong on screen, and only on a slow day.** Two on 2026-08-14, same shape: `aiReady` starts `false` and the ✨ 生成 button depends on `getSettings` beating `getDashboardData` — normally free, but the run right after setup has `startupJobs` mid-sync on a single thread, so the order flips and the fix-up repaint queues behind the same sync. And `Setup.html`'s `load()` had no `catch`, so a server that isn't listening yet (Electron opens the window before the child is up) skipped `initSteps()` entirely and left every wizard button on screen at once. Both were reported by a real user, and both are invisible in development, where the server is always warm and always up. **Ask what the screen looks like when that call is slow, and when it throws.** Prefer re-rendering from state already in memory over re-fetching to flip a flag.
- **An author `display:` silently defeats the `hidden` attribute.** `[hidden] { display: none }` comes from the *user-agent* stylesheet, so any author rule outranks it and turns that element's `hidden` into decoration — JS keeps setting `.hidden = true`, the element keeps showing, nothing errors. Both pages now carry a global `[hidden] { display: none !important }`, and `html-smoke.test.js` pins it; see that file's entry above for the three that were already live. Patching per element is whack-a-mole — the next `display:` rule opens a fresh hole just as quietly.
- **Guide text never goes in the database** — only a pointer. Guides have to stay human-editable and tickable where they live; the `guides` table tracks *where*, never *what*.

## Working on this efficiently

1. **Bulk repetitive external calls are disproportionately expensive.** Notion has no batch-update API, so "add one line to forty pages" is forty round trips — and each one carries the whole conversation history. Before starting that kind of job, say roughly how many calls it will take and offer to do it in a fresh session.
2. **Rule of thumb for a fresh session:** if the content to read/write clearly exceeds what's already in context, or the task is purely repetitive and needs no history, suggest starting clean. Small one-off edits are fine inline.
3. **Verification beats assumption.** A successful tool call does not mean the content is right — see the Notion page-ID and documentation-drift pitfalls above. Re-read results after bulk writes or overwrites, and prefer a read-only preview (`--dry-run`, a SELECT) before anything that writes outside this repo.
