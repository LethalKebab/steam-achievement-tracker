# AI 攻略生成 —— 设计方案(尚未实现)

状态:**设计完成,一行代码都还没写。** 2026-08-09 定的方案,决策来自一轮完整的问答排查。
下次动手前先读这份,不要重新设计——每个选择背后的取舍都记在这里了。

## 要解决什么

写一份攻略现在必须经过一次 Claude Code 会话:拉 Steam 成就数据、查 wiki、逐条消化改写、
写进 Notion、再回读验证(完整流程见 `.claude/skills/achievement-guide-writing/SKILL.md`)。
目标是让**用这个应用的人自己**用他们自己的 AI API key 生成攻略,不必经过某一次对话。

## 已定的决策

| | 决定 | 为什么 |
|---|---|---|
| 面向谁 | 打包进 app,给用户用 | 不是只给作者的 CLI 工具 |
| 联网研究 | **用供应商自带的服务端搜索** | 自建"搜索 API + 抓页 + HTML→文本"是整个方案里最大的一块;供应商自带的话这块归零 |
| 供应商 | **Anthropic + OpenAI**,「有服务端搜索」是硬性准入 | 混进一家没有搜索的,会让质量取决于用户选了谁,而用户看不出这个差别 |
| 质量目标 | 成品,不是初稿 | 靠机器闸门达成,不是靠"让模型写得更好"——见下 |
| v1 规模 | 单次上下文装得下的游戏(约 <60-100 个成就) | 已有攻略的 99 款里 87% 在 100 个以下;100+ 的分片编排是独立工程,以后再说 |
| 输出后端 | **v1 只写本地 `guides/*.md`** | `syncGuidesFromMarkdown` 已经能收;Notion 那边要从头写"创建带嵌套 to_do 的页面",是第二阶段 |
| 落盘闸门 | **按可逆性分,不按后端分**:新建文件 = 机器闸门过了就自动写;覆盖已有文件 = 必须人工确认 | 这样以后加 Notion 不用重写规则,它自然落进"不可逆"那一档 |
| 花钱 | 用户设硬上限 + 实时显示已花费 + **每次运行显式确认**;**暂不做预估** | 没有实测数据的金额预估必然是错的,而在花钱这件事上给错数字比不给更糟。攒够实测再上预估 |
| 勾选状态 | **模型一律只写 `- [ ]`,生成完由我们按数据库机械打勾** | 让"勾选状态必须等于真实 achieved"从"要检查的东西"变成结构上不可能违反 |
| 解锁状态 | **不喂给模型** | 上一条的推论。而且更符合规则 3.1:攻略是"怎么打过的"记录,不是"还剩什么没做"的清单 |
| 不过关 | 最多 3 轮修改;仍不过就**留成草稿**,报告哪几条没过 | 丢弃等于烧掉钱和时间还什么都不留;而"哪条没过"本身有信息量 |
| 重写已有 | 允许 | 但必须备份 + diff 预览 + 人工确认 |
| 中断 | 已完成部分存草稿,**且支持续跑** | 中间状态(搜到的资料、已写好的分节)需要持久化 |

## 能保证什么,不能保证什么

这是整个方案最重要的一段,UI 上必须如实告诉用户。

**机器能验(全部对着本地真实数据):** 每个成就都有独立 checkbox 行 · 没有合并行 ·
勾选状态等于真实 `achieved`(现在由机械打勾保证)· **描述是不是原文照抄**(直接和
`achievements.description` 比对)· 重名成就有没有抄描述 · 本地 md 有 `# 游戏名` 那行 ·
节标题没有"共N个"统计 · 没有"数据来源"说明。

**机器验不了:攻略内容对不对。** 步骤是否可行、难度评级准不准、"易错过"标注是否属实、
互斥关系是否真实——而这正是攻略的全部价值。

所以本方案保证的是「**格式和数据一定正确**」,不是「**攻略正确**」。UI 必须写明内容未经验证。
(曾考虑强制模型给出来源 URL 让人抽查,已决定不做。)

**为什么这件事必须较真:** `audit` 实测 1,190 个已勾选的框里有 **64 个反查不出来**,
原因全是攻略把官方描述改写了。改写描述恰恰是 LLM 无监督生成时必然会做的事。
没有这道闸门,这个功能就是在稳定地污染匹配系统——而那套匹配规则是踩了三轮假阳性才调准的。

## 架构

```
lib/ai.js         供应商抽象:请求组装、tool-call 循环、usage 统计。两家的请求结构、
                  工具定义格式、返回体、错误码都不一样,这层就是为了把差异关在里面
lib/guidegen.js   编排:取成就数据 → 调模型研究+撰写 → 机械打勾 → 交给校验器 →
                  不过就把具体错误回灌重写(最多 3 轮)→ 落盘。中间状态持久化以支持续跑
lib/guidelint.js  校验器。**复用现成的东西**,不要重写:
                    guides.js  extractTitleCandidates / findAmbiguousNames /
                               resolveTodoToAchievement
                    markdown.js loadTodos(已经能解析 `- [ ]` 和缩进层级)
```

服务端的长任务照抄 `lib/server.js` 里 `startBackgroundSync` 那一套:**一个函数、一处并发
保护、进度靠 `/api/syncStatus` 轮询**。不要为它另起一套状态机——同步那边的教训是两个入口
就会有两份并发保护。

### 一个必须注意的坑

`syncGuidesFromMarkdown` 会扫 `guides/*.md`,**把任何带 `appid:` 行的文件登记进 guides 表**。
没过闸门的草稿如果就放在 `guides/` 下,会被自动登记,然后 `checkbox-sync` 就开始拿一份
没验过的攻略去勾用户的框——正是本方案明令禁止的事。

草稿必须放在别处(比如 `guides/.drafts/`),或者不带 `appid:` 行。备份同理
(`guides/.backup/<appid>-<时间戳>.md`)。落地前先确认 markdown 发现逻辑扫不到这两个目录。

## 动手顺序

1. **先做 spike,再承诺后面任何事**(半天):验证 Anthropic 和 OpenAI 的服务端搜索到底
   返回什么——是全文还是摘要,中文攻略站(3DM / 游民星空 / NGA / B站)覆盖如何。
   skill 8.3 明确说大 wiki 用 `WebFetch` 会被截断、必须拿到 40 万字符级别的全文;
   如果供应商只给摘要,质量目标就要重定,或者被迫回到自建研究层(那是另一个量级)。
   **这一条没验之前,下面的工时估算都不作数。**
   (2026-08-09 当天 web 搜索工具连续三次不可用,所以关于两家 API 现状的说法全部未经核实。)
2. `lib/guidelint.js` + 机械打勾 —— 可以脱离 AI 单独开发和测试,拿现有的 99 份攻略当测试
   语料(它们应该全部通过;不通过的地方要么是校验器写错了,要么是真的发现了问题)
3. `lib/ai.js` 单家(Anthropic)跑通端到端
4. 加 OpenAI
5. 费用上限 + 实时花费 + 运行前确认
6. 续跑用的中间状态持久化
7. 设置页(供应商、key、上限)+ Dashboard 入口 + 进度显示
8. 备份 / diff 预览 / 覆盖确认
9. 文档 + 测试

| 费用上限 + 实时花费 + 确认 | 1 天 |

| 备份 + diff 预览 + 覆盖确认 | 1 天 |

| **合计** | **约 15-17.5 天(3-3.5 周)** |

比最初"2-4 周"的估算偏上,原因是两个明确的加码:支持两家供应商(≈ 两倍的循环调试)、
以及中断后能续跑(要持久化中间状态)。

**缩减范围时按这个顺序砍**(每一条都不影响前面的东西能用):续跑(-2 天)→
第二家供应商(-1.5 天)→ 重写已有攻略,只保留新建(-1 天)。砍完约 10.5-13 天。

## 明确不在 v1 范围内

  毁掉 API 拿不回来的内容,比如 bookmark 块 —— 见 SKILL.md 规则 9.3)

- 强制来源引用(已决定不做)
