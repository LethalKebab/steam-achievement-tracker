# AI 攻略生成 —— 设计方案

状态:**9 步里做完 3 步**(spike、校验器 + 机械打勾、`lib/ai.js`)。2026-08-09 定的方案,
决策来自一轮完整的问答排查。下次动手前先读这份,不要重新设计——每个选择背后的取舍都记在这里了。
「动手顺序」那一节是活的清单,做完一步就在那里划掉。

## 要解决什么

写一份攻略现在必须经过一次 Claude Code 会话:拉 Steam 成就数据、查 wiki、逐条消化改写、
写进 Notion、再回读验证(完整流程见 `.claude/skills/achievement-guide-writing/SKILL.md`)。
目标是让**用这个应用的人自己**用他们自己的 AI API key 生成攻略,不必经过某一次对话。

## 已定的决策

| | 决定 | 为什么 |
|---|---|---|
| 面向谁 | 打包进 app,给用户用 | 不是只给作者的 CLI 工具 |
| 联网研究 | **用供应商自带的服务端搜索** | 自建"搜索 API + 抓页 + HTML→文本"是整个方案里最大的一块;供应商自带的话这块归零 |
| 供应商 | **Anthropic + Gemini**,「有服务端搜索」是硬性准入 | 混进一家没有搜索的,会让质量取决于用户选了谁,而用户看不出这个差别。~~OpenAI~~ 换成 Gemini,2026-08-10,理由见下面「为什么第二家是 Gemini 不是 OpenAI」 |
| 质量目标 | 成品,不是初稿 | 靠机器闸门达成,不是靠"让模型写得更好"——见下 |
| 规模 | ~~单次上下文装得下的游戏(约 <60-100 个成就)~~ → **分段写,上限 500**(2026-08-11 改) | 原理由是"87% 的游戏在 100 个以下,分片是独立工程"。但那 13% 里有库里最想要攻略的几款(了不起的修仙模拟器 408、文明 VI 320、古剑奇谭二 294),而分片真做起来比预想的小:**同一个 session 分几轮写**,模型看得见自己前面写了什么,分节不重复、成就不重写,拼起来再对完整的一份打勾和校验。真正的约束从来不是清单装不下(清单很小),是**正文写不了那么长** —— 400 个成就约六万字,超过任何一家的单次输出上限,而且超了不报错,只表现为"后半段的成就都缺 checkbox" |
| 输出后端 | ~~**v1 只写本地 `guides/*.md`**~~ → **Notion 连着就写 Notion,`--local` 才写本地**(2026-08-11 改) | 原理由是"Notion 那边要从头写创建带嵌套 to_do 的页面,是第二阶段"。**这条排期是错的,而且错得不显眼**:SKILL.md 8.0 早就写着"只要 Notion 是连着的,新攻略就建在 Overview 数据库里,不要默认写本地",实现的时候只读了这份文档的排期,没回头对那条约定。用户手写的一百多篇攻略都在 Notion,机器写的落在别处 = 一套笔记劈成两处。真正的工作量也没有想象中大:转换器只需要覆盖**我们自己生成的**那几种块,不是通用 markdown 转换器 |
| 落盘闸门 | **按可逆性分,不按后端分**:新建文件 = 机器闸门过了就自动写;覆盖已有文件 = 必须人工确认 | 这样以后加 Notion 不用重写规则,它自然落进"不可逆"那一档 |
| 花钱 | ~~用户设硬上限 + 实时显示已花费~~ → **只保留运行前确认 + 跑完报 token 数**(2026-08-11 改) | 原决定是对的一半:「没有实测数据的金额预估必然是错的」—— 但接着还是做了上限,而上限本身就要靠那个估不准的金额。DeepSeek / Gemini 没有可信单价,**服务端搜索怎么计费更是从头到尾没测过**,于是「$5 上限」是拿一个没人敢背书的数算出来的。**一个不可信的上限比没有上限更糟:它看着像防护,实际什么都没防。** 整套(两组上限、价格表、ai_usage 账本、ai-cost 命令)已删。真要做回来,先去把搜索计费测出来 |
| 勾选状态 | **模型一律只写 `- [ ]`,生成完由我们按数据库机械打勾** | 让"勾选状态必须等于真实 achieved"从"要检查的东西"变成结构上不可能违反 |
| 解锁状态 | **不喂给模型** | 上一条的推论。而且更符合规则 3.1:攻略是"怎么打过的"记录,不是"还剩什么没做"的清单 |
| 不过关 | 最多 3 轮修改;仍不过就**留成草稿**,报告哪几条没过 | 丢弃等于烧掉钱和时间还什么都不留;而"哪条没过"本身有信息量 |
| 重写已有 | 允许 | 但必须备份 + diff 预览 + 人工确认 |
| 重写的粒度 | **整篇之外还有"只重写点名的那几条"**(`--only`,2026-08-18 加) | 整篇重写有两个代价,而它们和"写得好不好"无关:**用户手改过的段落和手动勾上的子步骤框全部作废**,以及已经写对的部分被重新掷一次骰子。真实语料里这两条都不是理论问题 —— 库里 107 篇攻略全在 Notion,其中一批是手写的。判据不是省钱,是**保住没被点名的那部分**:未点名的每一个字节逐字不变,而这件事必须由程序保证(按行号/块 id 贴回),不能靠"叫模型别动别的" —— 模型交回整篇、声称只改了三条,没有任何办法验证 |
| 中断 | 已完成部分存草稿,**且支持续跑** | 中间状态(搜到的资料、已写好的分节)需要持久化 |

## 能保证什么,不能保证什么

这是整个方案最重要的一段,UI 上必须如实告诉用户。

**机器能验(全部对着本地真实数据):** 每个成就都有独立 checkbox 行 · 没有合并行 ·
勾选状态等于真实 `achieved`(现在由机械打勾保证)· **描述是不是原文照抄**(直接和
`achievements.description` 比对)· 重名成就有没有抄描述 · 本地 md 有 `# 游戏名` 那行 ·
节标题没有"共N个"统计 · 没有"数据来源"说明。

**机器验不了:攻略内容对不对。** 步骤是否可行、难度评级准不准、"易错过"标注是否属实、
互斥关系是否真实——而这正是攻略的全部价值。

所以本方案保证的是「**格式和数据一定正确**」,不是「**攻略正确**」。UI 必须写明内容未经验证。
(曾考虑强制模型给出来源 URL 让人抽查,已决定不做。)

**为什么这件事必须较真:** `audit` 实测 1,190 个已勾选的框里有 **64 个反查不出来**,
原因全是攻略把官方描述改写了。改写描述恰恰是 LLM 无监督生成时必然会做的事。
没有这道闸门,这个功能就是在稳定地污染匹配系统——而那套匹配规则是踩了三轮假阳性才调准的。

## 架构

```
lib/ai.js         供应商抽象:请求组装、tool-call 循环、usage 统计。两家的请求结构、
                  工具定义格式、返回体、错误码都不一样,这层就是为了把差异关在里面
lib/guidegen.js   编排:取成就数据 → 调模型研究+撰写 → 机械打勾 → 交给校验器 →
                  不过就把具体错误回灌重写(最多 3 轮)→ 落盘。中间状态持久化以支持续跑
lib/guidelint.js  校验器。**复用现成的东西**,不要重写:
                    guides.js  extractTitleCandidates / findAmbiguousNames /
                               resolveTodoToAchievement
                    markdown.js loadTodos(已经能解析 `- [ ]` 和缩进层级)
```

服务端的长任务照抄 `lib/server.js` 里 `startBackgroundSync` 那一套:**一个函数、一处并发
保护、进度靠 `/api/syncStatus` 轮询**。不要为它另起一套状态机——同步那边的教训是两个入口
就会有两份并发保护。

### 一个必须注意的坑

`syncGuidesFromMarkdown` 会扫 `guides/*.md`,**把任何带 `appid:` 行的文件登记进 guides 表**。
没过闸门的草稿如果就放在 `guides/` 下,会被自动登记,然后 `checkbox-sync` 就开始拿一份
没验过的攻略去勾用户的框——正是本方案明令禁止的事。

草稿必须放在别处(比如 `guides/.drafts/`),或者不带 `appid:` 行。备份同理
(`guides/.backup/<appid>-<时间戳>.md`)。落地前先确认 markdown 发现逻辑扫不到这两个目录。

## spike 结果(2026-08-09)

来源是 `claude-api` skill 里的权威文档,不是网页搜索(当天 web 搜索工具连续三次不可用)。

**问题本身问错了。这不是一个工具,是两个,而这个分工恰好就是答案:**

| 工具 | 返回什么 | 关键参数 |
|---|---|---|
| `web_search_20260209` | `web_search_tool_result` → 一个**结果列表**(摘要形态) | `max_uses`、**`allowed_domains`/`blocked_domains`**、`user_location` |
| `web_fetch_20260209` | `web_fetch_tool_result` → 一个 **`document` 块,是页面全文** | `max_uses`、`allowed_domains`、**`citations`**、**`max_content_tokens`** |

所以"只给摘要还是给全文"是个伪二选一:搜索负责找出候选,**`web_fetch` 负责把全文抓回来**,
`max_content_tokens` 就是控制抓多少的旋钮——正好对应 SKILL.md 8.3 要的
`get_page_text(400000)` 那套。适用于 Opus 5 / 4.8 / 4.7 / 4.6、Sonnet 5 / 4.6。

**三条会直接改变设计的发现:**

1. **`web_fetch` 只能抓"已经出现在对话里"的 URL。** 必须先由搜索把 URL 抛出来,
   才能 fetch。这是编排上的硬顺序,不是实现细节。
2. **`allowed_domains` 是中文攻略站问题的现成解法**——可以把搜索直接偏向 3DM /
   游民星空 / NGA / B站,而不是指望索引自己给面子。
3. **绝对不要再单独声明 `code_execution`。** `_20260209` 版本内部已经跑代码做动态过滤,
   再加一个会变成两套执行环境、把模型搞糊涂。(这是个不看文档必然会写出来的 bug。)

顺带一条给校验器用的:**服务端工具的错误不抛异常**,而是 HTTP 200 + `content` 里放一个
错误对象。而**成功的形状两个工具并不一样**:web_search 成功是**数组**,web_fetch 成功是
**对象**(`{type:'web_fetch_result'}`)。把其中一条当成通用规则,两个方向都会出事 ——
见下面「三种长得像成功的失败」那节。

**还没验、需要真 key 的两条:**(本机没有 `ANTHROPIC_API_KEY`,也没装 `ant` CLI)

- 中文攻略站在搜索索引里的实际覆盖率
- `max_content_tokens` 的实际上限够不够 SKILL.md 8.3 要的量级
- 搜索工具本身怎么计费(skill 里只有模型价格:Opus 5 是 $5/$25 每百万 token)

这三条都只影响"质量能到哪",不影响方案成不成立,所以后面的工时估算现在可以当数。

## 校验器跑全量语料的结果(2026-08-10)

设计文档原话是"现有的 99 份攻略应该全部通过;不通过的地方要么是校验器写错了,要么是
真的发现了问题"。跑完之后:**两者都有,而且真问题占压倒多数。**

能校验的是 44 份(另外 55 份是 100% 通关的游戏,`syncAchievementSchema` 故意不同步
它们的成就详情,没有可比对的基准)。

第一次跑报了 350 条 `missing-checkbox`。修掉下面那个匹配引擎 bug 之后重跑,
剩 **333 条**,分布是:

| 分类 | 攻略 | 成就 | 是什么 |
|---|---|---|---|
| 没按 checkbox 格式写 | 1 | 84 | 河洛群俠傳,见下 |
| 写了一部分 | 25 | 249 | 普通的"攻略没写完" |
| 完全干净 | 18 | 0 | 每个成就都有框 |

**大头是攻略没写完,不是坏掉了。** 巫师 3 覆盖 44/78、FF7 Remake 30/63、
Supermarket Together 26/51;长尾很短——25 份里有 12 份只缺 1~4 个。这些成就没有
框可勾,但数据本身没有任何问题。

唯一一份真正格式不对的是 **河洛群俠傳(84 成就 / 35 框)**:那 35 个框根本不是成就
条目,是流程步骤(「入村南边墓地对话获得天选之人称号」「龙洞」)。整份攻略没按
"一个成就一行 checkbox"写,违反 SKILL.md 规则一,对同步来说等于完全不存在。

剩下的 333 条里抽查了 17 条(挑的是"框数 ≥ 成就数却还报缺"这种最可疑的),
**15 条确实没有框,2 条是格式擦边**:

- `秘密食材。` vs Steam 上的 `秘密食材` —— 结尾多一个句号,精确相等就不成立
- `全成就\n最强的炼金术士获得了所有的成就。` —— 成就名和描述挤在第二行没分开

⚠️ **这个 2/17 不能外推成全局误报率**。抽样刻意挑的是最可疑的一档,不是随机抽的。
按"1/8"估出来的收益(~40 条)与事实不符:句号那条真去修完之后,全量只恢复了
**3 条**(333 → 330)。剩下的 330 基本就是攻略没写完,不是匹配问题。

**为什么这么大一片问题以前一直没被发现**,值得单独记一笔:

- `audit` 只检查**已经勾上**的框,勾不上的框它根本不会去看
- `checkbox-sync --dry-run` 报"0 个要勾的",和"全都勾完了"输出一模一样

两个工具各自都没说谎,合起来正好留出一个谁都不覆盖的盲区。CLAUDE.md 里那句
"dry-run 0 ticks,Notion 和 Steam 一致"因此是过度解读,已经改掉。

### 顺带修掉的匹配引擎 bug

`extractTitleCandidates` 原来只按 `' - '`(破折号**前面有空格**)拆,于是
`胜利！- 使用北条时宗获得一场常规赛胜利` 这种写法整行只有一个候选,成就名提取不出来。
修完少报 17 条(全是文明 6,那份因此从"有 error"变成完全干净)。
已加一条"破折号后面跟空白就拆"的候选规则——
**仍然是精确相等匹配,只是多给一个候选片段,没有放宽判定**(CLAUDE.md 明确允许加
候选提取规则,不允许动等值判断)。

改的是勾选路径,所以按规矩跑了 `checkbox-sync --dry-run` 验证影响:
**新规则带来 0 个新勾选**。dry-run 里唯一那 1 个待勾(杯杯倒满「店长鳄鱼」)和这次
改动无关——那个框用的是换行分隔,本来就能匹配,是前两天玩过之后积下的正常待办。

### 第二个:成就名尾部多标点

同一天顺着上面那 2 条擦边案例修的。攻略写「秘密食材。」,Steam 上是「秘密食材」,
精确相等因此不成立。加了一条"去掉候选结尾的句读之后再算一个候选"的规则:

- **追加,不替换**。「白手起家。」「胜利！」这类成就名本身就带标点,原样候选必须留着,
  否则等于把本来能匹配的改成匹配不上;去标点的候选排在最后,精确的那个优先命中。
- **只动候选侧,不动 defs 的名字索引**。给索引加去标点的键会让 `X` 和 `X。` 撞成同名、
  双双按"歧义"跳过——那是拿"勾不上"换"勾错"。代价是反方向(攻略写对、Steam 名字带
  标点)仍匹配不上,属于已知未覆盖。
- 成对符号(引号、括号、书名号)不在去除范围内,不然 `《物种起源》` 会被削成 `《物种起源`。

同样跑了 `checkbox-sync --dry-run`:**0 个新勾选**(杯杯倒满那条这期间已经勾上了,
不是被这次改动弄丢的——匹配照常命中,只是同步只勾未勾的框)。
实际收益:全量 missing-checkbox 333 → **330**。

## lib/ai.js 落地记录(2026-08-10)

供应商层写完了:请求组装、服务端工具循环、usage 统计。**编排(`lib/guidegen.js`)还没开始**,
所以现在还生成不出攻略——`ai-check` 只问一个成就、拿三句话回来,验的是链路通不通。
离线测试在 `test/ai.test.js`(23 条,注入 fetch,一个字节都不发出去)。

**设计文档写"tool-call 循环",实际不是客户端在执行工具。** web_search / web_fetch 全在
Anthropic 那边跑完,我们这边没有工具要执行。要循环是因为服务端的采样循环有迭代上限
(默认 10 次),撞上就返回 `stop_reason: 'pause_turn'`,把 assistant 那一轮**原样**加回
messages 再发一次。**不要额外补一句「继续」**——服务端认的是结尾那个 `server_tool_use` 块,
多塞一条 user 消息反而打断它。续跑时前几轮的 content 也必须拼回去还给调用方,
不然搜到的资料全丢了,只剩最后一段。

**必须流式,这不是性能选择。** `max_tokens` 是 thinking + 正文的**总**上限,而 Opus 5
默认就在思考;一份 60 个成就的攻略配上联网研究,非流式请求会先撞上 HTTP 超时
(undici 默认 5 分钟)而不是撞上 token 上限。于是这一层自己解析 SSE。

**四个参数在 Opus 5 上是 400,不是被忽略**:`temperature`、`top_p`、`top_k`、
`thinking.budget_tokens`。深浅只能用 `output_config.effort`。另外 assistant 结尾的
prefill 同样 400,要固定输出格式得用 structured outputs。

**绝对不要再单独声明 `code_execution`** —— `_20260209` 版的 web 工具内部已经跑代码做
动态过滤,再加一个等于两套执行环境。(这是不看文档必然会写出来的 bug,spike 那节也记了。)

### 三种"长得像成功"的失败

这三种全是 HTTP 200,分支写漏一处就会把坏结果当好结果往下传,所以统一收在 `checkResult()` 里:

| 情况 | 表面 | 实际 |
|---|---|---|
| `stop_reason: 'refusal'` | 200 | 安全分类器拒答,content 空的或半截 |
| `stop_reason: 'max_tokens'` | 200,**有正文** | 正文被砍了一半——截断的攻略比生成失败更糟。**这一种现在会自愈**,见下 |
| 停止原因正常,但**一个 `text` 块都没有** | 200,没有工具错误,停止原因也正常 | 这一轮什么都没写。最难查的一种,因为三样表面正常;**现在会重试,而且报得出回包里到底有什么**,见下 |
| 正文里混进**供应商自己的控制符** | 200,停止原因正常,正文非空 | 正文从那个位置**断掉**了。表面比上一条还正常(有正文!),而实际少了一截,见下 |
| 工具报错 | 200,`stop_reason: 'end_turn'` | 结果块里放的是错误对象。**但两个工具的「成功」形状不一样**:web_search 成功是**数组**,web_fetch 成功是**对象** `{type:'web_fetch_result'}` |

**判错方向反了一样致命,而这是 2026-08-13 修的一个真事故。** 判成功一度对两个工具都用
`Array.isArray` —— 那条规则只对 web_search 成立,于是每一次**成功**抓页都被记成一条错误
(错误码正是成功块自己的 type,`web_fetch_result`),整轮直接判死。`web_fetch` 只在官方端点
默认开着(`ai.webFetch ?? !ai.baseUrl`),而此前跑通的实盘全在 DeepSeek 兼容端点上,那里它
默认关着 —— 所以这个 bug 一路跑到用户第一次用官方 key 才炸。两处判断(校验和进度事件)
本来各写了一份,于是同一个 bug 有两份拷贝:进度条同时把每次成功抓页显示成 `失败(unknown)`。
现在共用 `toolResultError()`。

修的时候顺手把严重程度分开了,因为一刀切两个方向都错:

- **搜索失败 ⇒ 整轮不可用。** 搜索是研究的入口,它没成,模型就是凭记忆在写 —— 正是
  `canSearch` 那套准入设计要防的、用户看不出来的质量差别。
- **抓页失败 ⇒ 报出来,但不拦路。** `web_fetch` 是逐个 URL 的:`url_not_allowed`
  (它只能抓已经出现在对话里的 URL,模型自己拼一个就是这个码)和 `url_not_accessible`
  (404 / 反爬 / 超时,中文攻略站尤其常见)在一次正常研究里几乎必然出现几条。搜了十页、
  抓失败两页,资料是够的;为此作废整轮是把常态当故障,而代价是用户已经付掉的几分钟和 token。

不拦路 ≠ 不吭声:`checkResult` 把它放进 `warnings`,`guidegen` 走进度事件报给用户,
`ai-check` 逐条列出来并标明"不影响这一轮"。

### 一段写不出来时的三级阶梯(2026-08-16 起,2026-08-17 补齐)

**原样再问 → 切成两半 → 记下来接着跑。** 三级各治一种病,顺序不能换。

`max_tokens` 以前是直接 throw 出 `generateGuide` —— session、已经写好的段落、那几分钟和
那些 token,一起作废。现在第一轮撞上截断就把**这一段**一分为二,只重问这两半,直到写得下
或者切到 5 个成就(`MIN_CHUNK`)为止。每次至少减半,所以必然收敛。

**为什么是事后重试,不是事前算尺寸。** 装进单次请求的是 thinking + 正文。正文可以估
(一个成就约 150 字),thinking 估不了:它随游戏冷门程度、模型、端点变,而在兼容端点上
连压它的参数都发不出去(`ai.baseUrl` 一设 `extras` 就是 false,`thinking` /
`output_config` 根本不发)。任何开跑前算出来的段长都是在预测那个量;而**截断是量到的
事实**,它直接说明这一段越了界。这和本文档删掉估价那一节是同一条原则:报测到的,
不报推出来的。

三处边界都有理由:

- **重问前必须 `session.dropLastTurn()`。** `ask` 是先 push assistant 再判定结果,所以
  那半份废稿已经躺在上下文里了,而分段提示词写着「不要重复前面已经写过的成就」——
  不摘掉,模型会跳过它写了一半的那几个。**产出看着完全正常,只是少了条目。**
  失败会报出来,缺条目不会。
- **拒答、RECITATION、搜索报错一级都不给。** 都不是长度问题,切小了照样撞,而且各自的
  正确处置完全不同。`checkResult` 为此多返回一个 `code`:调用方要分辨"这种失败能不能
  补救",而拿人话当接口,改个措辞就会悄悄失灵。
- **只在第一轮切。** 之后几轮是按 `lint.findings` 定点重写,下标和那份发现是绑定的,
  中途改段数会让对应关系失效。所以 `chunkFloorAdvice` 在非第一轮**不改错误码** ——
  那时候不切是因为下标动不得,不是因为段已经够小,说成"切到 N 个还是写不出来"
  是在报一个没发生过的事实。

切到下限还失败时,报错**不再建议调大 `ai.maxTokens`**:正文都这么短了还超,说明吃掉
额度的是思考,加大只会让它想得更久。顺带修掉了那条消息里的数字 —— 它打印的是
`r.usage.outputTokens`,而这个值是 `addUsage` 跨 pause_turn 续跑累加出来的**整轮产出**,
可以远大于单次请求的上限(实测报 61445,而当时上限是 32000)。原话读起来就像在说
"上限是 61445",照着调基准就错了。

#### 第一级:空回复原样再问一次(2026-08-17)

「一个 `text` 块都没有」是这条路上唯一真正的**瞬时**失败:请求没问题、段长没问题、
资料也搜到了,就是这一次没吐出正文。它此前**一次都不重试**,整份当场作废 —— 实测撞到过
三次,最近一次是 KINGDOM HEARTS -HD 1.5+2.5 ReMIX-(197 个成就分 4 段,第 3 段)。
原样再问一遍很可能就有了,代价是一次请求;不重问的代价是整份作废、十几次联网搜索白花。

`EMPTY_RETRIES` = 1,不是更多:第二次还空就不是抽风了,该换手法而不是继续撞。

**第二次还空就当长度问题处理,切成两半。** 这一步是猜,但有依据:兼容端点上既发不出压
thinking 的参数,**也不能假定它会把「额度被思考吃光」如实报成 `max_tokens`** ——
`api.deepseek.com/anthropic` 是别人实现的 Messages API,停止原因的保真度不在我们手里。
所以"空回复"里混着一部分实质上就是截断的情况,而切小正是那部分的解。猜错多花一次请求。
因为切不动时错误码会被改写成 `chunk-too-small`,`err.detail.was` 保留改写前那个码 ——
「被截断」和「什么都没输出」对"换个模型吧"这条建议的分量完全不同。

**同时把「没有正文」这句话变得可诊断了。** 它现在带上原始停止原因、产出 token 数、
以及回包里各类块的个数,因为这三样指向完全不同的处置:

| 回包 | 说明 | 该怎么办 |
|---|---|---|
| `thinking×1`,三万 token | 额度被思考吃光了,和截断是一回事 | 切小 |
| 一个块都没有,0 token | 这一次抽风 | 原样再问 |
| `server_tool_use×2`,没有 text | 光搜没写 | 看提示词 / 搜索预算 |

前三次撞上这个失败,能拿到的信息只有"模型没有输出任何正文"一句话,于是每次都只能靠猜,
而每一次猜都要花掉用户几分钟和一笔 token 才验得出来。

#### 第一级还管另一种:供应商把控制符写进正文(2026-08-17)

实测(KINGDOM HEARTS + DeepSeek):第 173 个成就写到一半变成

```
- [ ] **The Warrior: Ventus</｜｜DSML｜｜parameter>
</｜｜DSML｜｜invoke>
</｜｜DSML｜｜tool_calls>
```

然后输出就没了,后面 10 个成就再没写,**三轮都断在同一处**。

**停止原因正常、正文非空、工具没报错** —— 三样表面全对,所以在这之前一个分支都拦不住。
那三行乱码直接落进了用户的草稿;要不是恰好少了 10 个 checkbox 被校验器间接挡下,
它会跟着写进 Notion 页面。

**不能只把标记删掉接着用。** 正文是**断的**,不是脏的:删了标记只会得到一份看起来完整、
实际少了一截的攻略,而这个项目的偏好一贯是「报出来的失败胜过悄悄少东西」。
所以整轮判死,和 `empty` 一起进 `RETRYABLE`(同一性质:这一次采样跑偏,重问就好)、
`SPLITTABLE` 和 `CHUNK_LOCAL`。

**判据故意收得很窄,因为误判一次就是白花一轮的钱。** 攻略正文里合法地带着 `<br>`、
`<details>`、`<summary>`、`<table>`、`<span underline="true">`,所以只认三种不可能撞车的形状:

| 形状 | 哪一家 |
|---|---|
| 尖括号里出现全角竖线 `｜`(U+FF5C) | DeepSeek(`<｜tool▁calls▁begin｜>`) |
| `<\|…\|>` | Llama / OpenAI(`<\|im_start\|>`) |
| 闭合式 `</invoke>` `</tool_calls>` `</parameter>` | 通用 |

**故意不认开标签**(`<function_calls …>` 之类):它们和真 HTML 长得太像。漏掉一种没见过的
写法,下次会在「缺 checkbox」上暴露出来,那是便宜得多的方向。

#### 第三级:一段作废,整份不作废(2026-08-17)

招用完了就把这一段记进 `chunkFailures`,**第一轮接着写后面的段**。丢掉整份换不来任何东西,
而少的那一段有现成的补救路径:它的成就全部会被校验器报成 `missing-checkbox`(带 `apiName`),
`chunksNeedingRewrite` 于是精确挑出这一段,下一轮只重问它 —— 那套机器本来就是为
"某段整个没出来"这个头号失败方式写的。补的时候用 `buildChunkMessage`(「写这一段」)而不是
`buildChunkFeedback`:一段从没写出来,缺的不是修正意见,是这一段本身。

宽容必须有边界,三道:

- **先分级:`CHUNK_LOCAL`。** 只有 `checkResult` 判出来的那六种是**这一段自己**的问题
  (全是 HTTP 200)。401、网络断了、`maxContinuations` 用光了是**整体**故障,原样抛出去 ——
  当成"这一段没成"接着问,是拿同一堵墙按剩余段数再撞几次,而且真正的原因会被埋进一串
  「第 N 段没写出来」里,它自己那条终端建议(比如 `bad-api-key` 要说的
  「环境变量会盖掉 config.json」)再也走不到 `tracker.js` 的顶层 catch。
- **第一轮全军覆没就抛第一个真原因**,不要拿一份空草稿去校验、报出"197 个成就全缺
  checkbox"、再花两轮重问。报病因不报症状,顺带把系统性故障的开销压在一轮之内。
- **`ok` 要求 `chunkFailures` 为空。** 已经知道缺一段,就绝不落地 —— 哪怕将来校验器
  哪天放过了它。

CLI 和 Dashboard 都把失败的段**排在 blocking 清单前面**,同一条理由。Dashboard 那侧还给
生成状态加了一个 `warnings` 数组:`note` 那一格是"现在在干什么",三秒后就被下一个进度事件
盖掉,而"第 3 段没回来"必须一直留到结果出来 —— 和 `syncState.bumped` 同一条设计。

#### 草稿改成每写完一段就落盘(2026-08-17)

`writeFileSync(draftPath, …)` 原来在**整个分段循环之后**,所以中途任何一次抛异常都会把
已经写好的段落连同它们的联网研究一起丢掉。这也是「步骤 6(断点续传)不着急,草稿反正
留在 `guides/.drafts/`」那句话**在真正会发生的失败上是假的**:线上那次失败之后
`.drafts/` 是空的。

逐段写的成本相对一次两三分钟的网络调用可以忽略,而 `.drafts/` 本身是结构性安全的
(`syncGuidesFromMarkdown` 非递归,半份草稿不可能被登记然后拿去勾框)。写盘那一句放在
**`try` 外面**:写盘失败是我们这边的故障,不是"这一段模型没写出来",不该被重试阶梯
当成后者处理。

注意轮末那次 `writeDraft()` 会盖掉大部分测试的观察点,所以**逐段落盘只在"整轮被中断"
的路径上才观察得到** —— 第一版测试把那一句删掉照样全绿,得用一个供应商级的异常才钉得住。

### 记账

**一条消息内覆盖,跨消息累加。** `message_start` 和 `message_delta` 报的都是"这条消息到
目前为止的累计值",相加会把输出 token 多算一遍;而 pause_turn 续跑、回灌重写的每一轮是
各自独立的消息,那时才该加。两句话都对才叫账准,错一半没有任何地方会报错,只会让费用
显示一直偏高。测试钉住了这条。

**估价整套已删(2026-08-11)。** 当时写的是"只估模型 token 的钱,搜索次数如实报、
不折算",理由是"搜索计费还在三条待验里"。那条待验一直没验,而估价代码却先长出了
上限、账本和一个 `ai-cost` 命令 —— 全都架在一个我们自己声明过不可信的数上。
现在只报 token:那是 API 回的硬数字,也是唯一能拿去和账单对上的东西。

### 两个默认值是故意保守的

- **`allowedDomains` 默认空(不限制)。** spike 说 `allowed_domains` 是中文攻略站问题的
  现成解法,但 API 只提供**硬过滤**,而"中文攻略站在搜索索引里的实际覆盖率"还没实测。
  默认就把搜索锁死在几个站上,是拿没量过的假设换质量。要偏向中文站,先在提示词里说
  (提示词属于 guidegen),真需要硬锁再往这个数组里填。
- **`maxFetchTokens` 默认 50000。** SKILL.md 8.3 要的是 `get_page_text(400000)` 那个量级,
  但 `max_content_tokens` 的实际上限还没验过。往上调是旋钮,不是改代码。

`fallbacks` 默认**开**(被分类器拒答时服务端换个模型重跑同一个请求)。代价是多带一个
beta 头,万一账号不认那个头会整个请求 400——所以 400 的报错里专门提示了去哪关:
`"ai": { "fallbacks": false }`。

### 还没验的

**没有 API key 的机器上跑不了真请求。** 上面所有结论来自权威文档 + 离线测试;
`ai-check`(不带 `--dry`)第一次真跑之前,这些都属于"应该对"。真跑一次会打出
stop_reason、服务端工具调用次数、pause_turn 续跑次数、token 用量——先看那一行,
再谈质量。spike 里那三条待验(中文站覆盖率、`max_content_tokens` 上限、搜索计费)
也要等第一次真跑才有数据。

## lib/guidegen.js 落地记录(2026-08-10)

流水线通了:取成就数据 → 联网研究 + 撰写 → 机械打勾 → 校验 → 回灌重写(最多 3 轮)→ 落盘。
入口 `node tracker.js guide-gen <appid>`。离线测试 31 条在 `test/guidegen.test.js`。

### 三件事改成了结构性保证,不再靠检查

1. **勾选状态** —— 提示词明令只写 `- [ ]`,写完由 `computeCheckedKeys` 按数据库填。
   解锁状态也不喂给模型(设计里就定了)。
2. **`# 游戏名` 和 `appid:` 两行由程序写**,并且**主动削掉模型自己写的那两行**。
   这两行是纯数据,库里就有;让模型转录一遍等于凭空多一次写错的机会,而 **appid 写错
   一位数,攻略就登记到另一款游戏上**——两边都不会报错。提示词里也说了别写,
   但结构性保证不能靠模型听话。
3. **草稿一律写进 `guides/.drafts/`**。落地前按设计文档要求核对了发现逻辑:
   `syncGuidesFromMarkdown` 是 `readdirSync`(**非递归**)+ 只认 `.md`,子目录进不了它的
   视野。测试里直接拿真的发现函数扫一遍草稿目录,断言 `files === 0`——这条是整个
   测试文件里最要紧的一条。

### 一个设计漏洞:同名成就会让攻略永远过不了关

`computeCheckedKeys` 对名字撞车的成就一律跳过(分不清是哪一个,宁可漏勾不能勾错),
于是那些成就**解锁了框也不会被勾上**,而 `checked-mismatch` 会照报不误 —— 三轮改写全部
浪费在一条**模型根本改不动**的错上(它连 checkbox 都不许写)。CLAUDE.md 记的 12 款同名
游戏里,中英文都同名的有 3 款,全都会踩。

处理办法是新增 `unnameableApiNames(defs)`(在 guidelint.js,复用现成的名字索引):
两个名字没有一个是本作独一份的成就,它们的 `checked-mismatch` 算**预期内**,不拦。
豁免必须**按名字**算 —— 中文名撞车、英文名唯一的照样勾得上(9/12 是这种 Steam 本地化
bug),错误豁免会把真问题藏起来。这和 2026-08-09 那次「闸门按名字关」是同一条规则。

#### 同一个漏洞的第二个出口(2026-08-17)

上面那段原来还有一句「**只有 `checked-mismatch` 能这样豁免**」。那句话是错的,而且它
一直挡着一个形状完全相同的问题:

`ambiguous-no-description` 这条规则要求同名成就必须抄描述原文(那是区分它们的唯一凭据)。
但**如果 Steam 上那个描述本身是空字符串,就没有可抄的东西** —— 谁都修不了。校验器自己
知道这件事:消息写着「不是攻略的错」,还算了一个 `fixable: Boolean(d.description)`。

然后那个字段**没有任何生产代码读它**,唯一提到它的是一条断言它被设上了的测试。

代价是实测出来的:《KINGDOM HEARTS -HD 1.5+2.5 ReMIX-》是四合一合集,KH1 / Re:CoM /
KH2 / BbS 各自都有一个 `Proud Player`、`Hero of the Coliseum`、`Treasure Hunter`,
16 个名字撞车、15 个成就描述为空。一份 **197/197 全覆盖**的攻略被这 15 条拦在门外,
而且因为 `ambiguous-no-description` 在 `MODEL_FIXABLE` 里,三轮全花在让模型去抄不存在的
描述上,最后什么都没落地。

**判据是:有没有任何人的任何操作能消掉这条?** 没有 ⇒ 它属于 `expected`,报出来但不拦。

修法是**拆成两个 code**,而不是去读那个布尔字段:

| code | 含义 | 拦不拦 | 回灌给模型 |
|---|---|---|---|
| `ambiguous-no-description` | 描述存在,攻略没抄 | **拦** | **回灌**(重写就能修) |
| `ambiguous-empty-description` | Steam 上描述是空的 | 不拦(进 `expected`) | 不回灌 |

为什么是 code 而不是布尔:这个项目里「这种失败能不能补救」一律按 `code` 分流
(`MODEL_FIXABLE`、`splitFindings`、`CLI_HINTS` 全是),再加一个只有这条规则会设的布尔值,
就是给同一个问题开第二套机制 —— 而第二套机制没接线正是这次的故障本身。

两个细节:

- **这条豁免不看 `unnameable`**,和 `checked-mismatch` 那条不同。后者对任何成就都会报,
  所以需要那道闸;这条的触发前提本身就含「名字撞车」,比 `unnameable` 更窄,加上去是个
  恒真判断,读起来像有疑问。
- **不拦 ≠ 不说。** 那几个框**永远**不会被自动勾上,所以 CLI 把名字列出来、Dashboard
  的**成功**那一条也带上(`unsyncable`)。不报的话,「有 15 个框几个月一直没动」会被
  当成同步坏了。消息里的名字改用 `d.name_cn || d.name_en` 而不是 `byName` 的键 ——
  那个键过了 `normalizeText`,弹窗里显示的是 `proud player`,而 Steam 上写的是
  `Proud Player`。

### 回灌只回灌模型改得动的

`checked-mismatch` **永远不进回灌清单**。把它发回去等于要求模型写 `- [x]`,而
"模型只写 `- [ ]`、程序按数据库打勾"是这套设计的地基。真出现一条豁免不掉的
`checked-mismatch`,说明是我们自己的打勾出了问题,当场停下来说清楚,别再问模型。

### 落盘闸门

按可逆性分,不按后端分(设计里定的):

- **新建文件** + 机器闸门过了 ⇒ 自动写。写完**重新读一遍再验一次**——"调用成功 ≠ 内容
  正确"是这个项目栽过的跟头。然后调**真正的发现逻辑**(`syncGuidesFromMarkdown`)登记,
  不自己 upsert,省得两处对"标题怎么取""后端冲突怎么办"的理解慢慢跑偏。
- **覆盖已有攻略** ⇒ 默认**拒绝**,`--overwrite` 才放行(2026-08-11 做出来了)。放行之后
  仍然是"先能回退,再动手":先读旧攻略 → 备份原文(本地拷 `.md`,Notion 存原样 block JSON)
  → 把会失去的东西讲清楚 → 人工确认 → 才写。**备份失败就一个字都不写。**
- 所有拒绝理由都在 `planGuide()` 里**一次性给完**(没有成就详情、成就太多、已有 Notion 页、
  文件已存在、Steam 给不出解锁状态),不能跑到一半、花了钱才发现。

**Steam 拿不到解锁状态就不生成。** 全部不勾的攻略是一份错的攻略,而且会被校验器报成
一堆 `checked-mismatch`,看着像模型写错了。

### 顺手做了半步第 5 步

`guide-gen` 默认会问一句「这一步会调用 AI 并产生费用。继续?」(`--yes` 跳过)。
一个默认不问就花钱的命令实在不该存在,所以先把最低限度的闸门加上。

**后来这句确认成了唯一的闸门** —— 第 5 步的硬上限做出来之后又整套删了,
理由见上面决策表「花钱」那一行。

### 还没验的

和 `lib/ai.js` 一样:**真跑一次需要 API key**,这台机器上没有。上面所有断言来自离线测试
(假供应商 + 假 Steam)。第一次真跑要看的是:模型认不认"每个成就一行 checkbox"这条硬规则、
44 个成就的攻略一轮能不能过、`missing-checkbox` 的回灌管不管用、以及一份攻略实际花多少钱。

## Gemini 落地记录(2026-08-10)

### 为什么第二家是 Gemini 不是 OpenAI

原计划第二家是 OpenAI。换掉的**直接原因是没法测**:Anthropic 是按量付费、没有免费层,
而本机没有 key,于是整条流水线写完了一次都没真跑过。**OpenAI 同样没有可用的免费额度**
(试用金名存实亡,唯一的免费 token 计划要用"共享数据训练"来换),所以它解决不了这个问题。
Gemini 有免费额度,能让流水线第一次真正跑起来。

顺带一提,这也让第二家回到了它本来该有的价值:**降低用户的门槛**。方案的目标是
"让用这个应用的人用他们自己的 key",而一个有免费额度的选项比第二个付费选项有用得多。

「有服务端搜索」这条硬性准入没有放宽:Gemini 的 Google Search grounding 就是服务端搜索。

### 这个文件是在拿不到文档的情况下写的

写 `lib/ai-gemini.js` 的时候网络工具连续不可用(和 spike 那天一样),字段名、模型名、
工具名全部来自记忆,**没有对着官方文档核对过**。

应对办法不是赌记性,是**把每一个不确定的地方做成运行时能自己回答的**:

- **模型名可配置**,而且 `node tracker.js ai-check --models` 直接问 API 要列表。
  猜错了不用改代码,问一句就知道
- **工具声明可配置**(`ai.geminiTools`)。工具改名、或者免费层不给用,也是改配置
- **思考预算不配就完全不发那个字段**,让模型用自己的默认值——发一个可能不被接受的字段
  比不发更容易出错
- **搜索到底有没有发生,看回包不看文档**。`groundingMetadata.webSearchQueries` 是模型
  实际发出去的搜索词;声明了工具却一条都没有,`ai-check` 会专门警告一行。
  **这比读一份可能过期的定价页可靠得多**——"免费层带不带 grounding"这个问题,
  第一次真跑就自己回答了

错误信息也照这个思路写:404 指向 `--models`,工具相关的 400 指向 `ai.geminiTools`,
429 说清楚免费层有每分钟和每天两道上限、撞上后者当天重试多少次都没用。

### 一个 Anthropic 那边没有的失败模式

`finishReason: 'RECITATION'` —— 模型因为大段复述受版权保护的内容被拦下。**写攻略正好是
高危场景**:我们明确要求它原文照抄官方描述,还要它读 wiki。所以它单独成一类
(`stopReason: 'recitation'`),给一条能照着做的信息,不和普通拒答混在一起。

注意那条信息里专门写了一句:**不能为了绕开这条限制而改掉"官方描述原文照抄"**——
那是整个匹配系统的地基,改了等于把功能废掉。

### 拆文件 + 统一词汇

`lib/ai.js` 加一家会超过 800 行,所以先拆:

| | |
|---|---|
| `lib/ai.js` | 公共部分:用量记账、估价、会话、SSE 拆包、结果判定、供应商注册 |
| `lib/ai-anthropic.js` | Anthropic 的请求格式、块拼装、pause_turn 续跑 |
| `lib/ai-gemini.js` | Gemini 的请求格式、chunk 拼装、grounding |

拆的时候顺手统一了两处词汇,**都是为了让上层不再出现"如果是这家就……"**:

- **`stopReason` 在供应商边界上就翻译成同一套**(`end_turn` / `max_tokens` / `refusal` /
  `recitation` / `other`),原值留在 `rawStopReason` 里备查。**认不出来的一律落到 `other`
  并判为不可用**——默认当成功处理的话,以后哪家加一个新的终止原因,失败的生成会看起来
  像成功。
- **进度事件也归一化**(`text` / `tool` / `tool-result` / `search`)。CLI 的实时输出和
  guidegen 的进度条因此不认识任何一家的原始格式,加第三家不用改展示代码。

联网工具的声明从模块级函数 `buildWebTools()` 改成了供应商方法 `provider.webTools()` ——
两家的形状完全不一样,编排层不该知道。

### 第一次真正碰到 API 的结果(2026-08-10)

`ai-check --models` 跑通了,这是这个功能**第一次真的连上供应商**。两条实测结论:

**1. 免费层对 Pro 系列的额度是 `limit: 0`。** 原文:

```
Quota exceeded for metric: generativelanguage.googleapis.com/generate_content_free_tier_requests,
limit: 0, model: gemini-2.5-pro
```

**这不是"用完了",是这个模型压根不在免费层里。** 等次日重置永远不会恢复。
Google 把两件事用同一个 429 报回来,而错误信息里唯一的区别就是 `limit: 0` 这几个字。
第一版提示写的是"配额用完了,等次日重置",会让人白等一天;而且重试逻辑把它当可重试的
429,白白退避了三次。两个都修了,并且钉了测试。**要用免费层就得挑 flash 系列。**

**2. 默认模型名过期了,而且是双重过期。** 写代码时凭记忆默认写的 `gemini-2.5-pro`,
到 2026-08 既不是当前主力(列表里已经有 3.1 / 3.5 / 3.6 系列),又正好撞上上面那条。
默认值因此改成 `gemini-flash-latest` 这个**别名**:具体版本号必然会过期,别名由 Google
维护。代价是行为可能悄悄变,所以文档里写明**要可复现就 pin 一个具体版本**。

这两条正好验证了"把不确定的地方做成运行时能自己回答的"这个做法——`--models` 是唯一
让我们发现默认值早就不对了的东西,而它只花了一次请求。

**还没验到的:** 429 挡在前面,所以联网 grounding 到底给不给、`webSearchQueries` 回不回来,
仍然未知。换 flash 模型之后才能知道。

### 记账

Gemini 的模型曾经**故意不进价格表**:免费层确实是 0,但付费层单价没核实过。
后来价格表整个删了 —— 那条"不给没核实的数字"的规矩,对每一家都成立,不只 Gemini。
现在一律只报请求数和 token 数,而跑在免费层上时,那本来就是唯一有意义的计量单位
(配额是按这个算的)。

有一条要在第一次真跑时核对:`thoughtsTokenCount` 被合进了 `outputTokens`,理由是思考
在计费上算输出、和 Anthropic 那边口径一致。这是推断,不是查证过的。

## 第一次真正跑通(2026-08-10)

流水线端到端跑完了:《部落幸存者》51 个成就,**第一轮就过、0 条要改**,207 秒,
逐条核对勾选状态 0 条不一致。用的是 **DeepSeek**。

### 供应商:同一家、两个端点、能力不同

这是这一轮最值钱的一条,而且我一开始判断错了:

| 端点 | 服务端搜索 | web_fetch |
|---|---|---|
| `api.deepseek.com/chat/completions`(OpenAI 兼容) | ❌ 没有 | ❌ |
| `api.deepseek.com/anthropic`(Anthropic 兼容) | ✅ **有** | ❌ 不认 |

我照 OpenAI 兼容那个端点实现,得出"DeepSeek 没有联网"的结论,然后把这个结论套到了
整家公司头上。实测证据没有模糊空间:带 web_search 时回包里有 `server_tool_use` +
`web_search_tool_result` 块、`usage.server_tool_use.web_search_requests = 4`,
答出了具体日期和版本号;同一个模型不给工具时老老实实回"查不到"。

**所以不用为它另写一套** —— `AnthropicProvider` 加一个可配置的 `ai.baseUrl` 就够了,
服务端工具循环、pause_turn 续跑、web_search 解析全是现成的。

两个配套开关,都是被 400 教出来的:
- `ai.webFetch` —— 兼容端点默认不发 web_fetch(它不认,整个请求会挂)
- `ai.anthropicExtras` —— `thinking` / `output_config` / `fallbacks` 这些 Anthropic 专有
  扩展,配了自定义 baseUrl 就默认不发

### 难度信号:Steam 的全球解锁率

`GetGlobalAchievementPercentagesForApp`,**不需要 API key**,返回每个成就的全球解锁率。
实测《部落幸存者》51 条全部对得上 `api_name`,最难 1.1%、最容易 64.5%,**差 60 倍**。

不给这个信号时,模型光看名字和描述分不出哪条难,只能把力气平摊。现在每条后面标
`🔴 全球仅 1.1% —— 这类要写深` / `⚪ 64.5% —— 一两句带过`,并明说"力气按它分配"。

**效果体现在"搜什么"上**:搜索词从一条泛泛的"全成就攻略",变成
"大城堡 奢华住宅 花园别墅""摸鱼勇者 负面效果"这种对着难成就去的。

### 一个否定结果:加预算没用

改动:`maxSearches` 6 → 30、`maxTokens` 16000 → 32000,提示词也明写了"难的要写深"。

| | 旧 | 新 |
|---|---|---|
| 输出 token | 13975 | 24960(+79%) |
| 攻略实际字符 | 5999 | 6433(**+7%**) |
| 🔴 那 12 条平均心得字数 | 100 | 99 |

**多出来的 11000 token 几乎全进了思考,没进攻略。** deepseek-v4-flash 是推理模型,
给它 token 空间它就多想一轮。**预算不是深度的瓶颈**,下次别再从这里下手。

### 一年后的补记(2026-08-17):同一件事从另一头看,是**唯一有效的提速旋钮**

上面这条结论没错,但它只说了一半。「加预算没用」量的是**天花板**——而思考根本没顶到
那个天花板,所以抬高它当然什么都不换。真正决定它想多久的是另一个字段,
`output_config.effort`,而那个字段**在实际跑的这条路上从来没被发出去过**。

原因是三个参数捆在一个开关上:

```
extras = ai.anthropicExtras ?? !ai.baseUrl
```

这个式子问的是「**这是不是官方端点**」,而它被拿去回答「**这个字段会不会被拒**」。
两个问题在 DeepSeek 的 `/anthropic` 上答案相反:它不是官方端点,但它认这个字段。
而 `provider: "deepseek"` 预设总会设 `baseUrl` —— 于是 `config.js` 里那个注释写着
「深浅旋钮」、默认 `'high'` 的配置项,一次都没被送出去过。

实测(2026-08-17,同一段 10 个成就,带联网工具,背靠背):

| 发过去的 | 墙上 | 思考 | 搜索 | 正文/成就 |
|---|---|---|---|---|
| 什么都不发(当时跑的) | 337 s | 145955 字 | 8 | 255 字 |
| `effort: medium` | 219 s | 94104 字 | 6 | 275 字 |
| `effort: low` | **43 s** | 15523 字 | 2 | 211 字 |
| `thinking: disabled` | 6 s | 0 | **0** | 117 字 |

基线那次,**337 秒里有 332 秒花在吐出攻略第一个字之前**。

三条结论,每条都改了代码:

1. **`thinking` 和 `effort` 必须能分开发。** 同一个 `effort: low`,多带一个
   `thinking: {type:'adaptive'}` 就从 43 秒变 87 秒、思考量翻倍 —— adaptive 会把
   effort 顶掉。捆在一起时,唯一管用的旋钮既发不出去、发出去也会被同伴压住。
2. **`thinking: disabled` 不是「更快的 high」。** 它把联网搜索一起关掉了(跑两次都是
   0 次),也就是模型凭记忆写攻略 —— 正是 `canSearch` 那套准入设计要防的、
   用户看不出来的质量差别。留着能配,但它不该出现在任何推荐档位里。
3. **「这个端点认不认某个字段」是逐个端点量出来的事实,不能从 baseUrl 推。**
   所以改成一张只列实测过的端点表,没量过的一律不发 —— 那些端点今天本来就没在收
   这个字段,给它们新发一个可能被拒的参数,是拿别人的可用性换我们的速度。

**为什么允许把它调低。** 因为代价是看得见的:思考量、搜索次数、每成就字数三者同向
移动,而 `searchQueries`(「能搜 ≠ 搜了」)本来就每次都打在 CLI 和 Dashboard 上。
所以调低 effort 不是静默降级,是一个用户每次生成都能读到数字的取舍 ——
这和 `thinking: disabled` 把搜索归零、却什么都不说,是两回事。

### effort 换掉的是**广度**,不是深度(2026-08-17 质量 A/B)

上面量的全是速度。这一节量的是**代价**,而结论和直觉相反。

做法:同一款游戏、同一套 system prompt、同一句分段提示词,只改 effort,背靠背跑两遍,
两份正文都落盘让**玩通过这游戏的人**读。挑的是 Return of the Obra Dinn(653530,
16 个成就一段写完,纯推理解谜,攻略好不好一眼看得出)。

| | 墙上 | 搜索 | 正文总量 |
|---|---|---|---|
| `high` | 280 s | 5 次 | 1643 字 |
| `low` | **35 s** | 2 次 | 1633 字 |

**八倍,而正文总量几乎一样。** 到这儿为止,任何一个自动算出来的数字都会说"没有代价"。

再按难度拆开,还是说不出代价 —— 反而像是 `low` 更会分配力气:

| 全球解锁率 | high | low |
|---|---|---|
| 7.0% 船长干的 | 454 | **542** |
| 44.6% 奥伯拉癸 | 116 | **205** |
| 45–62% 那 13 条 | 787 | 626 |

**两个读法都是错的。真正的差别要读正文才看得见:16 条里 `low` 有 9 条是套模板的,
`high` 一条都没有。**

```
low :  第 III 章(凶案)全体查证正确即解锁。
       第 IV 章(召唤)全体查证正确即解锁。
       第 V 章(邪恶俘虏)全体查证正确即解锁。          ← 九条,一个句式填章号和名字

high:  召唤    —— 叛变者劫走宝箱、乘救生艇离船的一章,死亡多发生在海上
       邪恶俘虏 —— 本章起海妖登场,死因列表里开始出现「被怪物」类选项
       劫数    —— 海怪袭击的一章,不少人被卷入海中下落不明,别忘了书里「失踪」这一栏
```

那九条模板句**不查任何资料也写得出来** —— 素材全在我们自己发过去的成就清单里。

**而这直接对得上多出来的那几次搜索。** `high` 第 5 次搜的是
`Obra Dinn chapter list "Loose Cargo" "A Bitter Cold" ... chapter contents` ——
它就是去查"每一章讲什么"的,而那次搜索的产物,正好就是 `low` 缺的那九条。

所以这根旋钮真正在调的是:**要不要花力气去了解这游戏本身。** 它换掉的是攻略的
**广度**(那一大批中等难度的条目有没有内容),不是最难那几条的**深度** ——
最难那条上 `low` 反而写得更能照做(人名带编号 `#1`/`#4`/`#28`、给了"报告第 3 页
核对 `Murder of crewmate (57)`"这种自检方法、用编号列表而不是 `<br>` 堆在一段里)。

**中档补跑(2026-08-18):三档其实是两档。** 同一款游戏同一套提示词,`medium` 跑出
262 秒、4 次搜索、**0 条模板句** —— 和 `high`(280 秒、5 次、0 条)在两个轴上都分不开,
而那 18 秒的差距远小于这条路的方差。断崖只有一处,在 `medium` 和 `low` 之间。

| 档位 | 模板句 | 正文总量 | 最难 5 条 | 搜索 | 墙上 |
|---|---|---|---|---|---|
| `high` | 0 | 1643 | 856 | 5 | 280 s |
| `medium` | 0 | 2393 | 1061 | 4 | 262 s |
| `low` | **9 / 16** | 1633 | 1007 | 2 | **35 s** |

中档那份的章节条目甚至比 high 更具体(点到吊床编号、谁杀了谁),但**每档只有一个样本,
不足以说 medium 比 high 好** —— 能说的只有"低档以外的档位之间分不出来"。

这直接决定了控件形态:三档在效果上**不等距**,而滑块的形状本身在暗示均匀,所以用
三个离散按钮。

> **顺带记一次自己的失误。** 中档第一跑失败了(352 秒、6 次搜索、0 字正文),而我的

一处 `low` 确实漏了:互斥的固定写法

### 一个会撒谎的参数:`thinking.budget_tokens`

官方端点上它是 400。DeepSeek 的 `/anthropic` 上**比 400 更糟**:HTTP 200,然后
朝反方向走 —— 要 2000 得到 49653 字思考,要 8000 得到 62107 字,而**完全不发这个字段
才 38196 字**。一个存在意义就是设上限的参数,在最需要它的地方把下限抬高了,还不报错。

`buildBody` 一律不发它,`ai.test.js` 在两种端点形状上都钉住了这一条。
和 Notion 悄悄吞掉状态属性的 `groups` 是同一类事情:**200 不等于它照做了。**

### 另一条要记的:这条路上的绝对时间不可复现,比值才可信

同一段 10 个成就、同一个提示词、同一个模型,什么都不发跑三次:
**76 秒 / 174 秒 / 337 秒**,思考 18158 / 38196 / 145955 字。同样的输入,8 倍的差。

所以任何单次数字(包括 KINGDOM HEARTS 那次 32 分钟)都是从一个很宽的分布里抽的一个点,
拿它线性外推会得出 25 到 110 分钟不等的估计,而真值是 32。**要比就同一批背靠背比,
报比值,别报绝对值。**

这也顺带回答了「进度条为什么给不出剩余时间」:方差不在网络上,在模型每次决定想多久。

### 但"字数"本身就是个错的度量

上面那张表让我判断这次改动没效果。**作者(玩过这款游戏的人)的判断是显著变好了。**
两边都没错 —— 搜索变准之后,**同样 100 字里装的东西不一样了**,而字数量不出这个。

这件事值得单独记:**攻略质量没有机器可读的代理指标**。字数、覆盖率、warn 数量,
量的全是格式和数据。这正是方案一开始就写明的那条边界(「机器验不了攻略内容对不对」),
只是真做起来的时候很容易忘,拿一个能自动算的数字当成质量。

### 分批:机制做了(2026-08-11),但**深度那一问仍然没测**

模型是按**整份列表**分配注意力的,51 行里的一行天生写不长。同一套配置跑
Automachef(11 个成就)平均 110 字、最深 207 字,而 51 个成就那份是 67 / 116 ——
方向一致,**但这个对比有混淆**(换了游戏,可查资料的多少也不一样),不能当结论。

设计文档原来把分片定性成"100+ 成就游戏的上下文问题",这个定性不完整:
它同时是个**深度**问题,51 条就已经发生。

分批本身现在做出来了(`chunkDefs` + 同一 session 多轮,见决策表「规模」那一行),
但做它是为了解决**装不下**,不是为了解决**写不深**:每段没有独立的搜索预算,
也没有"先出分节方案再逐节生成"那一步。所以上面那个混淆的对比**仍然没有被干净地验证过** ——
要验就得拿同一款游戏、同一套配置,只改每段大小,比每条心得的字数。
**在跑出那个数字之前,不要声称分批提高了质量。** 它目前只被证明能让写不完的游戏写得完。

### 各段并发(2026-08-17)

分段本来是为了解决"装不下",它顺带带来了一个纯粹是实现造成的开销:**各段排队。**

各段的内容互不相交 —— 每段的提示词点名了它要写的编号区间和首尾成就名。
它们之所以只能一段一段跑,唯一的原因是**全篇共用一个会话,而一个会话就是一条链**。
改成每段一条链之后,第一轮从"各段之和"变成"最慢那一段"。真端点上验过:
3 个并发请求,不限流,`ai.concurrency` 默认 3,设 1 退回原来的顺序行为。

共用会话买到的是两件事,拆开之后各自有交代:

- **成就不会重复** —— 本来就不靠它。每段被点名了自己的区间,这是结构保证。
- **小节标题会重复** —— 这个是真的。相邻两段都属于「主线」就会各写一行 `## 主线`。
  提示词因此从「别把小节标题再写一遍」改成「该开就开」,拼接时由 `joinBodies`
  合掉紧挨着的同名标题(同名**且同级**,且只在段首)。**老那句话在并发下是有害的**:
  它让一个看不见前文的模型去省略一个只有它能写的标题,结果那几条就悬在上一段的小节底下。

顺带省掉一笔没人算过的账:共用会话时每段请求都要把**前面所有段的正文连同 thinking**
重发一遍,KINGDOM HEARTS 到第 4 段时上下文已经十几万字符。

四处必须跟着改,每一处都是"不改也不报错"的那种:

1. **切小不能再动共享数组。** `chunks.splice(i, 1, a, b)` 在顺序下没问题,并发下是
   数据竞争 —— 一段切自己一刀,正在跑的别的段编号当场错位,而错的是提示词里的段号、
   失败报告的段号、和下一轮的重写目标,**没有任何东西会报错**。改成各切各的格子,
   跑完再按 `(段, 子段)` 摊平,顺序和谁先跑完无关。
2. **失败的段号在池子跑完之后才算。** 顺序版能当场记,靠的是"切分只发生在当前下标、
   循环只往前走";这两个前提都没了。
3. **抛出去的要是段号最小的那个错,不是最先炸的那个。** key 不对会让在飞的请求一起
   失败,而谁先 reject 取决于网络快慢 —— 取"最先"意味着同一个输入两次跑报出不同的原因。
4. **用量要把每条链加起来。** 只报第一条会把绝大部分吞掉,而这个数是唯一能拿去和
   供应商账单对账的东西。

重写轮**故意不并发**:通常只有一两段,而切小过的段和它的母段共用会话,并发会让两个
请求同时写同一条 messages。收益小、失败方式脏。

还有一处是进度显示:并发之后好几段同时在写,而 `ask` 事件每段各发一次 ——
报"正在写第几段"会让那一行在 1/4、3/4、2/4 之间来回跳,看着像进度在倒退。
改成报**已写完几段**,单调,而且顺序跑时同样成立。

#### 真实验证(2026-08-18,《Raft》104 个成就)

单元测试证明得了代码在并发,证明不了真端点上整轮会变短。所以拿真路径跑了一遍 ——
真 `planGuide`、真解锁状态、真机械打勾、真校验、落 Notion 再回读。唯一的加工是
把 `provider.send` 包一层记时间戳(段数/请求数/攻略内容并发前后完全一样,**只有时间
能证明它在并行**)。

```
104 个成就 → 3 段 · concurrency=3
ok=true · 1 轮 · 0 次重写 · 104/104 checkbox · 勾上 51(Steam 实际 51)

总墙上时间        650 s
同时在飞的峰值      3
所有请求耗时之和  1192 s   ← 顺序跑至少要这么久
实测加速          1.83×

  #1    1– 312s █████████████████████████████
  #2    1– 245s ███████████████████████
  #3    1– 375s ███████████████████████████████████
  #4  375– 522s                                    ██████████████
  #5  522– 638s                                                 ███████████
```

**这一跑最值钱的地方是它撞上了 `resplit`。** 第 3 段在 375 秒撞 `max_tokens`,
而那时另外两段**已经跑完了** —— 这正是这次改动里最危险的那条路:顺序版的切分是
`chunks.splice(i, 1, a, b)`,直接改全局数组;并发下这么干会把别的段的下标整个挪位,
**而不会有任何东西报错**,只会让提示词段号、失败报告段号、下一轮重写目标各错各的。
它真的发生了,结果是 `ok=true` / 一轮过 / 104 条全覆盖。**「各切各的格子、跑完再按
(段, 子段) 摊平」是对的,而这不是推出来的,是撞出来的。**

**1.83× 低于 3 段的理论上限,原因也在图里:#4 #5 是串行的尾巴。** 切出来的两半
共用母段的会话(重写要看得见"你上一版写了什么"),所以只能一前一后跑,而且是在别的段
都收工之后。没有这次切分的话,墙上时间约 375 秒、之和约 932 秒 —— **2.5×**。
这是取舍不是缺陷,但它解释了为什么实测会低于段数:**一次切分就把加速比从 2.5 拉到 1.8。**

> 想再往上抬只有一条路:让切出来的两半各自开会话、丢进同一个池子。**代价是它们之间
> 最需要的那点上下文没了** —— 相邻的两半正是最容易写重、最需要"看得见对方"的一对。
> 没做,记在这里免得下次当成漏掉的优化。

> **这次改动最难测的地方:段数、请求数、攻略内容全都不变,只有墙上时间变了。**
> 也就是说把并发池换回 `for` 循环,整套测试一条都不会红。所以测试里直接量重叠 ——
> 挂住每段的请求,数同时在飞的有几个。变异验过:换回顺序立刻红。
>
> 另外两条也是变异逼出来的。「撞墙后不再派新活」第一版用 8 段 + 并发 2、脚本只给两条,
> 于是每条泳道都是被自己那次错误停下的,`stop` 拿掉照样绿 —— 得让**不出错的泳道有活可接**
> 才测得到它。「报段号最小的错」第一版只让一段失败,排序和不排序结果一样,
> 得让两段都炸、且**段号小的那个慢一点炸**。

   `overwritePreflight` 加个参数 —— 同一段措辞服务两种问法两边都会写歪,这个项目在
   `inspectGuideDb` 和 `previewGuideRewrite` 上已经两次得出同一个结论。

   经 `previewGuidePatch` 下发),清单顶上两片**筛选**(稀有 / 未解锁,两片都按下
   = 且),计数旁边是「全选」——**收的是当前显示出来的那批**——和「清空」。
   筛选只改显示、不碰选择,所以按下态的含义就是"我按了它"。
   **发出去的永远是一串点名的 api_name**,走后端
   `resolveScope` 的显式列表那条分支 —— 界面不需要自己的选择器种类,而且同名成就
   按名字点不动(库里真有 12 组同名)。

   界面上不做的两件事,都是想清楚了不做的:
   (a) **算出来的选择器不做成范围档位。** `rare` / `locked` / `section` 在 CLI 上
   是选择器,在界面上是**筛选**(小节那一层是列表里的三态方框)—— 因为属性之间
   **互相重叠**(那唯一一条未解锁的成就恰好也稀有):做成"选中一批"的开关会出现
   "没人按过它,它自己亮了";做成只加不减的动作则只能表达并集,交集要不到。
   筛选两样都没有,而且"两片都按下 = 且"是白捡的。
   `thin` / `failing` / `all` 这几个连 CLI 也一并删了:界面上给不出一个诚实的名字的
   东西,命令行留着也只是多一条没人敢用的路。
   (b) **自然语言 → 选择集** —— 这是唯一一个"解析错了要花钱才发现"的环节,所以排在
   算出来的选择器全部可用之后。现有这几种覆盖了绝大多数真实场景,而且不需要任何模型调用。

7b. ~~写 Notion(默认后端)~~ —— **已完成(2026-08-11)**。`lib/notionblocks.js` 做
   markdown → block 的转换,`planNotionTarget` 把该拒的都在花钱前拒掉,`landToNotion`
   写完**回读重校验**再登记。同样是补编号而不是重排 —— 理由和 3b 那条一样。
